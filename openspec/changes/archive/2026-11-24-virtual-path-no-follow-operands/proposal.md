## Why

The virtual path validator returns the path with every link resolved, the last component included, and every operation runs on that path (archived change `virtual-path-physical-normalisation`, design D3). That is right for an operation that follows its operand (open, `cat`, `cp`, `cd`), and wrong for one that acts on the last component itself:

- **Data loss on every platform, both access modes (pre-existing; verified on v0.17.0):** `rm link` deletes the link's target and keeps the link. The maintainer reproduced it on a v0.17.0 build.
- **Windows, both access modes (new on this branch, PR #198):** `rm -rf <junction>` deletes the junction's target tree. Under `full` access that tree may lie outside every allowed root.
- **Restricted access (new on this branch):** `rm -f stale` on a dangling link exits 0 and keeps the link; `rm outlink` (a link inside the root whose target is outside) is denied, although the link is inside; `ln -sf target.txt stale` writes a link at the dangling target's path instead of replacing `stale`.
- **Both access modes:** `[ -L live ]` and `test -h live` are false for a live link, because the stat handler examines the target.
- **Restricted access, hardening (all validated u-root built-ins):** operands are to be classified the way each built-in parses them, option values that name paths validated, and the file `gzip` writes for each operand validated too. Classifying them that way also hands value options to the built-in as written, so `mkdir -m 755 d` and `touch -d <time> f` work under both access modes.
- **Hardening (`virtual-sh` access checks):** `cd`'s access check and the `-r`, `-w` and `-x` tests are to run on the validated path, like the other file tests. On Windows this also keeps `cd` into a directory link or junction working once `-L` stops following the link, because mvdan emulates the access check there with a stat that does not follow the last component.

Maintainer decision 73 reverses the default accepted in decision 67 ("the returned path is the resolved path") for these operations, and PR #198 does not merge until they are fixed. Decision 83 adds the operand hardening to this change. In the same PR, the `cd` and file-test regression that mvdan.cc/sh v3.14.1 (#194) fixed gets a CLI test, and a `cd` outside the allowed roots now says it was denied instead of "no such file or directory".

## What Changes

- **Operations on the last component no longer follow it** (both access modes): `rm` operands (with `-r`/`-rf` too), `mv` source operands, `ln`'s link name (both the `-f` removal and the creation), and the shell's `-L`/`-h` file tests. The parent directory is resolved physically, as before, and the final name is kept as written. Under `restricted` access that path must be inside an allowed root.
  - `rm link` removes the link and leaves its target. `rm -rf <junction>` on Windows removes the junction and leaves the target tree. `rm -f stale` removes a dangling link. `ln -sf target.txt stale` replaces `stale`. `mv link dir/` moves the link. `[ -L live ]` is true.
  - Under `restricted` access, removing or moving a link that lies inside an allowed root is allowed even when its target is outside; the target is not touched. A link whose parent directory is reached through a link that leaves the roots is still denied.
  - An `rm` operand, an `mv` source or `ln`'s link name that ends in a separator, `.` or `..` keeps full resolution, and is refused with "not a directory", naming the resolved path, when that path exists and is not a directory (read without the separator, so the check is the same on every platform). So `rm live/`, `rm -r live/`, `rm -rf live/` and `rm -f live/`, with `live` a link to a file, fail and keep the file, as on a host shell; `rm -r dirlink/` follows the link and removes the target directory's tree (design D1). The shell's `-L`/`-h` tests cannot see a trailing separator, because mvdan cleans the operand before the stat handler runs: `[ -L live/ ]` is true for a link, where a host shell says false (design Risks).
  - On macOS, `rm -r /tmp` is now refused under `restricted` access: the link `/tmp` itself is outside the allowed root `/private/tmp`.
- **Operands are found as each built-in's parser finds them** (all validated built-ins: `base64`, `cat`, `cp`, `find`, `gzip`, `ls`, `mkdir`, `mv`, `rm`, `shasum`, `tar`, `touch`; design D4). The registry reads the arguments with the built-in's own preprocessing and Go's `flag` package, from an option table that a test keeps equal to u-root's, and validates each operand it finds, whatever it starts with, except `cat`'s lone `-` (standard input) and the operands of `tar` with only `-t`/`-list` (which `tar` does not read): a lone `-` is a validated file name for the commands other than `cat`, `find`'s starting path is validated wherever it stands, and `tar`'s operands are validated in every mode that reads them, as is its archive path. Option values that are not paths (`mkdir -m`, `touch -d`, `shasum -a`, `gzip -S`) reach the built-in as written. The output path `gzip` derives from each operand is validated as well, and a `gzip -S` suffix that contains a path separator is refused under both access modes (design D4 step 7). A `--` before the operands ends the options, as on a host shell, and is not handed on. An option the built-in rejects stops the command before it touches anything. The wrappers' declared options are corrected to u-root's (`touch` has `-d`, not `-t` or `-r`).
- **Access checks run on the validated path** (both access modes, every platform; design D3, "The access handler"): `cd`'s access check and the `-r`, `-w` and `-x` tests go through an access handler that resolves the path in full, following its last component, checks it against the allowed roots under `restricted` access, and only then hands the resolved path to the shell's own access check. A refused path makes the test false and `cd` fail. `cd` into a directory link or junction, and `-r`/`-w`/`-x` on a link, test the target on every platform; `-L` and `-h` still test the link.
- **Every other operation keeps full resolution and today's decision** (which operands each built-in has is D4's subject; how each one is resolved does not change): opens and redirections, `cat`, `cp`, `cd`, `ls`, `touch`, `tee`, `find`, `tar`, the `mv` destination, the other file tests, Lua `io.open`, `require` and `invowk.path`.
- **virtual-lua:** its own file API has no remove, rename or link function (`os` exposes only `getenv`; `io` opens files). Its built-ins called through `invowk.cmd` and `invowk.capture` get the same rules (the no-follow operands of `rm`, `mv` and `ln`, and D4's operands), because they run through the same built-in registry.
- **`cd` denial message:** under `restricted` access, `cd` to a directory outside every allowed root prints `cd: virtual path denied: <path>` before the shell's own message, and exits 1. A `cd` to an empty path gets only the shell's own message. A CLI test covers `cd` and the file tests (`test -f`, `[ -e ]`, `[ -d ]`, `[[ -f ]]`, and, once this change lands, `[ -L ]`) inside the roots under both access modes, with a native mirror, and asserts that nothing panics.
- **Formal follow-ups of PR #198 folded in:** the walk's helpers are accounted for in the correspondence table, the `normalize` row's element becomes `normalized` and leaves `unresolved_elements`, the superseded F18 calibration figures are marked as such, and the `VirtualPathHarness` budget is labelled with its source. The model and golden do not change. The no-follow form is recorded as an abstraction in its own row (design D7).
- **Docs:** `virtual.mdx`, `virtual-lua.mdx`, their pt-BR copies and the README say which operations act on the link itself.
- **Not changed:** what any path that follows its last component may reach (no containment decision changes for a path; D4 changes which arguments are classified as operands and checks `gzip`'s output path, and the access handler checks the paths of `cd`'s access check and `-r`/`-w`/`-x`, so each of them gets that decision), the `mv` destination's full resolution (a known difference from a host shell, design Risks), F15 (the workdir as an allowed root), Windows alternate data streams (`j:s`), and the race between the check and the operation. Follow-ups set aside by the maintainer: design Open questions.

**Release note (data-loss fix, no breaking marker):** "Virtual runtimes: removing, moving or re-linking a symbolic link now acts on the link itself. Before, `rm link` in `virtual-sh` (and `invowk.cmd.rm` in `virtual-lua`) deleted the file or directory the link pointed to and kept the link, and on Windows `rm -rf` of a junction deleted the junction's target directory, outside the allowed roots too under full access. Now `rm`, `rm -r`, the source of `mv` and the link name of `ln` act on the link or junction, and `[ -L path ]` / `test -h path` report symbolic links correctly (a Windows junction still tests false, since these tests check for a symbolic link only). `rm link/`, for a link to a file, now fails with `not a directory` and keeps the file. On macOS, a restricted `rm -r /tmp` is now refused, because the link `/tmp` lies outside the allowed root `/private/tmp`. Under restricted access a link inside an allowed root can be removed or moved even when its target is outside; the target is never touched. Opening, reading, copying and writing through a link still follow it and are checked against the allowed roots as before. A restricted `cd` to a directory outside the allowed roots now says `virtual path denied`. Under restricted access, the operands of the u-root built-ins are classified the way each built-in parses them, option values that name paths are validated, and so is the file `gzip` writes for each operand; `cd` and the `-r`, `-w` and `-x` tests check access on the validated path, like the other file tests; `gzip -S` no longer accepts a suffix that contains a path separator; a `--` before the operands ends the options and is no longer passed on (so `cat -- file` reads only the file). `mkdir -m MODE` and `touch -d TIME` now work in the virtual runtimes; before, the value was taken for a path. The virtual runtimes are still not a sandbox: allowed host binaries run as normal host processes; use the container runtime for isolation."

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `virtual-runtime-sandbox`: "Checked and reported virtual paths are the resolved path" names the operations that do not follow the last component, and its junction scenario is inverted; "Virtual paths are resolved physically before the allowed-root check" allows a final name that is not inspected for those operations; "Unresolvable virtual paths are refused under restricted access" exempts the unread final name of a no-follow path; "Links inside allowed roots keep working" applies its acceptance to the parent's links for those operations (so macOS `rm -r /tmp` is judged by where the link lies); new requirements for the no-follow operations, for operands with a trailing separator, for how the operands of every validated built-in are found (with `gzip`'s output path), for the access check of `cd` and `-r`/`-w`/`-x`, and for the `cd` denial message.
- `module-path-containment-model`: new requirements for the no-follow form as a recorded abstraction of the harness model, with its own binding test, and for the walk's helpers in the correspondence table (a row each when a Linux killer reaches it, else named in the `normalized` row's abstraction cell; the lexical preparation left out and why).
