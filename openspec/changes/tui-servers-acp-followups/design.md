# Design

## Context

Eight independent items share one change (proposal.md, Why). Each decision below names the current behaviour it changes, with file:line on the base `origin/main` 88f44a6e.

- **Drawn table (D1).** `newTableModelWithStyles` builds the bubbles table with columns, rows, focus and height but no width (`internal/tui/table.go:375-380`); only `SetSize` sets one (`table.go:138-147`), and only the TUI-server overlay calls it (`internal/tui/embeddable.go:303-305`). The bubbles table's `View` is the header plus its viewport (`charm.land/bubbles/v2@v2.2.1/table/table.go:251-253`), and the viewport renders nothing when its width is 0 (`viewport/viewport.go:737-739`). So a directly drawn table, the path of `invowk tui table` without a TUI server (`cmd/invowk/tui_table.go:259-277` -> `table.go:151-176`), shows the header and its rule and blank lines. Reproduced in this stage with the base binary in tmux 120x30, both with and without `--selectable`. The existing tmux tests wait only for the header text `name` (`tests/cli/tui_tmux_test.go:397-401`, `:425-427`), so they pass on the bug.

## Decisions

### D1. The drawn table gets a width

`newTableModelWithStyles` sets the table's width when it builds it: `opts.Width` when set, otherwise the natural width of the columns (the sum of each column's width plus the horizontal frame of the cell style, which is what one rendered row measures). The standalone model handles `tea.WindowSizeMsg`: when no width was configured, it sets the table width to the smaller of the natural width and the terminal width, so a table wider than the terminal is cut at the terminal edge instead of wrapping (spec "A drawn table shows its data rows"). "No width configured" means `m.width == 0`, the model field that `opts.Width` and `SetSize` set (`table.go:138-147`): the handler reads it, never writes it, so a `WindowSizeMsg` that reaches an overlay model after `SetSize` leaves `SetSize`'s width in place, and `SetSize` keeps overriding both for the overlay whatever the order of the two. The selected-row styles stay. Alternative: call `SetWidth` from `Table()` only. Rejected: `NewTableModel` and `TableBuilder.Model()` would keep building a table that draws no rows.

Tests: a unit test that `View()` of a model from `NewTableModel` with two rows contains both rows' cells (fails on the base: the view holds only the header and blank lines), and a tmux test (`TestTUI_Table`, new subtests for display and `--selectable`) that waits for `Alice` and `Bob` on separate lines before any key, then for the selectable one sends Down and Enter and checks the printed row. The tmux test is written first and seen failing on the base binary (brief: reproduce first).

### D2. Format and separator characters become spaces

`tableTextCells` maps a rune to a space when `unicode.IsControl(r) || unicode.Is(unicode.Cf, r) || r == '\u2028' || r == '\u2029'` (U+2028 is Zl and U+2029 is Zp; both categories hold only that one character). The code writes the two runes as `\u` escapes, never as literal characters, which read as plain spaces. Invalid UTF-8 keeps becoming U+FFFD through `strings.Map`; the godoc of `WriteTableText`, the spec, and the table docs (en and pt-BR) now say so. Trade-off, accepted by decision 125.4: Cf includes U+200D ZERO WIDTH JOINER and U+00AD SOFT HYPHEN, so a ZWJ emoji sequence is printed as its parts separated by spaces, and a soft hyphen as a space. Alternative: drop the characters instead of a space. Rejected: the brief says "as control characters already are", and a space keeps the replaced position visible.

The rename `errTUISpinNotRunMsg` -> `tuiSpinNotRunErrMsg` touches `cmd/invowk/tui_spin.go` only. The new testscript case goes into `tests/cli/testdata/tui_no_terminal.txtar` (it already runs table without a terminal and needs no mirror): a `rows.csv` with `Alice,"line1` / `line2"` and the expected two lines, plus a `--file` case whose cell holds `a`, U+202E, `b`, U+200B, `c`, U+2028 and `d` (spec "Format and separator characters in a cell"). A txtar file cannot carry an invalid UTF-8 byte portably, so the CLI scenario "Invalid UTF-8 in a cell" is covered in `cmd/invowk/cmd_tui_table_test.go`: the `tui table` command runs in process with a non-terminal stdout and stdin `name` / `a\xffb`, and the test compares stdout with `a�b`.

### D3. The Created check comes first in TransitionToStarting

`TransitionToStarting` takes `stateMu` first and changes the state only by one compare-and-swap from Created, whichever branch the caller's context selects:
- context already cancelled: `CompareAndSwap(Created, Failed)`. When it wins, the same locked bookkeeping as `TransitionToFailed` follows (record `lastErr`, `sendErrorLocked`, `closeErrChannelLocked`) and the call returns the wrapped context error; nothing is cancelled, since no server context exists yet. When it loses, nothing changes and the call returns `cannot start server in state <state>`, never `nil`.
- otherwise: the existing `CompareAndSwap(Created, Starting)` and context store in the same critical section (F1); a lost CAS returns the same error as today.

The CAS's compare is the state check, so the check precedes every effect of the context check, and a lock-free `TransitionToStopping` that moves Created -> Stopped concurrently (`base.go:165-169`) simply makes the CAS lose: the terminal state is never overwritten (F2) and the caller gets an error. The cancelled branch does not reuse `TransitionToFailed` or `casToTerminalLocked`: their CAS loop moves any non-terminal state to Failed, and a lost CAS there returns the recorded `lastErr`, which is `nil` after Created -> Stopped. The two outcomes for a Created server are unchanged, so every existing test of a first `Start` keeps passing.

What follows from it:
- `sshserver.Start` keeps its `State().IsTerminal()` check after `TransitionToStarting` (`server_lifecycle.go:101-106`) as cheap defence; its comment no longer says the base returns `nil` there. The "server started at most once" sentences go from the `Stop` godoc, the main spec (delta "Stop during Start leaves nothing running") and the server skill; the skill's Start caveat becomes "returns an error in any state but Created".
- `tuiserver.Start` needs no code change, because `TransitionToStarting` now returns an error in every case where it did not move Created -> Starting, so `bindAll` never runs after a cancelled `Start` (`internal/tuiserver/server.go:138-153` has no terminal check of its own). It gets the same double-Start tests, plus a cancelled `Start` on a server that `Stop` moved Created -> Stopped: the error is non-nil and no listener is bound. That test fails on the base, where `TransitionToStarting` returns the recorded `nil` and `Start` goes on to bind.
- The two tests that expect Failed after a first `Start` with a cancelled context (`internal/sshserver/server_test.go:388-405`, `internal/tuiserver/server_test.go:190-208`) stay as they are.

Formal plan (the `formal-verification` skill's procedure). `Serverbase.tla` gets a constant `FixStartGuard`. With it TRUE, the cancelled branch of `StartBegin` takes the lock in one step and, in a later step while it holds the lock, compares and swaps: Created -> Failed (then the Failed bookkeeping steps under the same lock), or, when the state is no longer Created, no change, then unlock and end. Because the Go code changes the state by a single atomic CAS, that CAS is one model step; the lock step before it lets a lock-free `Stop` move Created -> Stopped in between, so TLC explores the lost CAS. A history variable records whether a cancelled `Start` ever changed a state other than Created, and a new property `CancelledStartChangesOnlyCreated` says it never did. New manifest commands: `cancelledStartGuardFixed` (pass) and `mutantPreFixCancelledStartFailsAny` (`FixStartGuard = FALSE`, counterexample, `mutant_of` the former); the base constants set `FixStartGuard = TRUE`, and the `distinct_states` of every Serverbase command are re-measured. `base_formal_test.go`'s `sequentialStep` makes `opStartCancelled` fail only from Created, and the trace harness (`base_trace_test.go`, `ServerbaseTrace.tla`) is checked for the same step. The correspondence row "Starting steps" keeps its binding; its abstraction gains "the state check precedes the context check". This is a decision-120 follow-up, not a model finding: no F-number is assigned, so the change cannot collide with the numbering of the parallel W1a run. The pre-fix code stays only as the mutant configuration.

### D4. Stop closes every connection and uses the library's Close

The brief asks whether closing the connections lets `Stop` avoid waiting on the library's `connWg`. Closing them is not enough by itself: `Shutdown` still waits on `connWg`, and a connection whose handshake finishes after `Stop` closed the known connections calls `connWg.Add` while `Shutdown` waits (`server.go:448-449`, `:605-617`, `:274-279`). But once `Stop` closes every connection, the graceful `Shutdown` has nothing left to be graceful about, and the library's `Close` (`server.go:250-261`: closes the done channel, the listeners and its tracked connections, and waits for nothing) does the rest. No `Wait` on `connWg` runs anywhere, so gliderlabs/ssh#117 no longer applies. The decision is therefore to use it:

1. The `ConnCallback` wrapper registers every accepted connection in a server-owned set and counts it in a server-owned `sync.WaitGroup` (`Add(1)`), both under one mutex. Once a teardown has begun, the callback refuses (returns `nil`, which makes the library close the raw connection, `server.go:401-406`). Every `Add` therefore happens, under that mutex, before the teardown marks the set closed, and so before its `Wait`.
2. The `Done` for that connection runs in a `ConnectionCloseCallback` that `trackConnections` installs. The library defers it in `handleConn` exactly once for every connection whose `ConnCallback` returned non-nil, and only for those: a refused connection returns before the defer is registered (`server.go:401-406` vs `:419-425`). It runs when the connection goroutine ends, after the library's own `trackConn(false)` (deferred later, so run earlier) and before the deferred `conn.Close` (`server.go:419-425`, `:448-449`). `Done` is not tied to `tokenConn.Close`: teardown itself closes every connection, so a `Done` in `Close` would let teardown satisfy its own `Wait`, and the `Wait` would order nothing.
3. `tokenConn.Close` removes the connection from the set and from its token's index (`closeOnce`, `server_conns.go:45-51`) and marks it closed under `tokenMu`. `admitConn` refuses a connection already marked closed, in the same `tokenMu` section that binds it, so a login released after teardown closed its connection cannot put a closed, already-forgotten `tokenConn` back into `s.conns`. Revocation keeps closing the token's connections (F7).
4. `teardown`, after the listener close and the gate wait it has today (#213's ordering stays), marks the set closed, closes every connection in it, calls the library's `Close` instead of `Shutdown`, and waits for the connection WaitGroup, bounded by the rest of `ShutdownTimeout` (an expiry returns an error wrapping `context.DeadlineExceeded`, as today). The `beforeShutdown` hook runs before `Close`.

So `Stop` returning `nil` means every connection goroutine (`handleConn`) has passed the point where the library's `connWg.Done` runs today, which is the ordering the base `Shutdown` gave (`server.go:274-279`) when it did not time out. It does not cover goroutines the library starts per channel or per request (session handlers, `handleRequests`): those end when the closed connection makes their reads fail, and neither the base nor this design waits for them. A closed connection cannot keep `Stop` waiting, since its goroutine ends once its reads fail; only a goroutine blocked in invowk's own code, such as a password check that does not return, can, and then the bound applies. The serve gate is kept: with `Close` the listener-WaitGroup race of charmbracelet/ssh#61 cannot occur either, but the gate is what the main spec and #213's tests rely on, and removing it is a separate decision once upstream fixes #61 (decision 120).

Alternative: close the token-indexed connections, then call `Shutdown`. Rejected: it fixes F11 for authenticated connections but keeps #117 and leaves connections in their handshake to the timeout.

Tests: invert the F11 replay as `TestHostCallbackToken_StopClosesAuthenticatedConnection` (Stop returns `nil` well inside `ShutdownTimeout`, the client sees its connection closed, `NewSession` fails); a deterministic Stop-during-handshake test with a new test hook in the password handler (the login is held; `Stop` runs in its own goroutine; once teardown has closed the connections, which a test hook after that step reports, the test releases the hold while `Stop` waits; `Stop` returns `nil` well inside `ShutdownTimeout`, the login fails and `s.conns` holds nothing; `-race`), and a variant that never releases the hold until `Stop` returned, where `Stop` returns an error wrapping `context.DeadlineExceeded` at `ShutdownTimeout`; revocation racing `Stop`; #213's lifecycle tests unchanged and green. The inverted replay fails on the base (the base returns `DeadlineExceeded`); the handshake test is the regression test for #117 under `-race` and may pass on the base when the race does not trigger, which the result says.

Formal plan: `HostCallbackToken` base constants set `StopClosesSessions = "TRUE"`; `findingF11StopKeepsSessions` becomes `mutantPreFixF11StopKeepsSessions` (`StopClosesSessions = "FALSE"`, counterexample, `mutant_of = "noSessionAfterStopFixed"`, no `finding` key); calibration text ("F11 (open)" becomes a dated "F11 fixed" entry, as F7's is) and `distinct_states` updated, and the manifest comment `# Finding F11 (open)` becomes `# Fixed finding F11: Stop closes every connection`; the correspondence row "Stop" binds the inverted test and its abstraction drops "(F11)"; the model comment at `HostCallbackToken.tla:18-21` is updated.

The trace harness `TestHostCallbackToken_TraceHarness` (`internal/sshserver/token_trace_test.go`) follows the fix: `stop()` requires `Stop` to return `nil` and waits with `tokenTraceCloseBound` instead of the fixed `tokenTraceStopSettle`, which goes with its F11 comment (`:23-26`); the sequence comment "Stop with both executions active (F11)" (`:112`) and the `stop()` godoc (`:240-241`) drop F11. Since the base configuration no longer accepts a connection open after `Stop`, the rule "a behaviour accepted because of an open finding is never a targeted mutation" (`formal/README.md:243`) no longer excludes it: `tokenTraceMutations` gains "a connection stays open after Stop" (an edit of the accepted `S1 S2 A1 A2 P` trace's last record to `e1_session = TRUE`, commented `NoSessionAfterStop: the pre-fix F11 behaviour`), and its godoc (`:317`) drops the F11 exclusion. The main spec `protocol-trace-validation` changes with it (delta in this change; its Purpose, which names "open findings F11 and F12", is edited in the main spec directly, as for host-callback).

`formal/README.md`: row F11 reads "Fixed: Stop closes every connection; the pre-fix code is kept as `HostCallbackToken.mutantPreFixF11StopKeepsSessions`", status `(shipped)`, as F7's row does; the model table's "Go replay of F11" (`:174`) becomes "Go regression test of F11"; and `:243` reads "open finding (F12)". The main spec's Purpose, which calls #117 a known residual and the graceful shutdown a feature, is rewritten in the same commit. `.claude/issues/cst-adoption-gaps.md:525` names the old replay test; the brief forbids editing that file, so the result lists it as a tracker fact.

### D7. One copy, checked and hashed

The flow stays: resolve (check) -> cache key (hash) -> on a miss, build. `calculateCacheKey` returns the binary's hash along with the key, and `Provision` passes it to `buildProvisionedImage`. `prepareBuildContext` copies the binary once: it opens the configured path (following a symlink, as the check and the hash already do), requires the opened file to be regular (`File.Stat`), and streams it into `<build context>/invowk` while hashing the bytes it writes. It then runs `checkLinuxBinary` on the copy with the architecture the resolution used, and compares the copy's hash with the key's. What a rejection or a different hash does depends on where the binary came from, as it does for any unusable binary (spec "The installed binary is the one that was checked"):
- an explicit `binary_path`: the build fails with an error that names the configured path and says the binary changed during provisioning, and no image is tagged (main spec "An unusable explicit binary_path fails the command");
- the default binary (the running invowk executable): it is skipped with the warning of the main requirement "An unusable default binary is skipped with a warning", whose reason says the executable changed during provisioning, and `strict` does not turn this into an error. `prepareBuildContext` returns a sentinel error for this case; `Provision` then switches to the skipped resolution (no path, that warning), recomputes the cache key and tag for an image without the binary (so "Cached provisioned images reflect whether the binary is installed" holds), reuses that image when it is cached, and otherwise builds it. A realistic trigger is a package manager that upgrades invowk in place while it provisions: the command runs, and the next run provisions the new binary. The `Dockerfile` copies `invowk` from the build context as today. The cache-hit path and `GetProvisionedImageTag` do no copy, so their I/O and the cache key are unchanged (#214's key and drift tests stay green).

So the resolution must carry the architecture it checked against: `binaryResolution` gains it. The copy no longer goes through `CopyFile`; a symlinked `binary_path` is therefore installed instead of failing the build at `COPY` (Context). This is the one behaviour change outside the race, and it follows from the copy this change adds.

Alternatives: one descriptor shared by check, hash and copy. Rejected: it defeats a rename but not an in-place write between the steps. Snapshot the binary to a temp file before the check. Rejected: it copies the whole binary on every run, cache hits included.

Tests (each replacement test fails on the base): two seams, unexported hooks on `LayerProvisioner` like `imageArchitecture`: one after the resolution's check and before the cache key, one after the cache key and before the build-context copy. Each replaces the file at `binary_path` (or at the default binary's path) with a macOS Mach-O stub, a script, or a different Linux ELF; the fake engine records the build context. For an explicit `binary_path` the run fails with the named error and no build is recorded, where the base builds with the replaced bytes; for the default binary the run builds the binary-less image with the changed-during-provisioning warning, where the base installs the replaced bytes. Plus: an unchanged binary builds the same tag and build context as before, and a cached image for an unchanged binary is reused with no build context prepared (the fake engine records no build and the copy hook never runs).

`internal/provision` is formal-bound, but its only bound function is `CopyDir` (`formal/alloy/ModulePathContainment.als:40`), which this change does not touch; the fix stage still runs `formal_mutation.py symbols` on the changed functions.

### D8. A non-blocking duplicate of the master (investigate, then decide)

Proposed mechanism, without changing `xpty`: after `startInteractivePty` (Unix), duplicate the master descriptor inside `UnixPty.Control` (a raw-descriptor callback that, unlike `Fd()`, does not switch the file to blocking mode), set the duplicate non-blocking, and wrap it with `os.NewFile`, which registers a non-blocking descriptor with the runtime poller. A small adapter type satisfies `tui.InteractiveTerminal`: `Read` and `Write` use the duplicate, `Resize` delegates to the `UnixPty`, and `Close` closes the duplicate first (the poller wakes a blocked `Read` or `Write` with `os.ErrClosed`, and the descriptor closes at once) and then the `UnixPty`. O_NONBLOCK belongs to the open file description, so the original master becomes non-blocking too; the original `*os.File` is then used only for ioctls (`Control`) and its final close, never for `Read` or `Write`, which would see `EAGAIN`. Invariant: nothing calls `Fd()` on the original master (or on the duplicate) after the switch. Every `os.File.Fd()` call on a non-blocking file clears O_NONBLOCK (`os/file_unix.go:80-82`, `pfd.SetBlocking`), and since the flag belongs to the shared open file description, the duplicate would turn blocking again while the poller still treats it as non-blocking, which brings the leak back with no error. So the adapter exposes no `Fd()` and no `*os.File`; its `Resize` goes through xpty's `Resize`, which uses `Control` (`xpty@v0.1.4/pty_unix.go:12-45`), never through creack/pty's `Setsize`/`GetsizeFull` or `UnixPty.Fd()` (`pty.go:53-55`). The probe test includes a `Resize` before the hang-up so a regression of this invariant fails it. Both the writer and the reader are covered: a command that reads nothing and writes nothing pins the master through a blocked `Read` just as through a blocked `Write`.

Decision rule (brief item 8). Task group 8 starts with a probe test (`interactive_session_unix_test.go`): a command that never reads its input, enough input to fill it, session ended, then the command must receive SIGHUP within a bound while the test process runs on. If the probe passes with the mechanism on Linux and, in CI, on macOS (where kqueue must accept the pty master; if `os.NewFile` cannot register it, the file stays blocking and nothing changes), the item ships with that test. If it needs changes inside `xpty` or creack/pty (for example a master that cannot be duplicated or polled), the fix stage reverts the item's code, removes the delta `specs/interactive-mode-terminal/spec.md` and the unticked tasks of group 8 with a note, and records the finding in the result. That outcome changes no other item.

## Risks / Trade-offs

- [The drawn table's natural width can exceed a narrow terminal] -> D1 clamps it to the terminal width on `WindowSizeMsg`; rows are cut, not wrapped.
- [Cf replacement splits ZWJ emoji and soft hyphens in plain-text output] -> accepted by decision 125.4; documented.
- [`Stop` now ends SSH sessions of executions still running] -> that is F11's fix; production calls `Stop` after executions end (`formal/README.md:265`), so normal runs see no difference.
- [Replacing `Shutdown` with `Close` drops the library's own connection wait] -> the server-owned WaitGroup, released in `ConnectionCloseCallback` when each connection goroutine ends, gives the same ordering point (D4), and the handshake test runs under `-race`.
- [A password check that never returns keeps `Stop` waiting] -> bounded by `ShutdownTimeout`, as the base `Shutdown` was; production's password check does not block.
- [The ConnCallback refusal makes the library close a raw connection a client already opened] -> only after `Stop` began, when the listener is already closed; the client sees a reset, as with a closed port.
- [acp-go-sdk 0.20 is one week old] -> no production caller; tests with fake peers; pinned exactly; Dependabot keeps the group update visible.
- [A default binary replaced mid-run is skipped, so that run's container has no invowk binary] -> the same outcome and warning as any unusable default binary (main spec); the next run provisions the new binary.
- [The provision copy now follows a symlinked `binary_path`] -> consistent with the check and hash, which already follow it; the result lists it as a behaviour change.
- [The non-blocking master behaves differently on macOS] -> D8's decision rule; CI's macOS job runs the probe.
- [Formal ledger conflicts with W1a] -> W1a merges first; mechanical rebase and a fresh targeted refresh (D9).
