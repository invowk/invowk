## Goals / Non-Goals

**Goals:**
- An operation that acts on its last component acts on that entry (link, junction or file), on every platform and under both access modes.
- Under `restricted` access, such an operation is allowed exactly when the entry's own path (the parent resolved physically, plus the final name) is inside an allowed root.
- Every operation that follows its last component keeps today's path and today's decision; `cd`'s access check and the `-r`, `-w` and `-x` tests run on the validated path (D3, "The access handler").
- Under a validating context, the operands of a validated u-root built-in are classified the way that built-in's own parser classifies them, and each operand so found is validated, except `cat`'s lone `-` (standard input) and the operands of `tar` with only `-t`/`-list` (which `tar` does not read); `tar`'s archive path and the output path `gzip` derives from each operand are validated too; option values that are not paths reach the built-in unchanged.

**Non-Goals:**
- Per-operation rules for `ls`, `find`, `tar`, `cp` and `touch` on a link (they keep full resolution, as the brief directs), and the `mv` destination (decided: full resolution; Risks).
- The race between the check and the operation, which stays as recorded in the archived design.
- F15, Windows alternate data streams (`j:s`), and the lexical cleaning of `..` in a request before the walk (`absoluteVirtualPath`, `virtual_policy.go:471-495`), which this change keeps.
- The follow-ups of Open questions.

## Decisions

### D1. The no-follow form

For a request `p` and working directory `cwd`:

1. If the request as written ends in a path separator, or its last element is `.` or `..`, use full resolution (`resolve`) and go to the directory check below. This is read on the raw operand, before anchor expansion and cleaning, because both drop a trailing separator. Only the built-in operands (`rm`, the `mv` sources, `ln`'s link name) reach the resolver raw: the stat handler gets a path mvdan has already made absolute and cleaned (`MVDAN/interp/builtin.go:1133-1143`, `absPath`, called by `lstat` in `MVDAN/interp/runner.go`), so for `-L`/`-h` this step never applies (Risks).
2. Expand anchors and declared names (`r.expand`), then make the path absolute and clean it (`absoluteVirtualPath`).
3. Split it into the parent (`filepath.Dir`) and the final name (`filepath.Base`). If the parent equals the path (a volume root), use full resolution.
4. Resolve the parent with `normalizeVirtualPathForAccess(parent, "", access)`: the strict walk under `restricted` access, with the `full` access fallback of the archived D2 otherwise. Its error is the request's error.
5. Return the resolved parent joined with the final name. The final name is not read.

The validator's no-follow entry (`validateNoFollow`) runs this and then the same allowed-root check as `validate` (`pathWithin` on the result, skipped under `full` access), with the same `virtual path denied: <path>` error naming the result. Both, with the directory check below, go in a new file, `internal/runtime/virtual_path_nofollow.go`: `virtual_policy.go` is already at 895 lines, and every Go file stays under 1000 (checklist step 6). The stat handler stays in `virtual_policy.go` and only gains the call to `validateNoFollow`.

- **The directory check (step 1 only).** After the allowed-root check passes, `validateNoFollow` calls `os.Stat` on the fully resolved path as `resolve` returned it, with no trailing separator. When that `Stat` succeeds and reports no directory, the request is refused: the error wraps `syscall.ENOTDIR` and names that resolved path (the form "Checked and reported virtual paths are the resolved path" already lists). Otherwise (missing, a directory, any other error) the separator the request had, if any, is put back on the resolved path, which is returned, and the operation reports what it finds.
  - The check never stats the separator-suffixed path. On Linux `Stat("target.txt/")` fails with `ENOTDIR`, which an "any `Stat` error passes" rule would let through, and the error a suffixed `Stat` gives differs on Windows and macOS. A plain `Stat` of the separator-free resolved path reports the entry's kind on every platform. The resolved path holds no link, so `Stat` and `Lstat` agree on it.
  - The check runs after the containment check, so a denied path is never examined.
  - It is needed because a kept separator alone is not enough: `os.Remove("t.txt/")` fails with "not a directory", but `os.RemoveAll` strips trailing separators before its `unlinkat` fallback (`splitPath`, Go 1.27 `src/os/removeall_at.go`), so `rm -r live/` with `live` a link to `target.txt` would otherwise delete `target.txt`. u-root `rm -f` ignores every `*os.PathError` (`UROOT/pkg/core/rm/rm.go:145-153`); the refusal comes from the registry before `rm` runs, so `-f` does not hide it.
- **Outcomes of the trailing-separator rule** (maintainer decision 83: full resolution plus the not-a-directory refusal), with `live` a link to the file `target.txt` and `dirlink` a link to the directory `tdir`: `rm live/`, `rm -r live/`, `rm -rf live/`, `rm -f live/`, `rm -r live/.`, `mv live/ x` and `ln -sf t live/` fail with "not a directory" and change nothing (a host shell refuses them too, with ENOTDIR). `rm -r dirlink/` removes `tdir` and everything in it and keeps `dirlink`, which then dangles: the operand names the directory, and u-root's `RemoveAll` removes the directory itself where GNU `rm` empties it and then fails on `dirlink/`. `rm dirlink/` (no `-r`) acts like `rm` of `tdir`: it fails unless `tdir` is empty. `mv dirlink/ x` moves `tdir`.

- **Why containment on the entry's own path is safe.** The parent holds no link (the walk's invariant), so the entry named by the result lies in the parent directory, inside the allowed root that contains the result. `unlink`, `rename` of a source, `lstat` and `symlink` creation act on that directory entry and do not follow it, so nothing outside the root is read or changed. `os.RemoveAll` removes a link entry with its first `Remove` and never descends into its target. On Windows, `Remove` of a junction removes the reparse point (`RemoveDirectory`), and `Lstat` reports a junction as irregular, not a directory, so `RemoveAll` does not recurse into it either; the inverted Windows test checks this on windows-latest.
- **A parent that crosses an escaping link is denied**, because the parent walk is the strict walk and the result then lies outside every root.
- **A final name that cannot be resolved is not refused.** Because the final name is not read, `rm cyclelink` (a link in a cycle) and `rm` of a reparse point whose target cannot be read remove the entry under `restricted` access, where the follow form refuses them. The parent is still refused when it cannot be resolved. The delta spec modifies "Unresolvable virtual paths are refused under restricted access" to say so.
- **A final name equal to an allowed root's own path** (for example `rm -r @work`) is checked like any other result: `pathWithin` accepts a root itself, as today for a root that is not a link. For a root reached through a link (macOS `/tmp`), the no-follow form of `/tmp` is `/tmp`, which is not inside `/private/tmp`, so `rm -r /tmp` is denied under `restricted` access, where full resolution used to accept it and remove `/private/tmp`'s contents. A delta scenario and the docs (task 4.7) state this narrowing.
- **A declared name** expands to its resolved path (`r.paths`, archived D2), so `rm NAME` acts on the last component of that resolved path, not on a link the declaration was written through.
- Rejected: **resolving the parent lexically** (`filepath.Dir` without the walk). It would accept `esc/name` with `esc` a link out of the root.
- Rejected: **race-free removal with directory handles** (`unlinkat` on an opened parent). It would need invowk's own `rm` and `mv` in place of the u-root wrappers, and the race is a non-goal.

### D2. A second hook next to `ValidatePath`

- `uroot.HandlerContext` gets `ValidateNoFollowPath func(cwd, path string) (string, error)` and a method `ResolveNoFollowPath(path string) (string, error)`:
  - with `ValidateNoFollowPath` set, it calls it with `h.Dir`;
  - with only `ValidatePath` set, it returns an error (`errNoFollowValidatorMissing`, naming the path): a validating context that cannot express the no-follow form must not fall back to the following one, which is the data-loss behaviour;
  - with neither set, it joins a relative path to `h.Dir`, as `ResolvePath` does.
- `pathValidatingHandlerContext` (`handler.go:81-84`) reports a validating context when either hook is set, so a context that sets only `ValidateNoFollowPath` still goes through the collector. In such a context `ResolvePath` returns an error (`errFollowValidatorMissing`, naming the path) instead of joining the path unvalidated: the mirror of the rule above.
- virtual-sh (`sh.go:546-548`) and virtual-lua (`lua.go:669-679`) set both hooks from the same validator.
- Rejected: **one hook with a mode argument** (`ValidatePath(cwd, path, follow bool)`). It is type-safe, but it changes every caller (`tee`, `mktemp`, `realpath`, `files.go`, `tar`, the registry), and the brief asks for a second hook.

### D3. Which operands use it (supersedes the archived D3 for these operations)

The archived D3 said the validated path is the resolved path for every operation, and that an operation on a link or junction acts on its target. That stays true only for operations that follow their last component. For the operations below, the validated path is the no-follow form (D1):

| Operation | Operands with the no-follow form | Operands with full resolution |
|---|---|---|
| `rm` (also `-r`, `-R`, `-f`) | every operand | none |
| `mv` | every operand except the last, when there are two or more | the last (the destination) |
| `ln` | the link name, for the `-f` removal and the creation | a hard link's target; a symbolic link's target is stored as written, unvalidated, as today |
| `virtual-sh` stat handler | the path when `followSymlinks` is false (`-L`, `-h`) | the path when `followSymlinks` is true (`cd`, every other file test) |
| `virtual-sh` access handler (`cd`'s access check, `-r`, `-w`, `-x`) | none | the path ("The access handler" below) |

- The operands of `rm` and `mv` are the ones D4's collector finds; each is resolved with the hook its position selects in the table. The mv destination is the last operand the collector returns, so `mv a b -x` treats `-x` as the destination and `a`, `b` as sources; `rm a -x` removes `-x` with the no-follow form.
- A single `mv` operand is treated as a source; u-root then fails with "insufficient arguments" (`UROOT/pkg/core/mv/mv.go:131-134`).
- Forms that change, against the archived D3 table: rows 2 and 4 (a dangling link under `restricted` access; a Windows junction under both modes) still give the target path, and `virtual path denied` messages still name it, for operations that follow the last component. For the operations in the table above, a link, junction or dangling link as the last component is kept, and the message names the no-follow path (the resolved parent joined with the final name).
- `INVOWK_PATH_*`, `invowk.path` and the Lua `io` functions do not change.
- **The access handler.** On Windows and every other non-Unix platform, mvdan's default access check calls the runner's stat handler with `followSymlinks=false` (Context), so once that call takes the no-follow form, `cd` into a directory link or junction and `-r`/`-w`/`-x` on a link would test the link's own entry. Both runner setups (`sh.go:395-402`, `:450-458`) therefore register `interp.AccessHandler(pathValidator.accessHandler(interp.DefaultAccessHandler()))` on every platform. Its code goes in a new file, `internal/runtime/virtual_sh_access.go`, next to `virtual_sh_cd.go`.
  - `accessHandler(next)` returns a handler that runs `validate(hc.Dir, path)`: full resolution, following the last component, with the allowed-root check under `restricted` access and the `full` access fallback otherwise. On an error it returns `&os.PathError{Op: "access", Path: path, Err: err}` and does not call `next`, so the `-r`/`-w`/`-x` test is false and `cd` fails (with the denial line of D5 before it under `restricted` access). Otherwise it calls `next` with the same context and the resolved path.
  - On Unix `next` is access(2) on the resolved path. On the other platforms it is the stat handler with `followSymlinks=false` on the resolved path: that path holds no link, so its no-follow form (D1) is the path itself and the stat handler repeats the same decision, and the permission bits read are the target's.
  - Under `restricted` access a path outside every allowed root never reaches `next`, so no host access check runs on it; the `-r`, `-w` and `-x` tests are validated like the other file tests (hardening, both platforms).
  - `-L` and `-h` keep the stat handler's no-follow form (table above); the access handler does not change them.
  - The delegate is a parameter so that the tests can wrap a recording delegate and assert which paths reached it (D8).
  - Rejected: **following the link inside the stat handler when the caller is the access emulation.** The stat handler cannot tell that call from `-L`; the access handler can.

### D4. Operands of every validated built-in are found as its parser finds them

Under a validating context, `validateUrootCommandPathArgs` replaces `validateNonOptionPathArgs`, `validateShasumPathArgs`, `validateFindPathArgs` and the tar scan with one collector, `urootCommandOperands`, driven by a per-command table:

| Command | Preprocessing (as upstream) | Operands and their resolution | Option values that are paths |
|---|---|---|---|
| `base64`, `cp`, `ls`, `mkdir`, `shasum`, `touch` | `ArgsToGoArgs` | every operand, full resolution; a lone `-` is a file name | none |
| `gzip` | none | every operand, full resolution; a lone `-` is a file name; plus the output path derived from each operand ("gzip's output path" below) | none; a `-S` value that holds a path separator is refused |
| `cat` | `ArgsToGoArgs` | every operand, full resolution; a lone `-` is standard input and stays as written | none |
| `rm`, `mv` | `ArgsToGoArgs` | every operand, a lone `-` included, with the hook D3 selects | none |
| `find` | upstream's `reorderArgs`, copied | every operand, full resolution | none |
| `tar` | `ArgsToGoArgs` | `-x`/`-extract`: the extraction directory; otherwise every operand (with no mode or more than one, the built-in then refuses); full resolution. With only `-t`/`-list`, operands stay as written (upstream reads none) | every `-f`/`-file` value, full resolution |

1. **Preprocess as the built-in does.** One exception, for the `ArgsToGoArgs` commands: a raw argument that is exactly `--` and comes before the first argument that does not start with `-` ends the options, as on a host shell. The arguments after it are operands, as written, and that `--` is not handed on. u-root itself would read it as an operand `-` (`ArgsToGoArgs` turns `--` into `-`), which names a file for every command but `cat`. `gzip`'s parser already ends the options at `--`, and `find` keeps upstream's reading.
2. **Parse with Go's `flag` package**, with a `flag.FlagSet` built from the command's declared options (step 5): a `flag.Bool` for each option without a value and a `flag.String` for each option with one, output discarded. The operands are what `FlagSet.Args()` returns. Using `flag` itself, not a reimplementation, makes the classification equal to upstream's for the same option table: options end at the first argument that is not an option, at a lone `-` or after `--`, an option that takes a value consumes the next argument (or its `=value`) whatever it starts with, and `--x` and `-x` are the same option.
3. **Resolve.** Each operand is resolved with the hook its row selects; option values that are not paths (`mkdir -m 755`, `touch -d <time>`, `shasum -a 256`, `gzip -S .z`, `find -name x`) stay as written; `tar`'s `-f`/`-file` values are resolved in place. For `gzip`, the output path of each operand is then checked ("gzip's output path" below).
4. **Rebuild and check.** The built-in receives an argument list that its own preprocessing and parser read as the same options, the same option values (with tar's archive paths resolved) and exactly the resolved operands.
   - The rebuilt list, in the form the parser reads, is the options and their values, then `--`, then the operands, so no operand can be read as an option (a resolved operand is absolute; `cat`'s `-` and a `tar -t` operand are kept as written).
   - For the `ArgsToGoArgs` commands it is then encoded so that `ArgsToGoArgs` gives it back: each argument that starts with `-` and comes before the first one that does not is written as `-` followed by it (`ArgsToGoArgs` maps `--x` back to `-x`, `---` back to `--` and `--` back to `-`), and the rest are written as they are. For `gzip` it is written as it is.
   - `find` gets its options in their written order, followed by its operand, with no `--`: `reorderArgs` moves every argument that starts with `-` to the front and reverses their order, and of repeated options the last one parsed wins.
   - Then the registry reads the rebuilt list again, with only the built-in's own preprocessing (`ArgsToGoArgs`, `find`'s `reorderArgs`, or none for `gzip`) and a fresh `flag.FlagSet` from the same table, and refuses the command (an internal error that names the command) unless the result equals the options and resolved operands it built. The re-read does not apply step 1's `--` rule: the encoded list is no longer what a user wrote, and that rule would misread it (`cat -- -` is rebuilt as `--`, `-` and encoded as `---`, `--`; `ArgsToGoArgs` and `flag` read that back as the operand `-`, standard input, while step 1 would take its second element for the end of the options and find no operand). The check makes a rebuild defect fail closed.
5. **Option tables come from `FlagInfo`.** Each validated wrapper's `SupportedFlags()` lists every option its upstream command defines, by its Go `flag` name (`Name`, plus `ShortName` when it differs), with `TakesValue` true exactly for the upstream options that take a value. The current lists are corrected to match UROOT (Context): `touch` declares `-a`, `-c`, `-d` (value) and `-m`, and drops `-t` and `-r`, which upstream does not define (`touch -r ref f` fails in the built-in's parser, so there is no reference file to validate); `mv` declares `-n` and `-u` and drops `-f`; `shasum` adds `-algorithm`; `gzip`, `cp`, `ls`, `rm`, `mkdir`, `find` and `tar` add the options they lack; `ls` declares `-p` only on Windows and Plan 9, as upstream does.
6. **A parse error stops the command before it runs.** When Go's parser fails (an option the table does not declare, a value missing, a malformed option), the registry hands the built-in only the option that failed, with its value when it has one, so the built-in reports its own error and usage, and no other argument reaches it. `-h` and `-help` are covered by this where the command does not declare them, and the built-in prints its usage. `ls` (`-h`, human-readable sizes) and `gzip` (`-h`, help) declare `-h`, so for them it is an ordinary option of the table.
7. **gzip's output path.** After its operands are resolved, the registry reads `-c`, `-t`, `-d` and `-S` (default `.gz`, upstream's) from its own parse of `gzip`'s arguments.
   - A `-S` value that contains a path separator (`/`, and `\` on Windows) is refused before `gzip` runs, with an error that names `gzip -S` and the value. A suffix names the end of a file name; with a separator, the derived path would have components that the validator checks after cleaning the text (Risks, "Requests are cleaned before the walk") and `os.Create` walks as written, so the checked path and the created path could differ. The rule holds under both access modes: the registry does not know the mode, which only the hooks apply.
   - Unless `-c` or `-t` is set, the registry derives each operand's output path as upstream does: the resolved operand plus the suffix, or, with `-d`, the resolved operand with the suffix trimmed (with no such suffix it is the operand itself, which `gzip` accepts only with `-f`). It validates that path with the follow hook (`ResolvePath`), because `os.Create` follows its last component, and refuses the command before `gzip` runs when any one is refused. The derived path is not handed on: `gzip` derives it again from the same resolved operand, and the validated result is discarded.
   - The checked path is the path `gzip` creates. The resolved operand holds no link, and a suffix without a separator changes only its final name, or, with `-d` and a suffix equal to the whole final name, leaves the parent directory, which `os.Create` refuses. So the request is the operand's resolved parent joined with one final name, and the validator and `os.Create` both follow that name.
   - Outcomes: `gzip -S .z f` writes `f.z`; `gzip -d -k f.gz` checks `f.gz` and `f`; `gzip -c f` and `gzip -t f.gz` check only the operand; under restricted access `gzip -k .`, run in a working directory that is an allowed root's own path, is refused, because `<root>.gz` lies next to the root, outside it; `gzip -k -S x/y f` is refused under both access modes and changes nothing.

- Outcomes: `cat a -x` and `touch a -x` validate `-x` like any other operand; `rm keep -x` validates `-x` with the no-follow form; `cat -- -x` reads the file `-x`; `rm -- -x` removes `./-x` and nothing else; `cat a -` reads `a` and then standard input; `cp a -` writes the validated file `-`; `mkdir -m 755 d` creates `d` with mode 755, and `touch -d 2024-01-02T03:04:05Z f` sets that time (both are rewritten as paths today); `find -name x dir` validates `dir`; `tar -x -f a.tar dir` validates `dir`; `tar -c -f a.tar src -x` validates `-x`.
- **A leading lone `-` is not an operand.** `ArgsToGoArgs` turns a lone `-` that comes before the first argument that does not start with `-` into nothing, so `cat - a` reads only `a` and `rm - a` removes only `a`, in the built-in and therefore in the collector. A lone `-` after the first operand, or right after a `--` that ends the options, is an operand. `gzip`, which has no `ArgsToGoArgs`, reads a leading lone `-` as its first operand, a file named `-`.
- **A `--` in the option prefix always ends the options**, also right after an option that takes a value: `mkdir -m -- d` fails with "flag needs an argument", where upstream would take `-` as the mode. That is a refusal: the command does not run.
- **Parity tests.**
  - `TestUrootFlagInfoMatchesUpstream` runs each validated upstream command with an option it does not define (`--invowk-flag-probe`), reads the option list that Go's `flag` prints in its usage (`  -name` for a boolean, `  -name type` for an option with a value), and requires it to equal the wrapper's `FlagInfo` names and `TakesValue`. A u-root bump that adds, removes or changes an option, or a value option, fails this test. It runs on every CI platform, which also checks `ls -p`.
  - `TestUrootCommandOperandsMatchFlagParse` runs `Registry.Run` with a recording validator and a recording command over a table of argument lists (dash operands, `--`, lone `-`, values with and without `=`, long and combined options, missing values), and checks three properties independently of the collector's code.
    1. Every operand of the reference reading of the original list reached a hook, except `cat`'s lone `-` and the operands of `tar` with only `-t`/`-list`, which stay as written. The reference reading is the built-in's own preprocessing plus a fresh `flag.FlagSet` from the table; for the `ArgsToGoArgs` commands, when step 1 finds a raw `--`, the reference splits the list there: it parses the arguments before that `--` that way, and the arguments after it are operands as written, so `rm -- -x` has the reference operand `-x`.
    2. The built-in's own preprocessing and a fresh `flag.FlagSet` of the list the command received (no step 1 rule, as in the rebuild check) return the same option values and, as operands, exactly the hook results, with the same two as-written exceptions in their places.
    3. For `gzip` without `-c` or `-t`, the output path derived from each resolved operand reached the follow hook, and a `-S` value with a separator stopped the command before it ran.
    The table is the seed corpus of a fuzz target, `FuzzUrootCommandOperands`, that checks the same three properties.
  - For `find`, `TestUrootFindOperandsMatchUpstream` runs upstream `find` on a small tree for a table of argument lists and checks that the path it walks is the operand the collector found.
- The custom commands keep their own handling: they resolve the operands their own parser returns (Context). `ln`'s link name moves to `ResolveNoFollowPath` (D3).
- Rejected: **keeping the old collectors and adding cases to them.** Their classification would still differ from the parsers' in other cases (a value option, `find`'s reordering, `tar`'s modes); one collector that reads the arguments as each parser does has no such cases.
- Rejected: **a hand-written Go-flag simulator.** The `flag` package is the parser upstream uses; a copy could drift from it.

### D5. The `cd` denial message

A call handler (`interp.CallHandler`) is added to both runner setups (`sh.go:395-402`, `:450-458`); its code goes in a new file, `internal/runtime/virtual_sh_cd.go`, so that neither `sh.go` nor `virtual_policy.go` grows past the file-length limit. For a call whose first argument is `cd` with zero or one further argument, under `restricted` access:

1. It computes the directory as `changeDir` will: `$HOME` with no argument, `$OLDPWD` for `-`, otherwise the argument (`MVDAN/interp/builtin.go:321-338`), read from the handler context's environment.
2. If `dir` is empty (`cd ""`, or `cd` with `$HOME` empty or unset), it does nothing: `absoluteVirtualPath` would refuse it with "path must not be empty", and mvdan already prints `cd: empty directory path` for it (`MVDAN/interp/builtin.go:1112-1115`), so a second line would only repeat it. Otherwise it runs `validate(hc.Dir, dir)`. On an error it writes `cd: <error>` and a newline to the handler context's standard error, for example `cd: virtual path denied: /var/tmp`. For a non-empty directory every `validate` error under `restricted` access is a refusal the stat handler repeats: a denial (`errVirtualPathDenied`) or a path that cannot be resolved (a cycle, too many links, no existing ancestor). Each is worth naming, since mvdan's own line calls all of them "no such file or directory".
3. It returns the arguments unchanged and never returns an error (an error would halt the runner). `cd` then runs, the stat handler refuses the path again, and mvdan prints its own fixed `cd: no such file or directory: "<dir>"` line and sets status 1.

- The check repeats the stat handler's validation, so the message cannot disagree with the decision except across a filesystem change between the two calls; then the stat handler's decision wins.
- A shell function named `cd` also reaches the handler with `cd` as its first argument. For a denied argument it gets the extra line and then runs normally. That is accepted.
- Under `full` access the handler does nothing.
- Rejected: **replacing the call with `builtin false` after printing**, which removes mvdan's line. A trace (`set -x`) then shows a command the script did not run, and a function named `cd` would be skipped. See Open questions.
- Rejected: **writing the denial from the stat handler.** It cannot tell `cd` from `[ -e ]`, and a file test must stay silent.

## Risks / Trade-offs

- **[The `mv` destination keeps full resolution]** (maintainer decision 83) `mv a linkToFile` replaces the link's target file, `mv a stale` (a dangling destination) creates the missing target, and `mv a live/` (`live` a link to a file) replaces `target.txt`, where a host shell replaces the link in the first two cases and refuses the third with ENOTDIR. → A known difference from a host shell: u-root decides "into a directory" with `Lstat` on the destination, so a link to a directory as destination needs the resolved form. Documented with the other link rules (task 4.7).
- **[Removing a root reached through a link is now denied]** `rm -r /tmp` on macOS used to remove `/private/tmp`'s contents; it is now refused under `restricted` access (D1). → A narrowing on a destructive path; a delta scenario and the docs state it.
- **[Behaviour change for scripts that relied on `rm link` deleting the target]** → Release note and docs; the target can be removed by its own path.
- **[A validating context without the second hook fails]** → Both runtimes set both hooks; the refusal is tested, so a third embedder cannot silently get the following form.
- **[Two lines for a denied `cd`]** mvdan's fixed "no such file or directory" line still follows the denial line. → The first line names the cause; follow-up.
- **[Requests are cleaned before the walk]** `rm sub/../x` with `sub` a link acts on `./x`, where a host shell acts on `x` next to `sub`'s target. → Pre-existing for every operation (`virtual_policy.go:475`); not changed here.
- **[`-L` and `-h` cannot see a trailing separator]** mvdan makes the operand absolute and cleans it before the stat handler runs (D1 step 1), so `[ -L live/ ]` and `[ -L live/. ]` test `live` itself and are true for a link, where a host shell follows the link and says false. → Recorded and pinned by a unit test; fixing it would need mvdan to pass the raw operand. The built-in operands do not have this limit.
- **[The trailing-separator rule follows the link]** `rm -r dirlink/` removes the target directory's whole tree (D1). → The operand names the directory, as on a host shell, which empties it; the directory check keeps a link to a file from being deleted through `live/`.
- **[`--` differs from u-root]** The collector ends the options at a raw `--` and does not hand it on, where u-root reads it as an operand `-` (D4 step 1). → Host-shell behaviour; `rm -- -x` removes only `-x`. A `--` right after a value option is refused (D4).
- **[Option tables must follow u-root]** A u-root bump that adds an option would make the registry refuse commands that use it, and one that adds a value option would shift the classification. → `TestUrootFlagInfoMatchesUpstream` fails on any such bump, and a refusal is the failure mode, never an unvalidated operand.
- **[`gzip -S` with a path separator is refused under both access modes]** (D4 step 7) → A suffix ends a file name; the registry does not know the access mode, and one rule keeps the derived path one that the validator checks as `gzip` creates it. Documented with the operand rules (task 4.7).
- **[Usage output under a parse error]** The built-in receives only the option that failed (D4 step 6), so its error and usage are its own, but nothing after that option is echoed. → Accepted.

## Migration Plan

No data migration. Scripts that removed a link's target through the link now remove the link; remove the target by its own path. Scripts that passed `--` to `cat` to read standard input first now read only the named files (write `-` for standard input). Rollback is reverting commits 2 to 4; commit 1 only adds a message and tests.

## Maintainer decisions

From the first brief (2026-11-24, `program-notes/briefs/no-follow-brief.md`; decisions 67, 72-74):

1. Decision 67's default ("the returned path is the resolved path") is reversed for operations that act on the last component: rm operands, mv sources, ln's link name, stat with `followSymlinks=false`, and the Lua equivalents. Every other operation keeps full resolution and its containment decision.
2. No-follow form: absolute path, parent resolved by the strict physical walk, final name joined; containment checked on that path; `.`, `..` or an empty final name keeps full resolution.
3. Per-operand plumbing in the u-root registry with a second ValidatePath-style hook.
4. First commit: the `cd`/file-test CLI regression with its native mirror and a `cd` denial message that names the denial.
5. Invert `TestVirtualPathWindowsRemoveJunctionActsOnTarget`; Windows and macOS evidence by test name.
6. Revise D3 here and the spec requirement at `openspec/specs/virtual-runtime-sandbox/spec.md` ("Checked and reported virtual paths are the resolved path"); docs and a release note calling it a data-loss fix.
7. Say how the no-follow form maps to the model; fold in the formal follow-ups (a)-(d); model, golden, manifest and reach edits belong to the implement stage.
8. Do not touch F15, Windows alternate data streams, or `.claude/issues/cst-adoption-gaps.md`.

From the revision brief (2026-11-24, `program-notes/briefs/no-follow-revise-brief.md`; decision 83):

9. Trailing separator: full resolution plus the not-a-directory refusal, from a `Stat` of the separator-free resolved path (D1).
10. The `mv` destination keeps full resolution, recorded as a known difference from a host shell (Risks).
11. Every validated built-in finds its operands as its parser does (D4), in this change; option values that are not paths are not rewritten; the `find` and `tar` collectors are included.
12. Public text describes D4 as hardening and names no command as still affected (D9).
13. Follow-ups, not this change: listed in Open questions.

From the round-3 brief (2026-11-24, `program-notes/briefs/no-follow-revise3-brief.md`):

14. An access handler on every platform resolves the path with full resolution and the allowed-root check, then delegates to mvdan's default handler (D3, "The access handler"); the `-r`, `-w` and `-x` tests move from Open questions into this change as hardening.
15. `gzip`'s output paths with the `-S` refusal, and `tar`'s extraction directory, are in scope (D4).
16. Other paths a built-in derives from a validated operand are a separate change (Open questions).
17. Pushed text uses hardening wording only (D9 "Public text"); the implement stage squashes this change's unpushed openspec commits (D9 step 0).

None of these changes the specs, the approach or the tasks. Each is a follow-up the maintainer has set aside for a later change (decision 83 and the round-3 brief).
