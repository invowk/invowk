# Design

## Context

Motivation: proposal.md, "Why". Current behaviour, at base 36f85fd6:

- `serve()` calls `s.base.TransitionToRunning()` as its first step (`internal/sshserver/server_lifecycle.go:172`), before it reads `srv` and `listener` (`:175-178`) and before `srv.Serve(listener)` (`:184`). `Start` returns `nil` as soon as `StartedChannel()` closes (`:98-102`), so it returns before upstream `Serve` has run.
- Upstream `Serve` (`charm.land/ssh@v0.4.3/server.go:294-339`) runs `ensureHandlers`, `ensureHostSigner` (`:304`), then `trackListener(l, true)` (`:312`), which resets `doneChan` when no listener or connection is tracked (`:592-596`) and calls `listenerWg.Add(1)` (`:598`), and only then its first `l.Accept()` (`:316`), in the same goroutine.
- Upstream `Shutdown` (`server.go:268-287`) closes the tracked listeners and `doneChan` under `srv.mu`, then waits on `listenerWg` and `connWg` in a new goroutine (`:275-279`). A `Shutdown` that runs before `trackListener` finds nothing to wait for; `Serve` then registers the listener, resets `doneChan` and serves on, and its `Add` races the `Wait` (CI: `server.go:275` against `:312`). This is https://github.com/charmbracelet/ssh/issues/61.
- Upstream also adds to `connWg` in `trackConn` (`server.go:605-617`) when a handshake completes, which can race the same `Shutdown`'s `connWg.Wait()` (https://github.com/gliderlabs/ssh/issues/117). This change leaves that residual alone (proposal.md, "Why").
- `doStop` closes our listener before `Shutdown` (`server_lifecycle.go:141-145`). That is why `Serve` does not serve on in invowk today: its first `Accept` fails on the closed listener and, with `doneChan` reset, returns the `net.ErrClosed` error, which `serve()` ignores (`:188-190`). The race on the WaitGroup remains.
- `Start` publishes `s.listener` and `s.addr` (`:62-65`) and `s.srv` (`:85-87`) in two separate critical sections and calls `AddGoroutine` outside any lock (`:90`, `:94`). `TransitionToStopping` accepts `StateStarting` (`internal/core/serverbase/base.go:174`), so a `Stop` during `Start` runs `doStop` at once. When it runs before `:90`, `doStop` takes nil resources, `WaitForShutdown` (`:158`, `base.go:218-220`) returns on a zero counter, and `Start` then calls `AddGoroutine`: an `Add` racing a `Wait` in our own WaitGroup. When it runs before `:62`, the listener `Start` stores later is never closed and the serve goroutine serves on it with nobody to stop it.
- In that case `TransitionToRunning` fails its CAS (`base.go:124-128`), `startedCh` never closes, and `Start` reads the closed error channel (`:104-106`): it receives `nil`, `TransitionToFailed(nil)` finds a terminal state and returns the recorded `nil` (`base.go:134-140`), so `Start` returns `nil` for a server that is stopped.
- `TransitionToFailed` CASes from any non-terminal state, `Stopping` included (`base.go:271-281`), and returns the recorded error, `nil` when the terminal state was reached without one.
- On a startup timeout or a cancelled `ctx` (`server_lifecycle.go:108-110`), `Start` calls `TransitionToFailed`, which cancels the base context but closes neither the listener nor the upstream server. The serve goroutine keeps serving, and a later `Stop` sees `Failed`, skips `doStop` and blocks in `WaitForShutdown` (`:118-121`). Today the path is almost unreachable, since readiness fires on the first line of `serve()`; once readiness waits for the first `Accept` (D1), it is reachable whenever the serve goroutine is slow to reach `Accept`.
- `TransitionToStarting` with an already-cancelled `ctx` returns `TransitionToFailed(...)` (`base.go:96-100`). On a server already terminal with no recorded failure, that returns the recorded `nil` (`base.go:134-140`) without any transition. A `Stop` on a `Created` server produces exactly that state: `TransitionToStopping` CASes `Created -> Stopped` and returns `false` (`base.go:166-170`), so that `Stop` goes straight to `WaitForShutdown` and runs no teardown. `Start` then goes on to bind a listener (`net.ListenConfig.Listen` binds even with a cancelled `ctx`; the spec reviewer checked this with a probe) and to launch goroutines for a stopped server. When that `Stop` runs concurrently, its `WaitForShutdown` is unordered with `Start`'s `AddGoroutine`, and in one ordering it waits for a serve goroutine blocked in `Accept` on an open listener that nothing will close. The same holds whether the `Stop` came before the `Start` or raced it.
- `TestServerServeFailureTransitionsToFailed` (`internal/sshserver/server_test.go:409-434`) builds a `Server` literal with only `base`, `srv` and `listener` and calls `serve()` directly, without `Start`.
- A `Stop` that loses `TransitionToStopping` (`Stopping`, `Stopped` or `Failed` already set) calls `WaitForShutdown` directly (`server_lifecycle.go:118-121`). While the winning `Stop` runs `doStop` during a `Start` that has not yet called `AddGoroutine`, that `Wait` on a zero counter can race `Start`'s `Add` too. The public `Wait()` (`:275-276`) calls `WaitForShutdown` in the same way.
- The only caller of `Start` outside the package is `HostAccess.Ensure` (`internal/app/commandadapters/host_access.go:44-73`). It calls `Start`, and `HostAccess.Stop` (`:85-95`) calls `Stop`, both under `h.mu`, so they never overlap. On a non-nil result it wraps the error and keeps no instance. No caller outside the package calls `Wait()` (check below, D12).
- `TestHostCallbackToken_TraceHarness` runs with a `ShutdownTimeout` of at most 100 ms and tolerates `context.DeadlineExceeded` from `Stop` (`internal/sshserver/token_trace_test.go:245`).

## Goals / Non-Goals

**Goals:**

- Readiness and teardown ordering that keep every upstream `listenerWg.Add` ordered before any `listenerWg.Wait`, and every `AddGoroutine` of ours ordered before any `WaitForShutdown` that a `Stop` call reaches, for any interleaving of one `Start` with one or more `Stop` calls.
- A `Start` that fails, on its startup timeout, a cancelled `ctx` or any other path, leaves the listener closed, and a later `Stop` and `Wait()` return.
- Regression tests that fail deterministically on 36f85fd6, run with `-race`, through behavioural assertions that hold without the race detector (D7).

**Non-Goals:**

- Changes to `internal/core/serverbase`, `internal/tuiserver`, `internal/discovery`, `go.mod` or the upstream module (no fork, no replace).
- The upstream connection-registration race (`trackConn` against `Shutdown`'s `connWg.Wait()`, gliderlabs/ssh#117). Closing it means dropping the graceful upstream `Shutdown`, which F11 requires.
- Supporting the public `Wait()` called concurrently with `Start`: the godoc rules it out (D12).
- Teardown of the upstream server after a runtime serve error once the server is `Running` (pre-existing; upstream `Serve` closes its listener on return, and `Stop` then waits for the goroutines).

## Decisions

- **D1. Readiness at the first `Accept` of a wrapped listener.** `serve()` passes `srv.Serve` a small wrapper around the listener whose `Accept` runs a one-shot callback before it delegates. The callback calls `s.base.TransitionToRunning()` and opens the serve gate (D2). Upstream calls `trackListener` before its first `Accept` in the same goroutine (`server.go:312`, `:316`), so `Add` happens before readiness, readiness before `Start` returns, and `Start` before any `Stop` that follows it. The wrapper's `Close` and `Addr` delegate; double `Close` (ours in the teardown, upstream's in `Shutdown` and its deferred close) stays best-effort as today.
  - *Alternative:* poll upstream state (`srv.started` is unexported; no public "serving" signal exists in v0.4.3). Rejected: nothing to poll.
  - *Alternative:* keep readiness early and only reorder `Stop`. Rejected: `Start` would still report ready before the server accepts, and the brief requires readiness to mean the listener is registered.
  - *Alternative:* serialise `Serve` and `Shutdown` with a mutex of ours. Rejected: `Serve` blocks for the server's whole life.
- **D2. A serve gate, opened on every exit path, owned by `serve()`'s argument.** A small nil-safe type (a `sync.Once` and a channel) is created by `Start`, stored in a `Server` field in the publish critical section (D4) and passed to the serve goroutine as an argument: `go s.serve(gate)`. `serve()` never reads the gate from the `Server`, so a teardown that has already cleared the server's fields cannot leave it without one. The gate opens at the first `Accept` (D1) and, through a `defer gate.open()` at the top of `serve()`, on every return: the early `srv == nil || listener == nil` return (which also covers a teardown that cleared the fields before `serve()` read them), an upstream `Serve` that fails before `Accept` (only `ensureHostSigner`, which cannot fail once `Start` has configured a host key), and the normal return. Its methods accept a nil receiver, so the literal construction in `server_test.go:409-434` keeps working with `serve(nil)`.
- **D3. One teardown routine, run once, under `stopMu`.** `teardown()` is the only code that closes the published listener and calls upstream `Shutdown`. Its caller holds `stopMu` (D11). In one `srvMu` critical section it checks and sets a `tornDown` flag (a second call returns at once with `nil`), takes `srv`, `listener` and the gate and clears the fields (clearing the gate is harmless, since `serve()` holds its own reference). It then closes the listener, waits for the gate with a context of `ShutdownTimeout`, and on an open gate calls `Shutdown` with that context, filtering closed-connection errors as today. On a timeout it logs, skips `Shutdown` and returns an error wrapping `context.DeadlineExceeded`; the closed listener ends the serve loop at its first `Accept`, and `WaitForShutdown` waits for it later. A nil gate (nothing published) skips the wait. It does not wait for our goroutines and does not change the state.
  - `doStop` is `teardown()`, then `WaitForShutdown`, then `TransitionToStopped`, and returns the teardown's error.
  - The start-failure helper (D5) calls `teardown()` after `TransitionToFailed` and logs its error instead of returning it.
  - The ordinary interleaving where the teardown's critical section runs between `Start`'s publish and `serve()`'s read of the fields ends at once: `serve()` returns early, its deferred open releases the teardown, and upstream `Shutdown` runs on a server whose `Serve` never ran (nothing tracked, nothing to race).
  - *Alternative:* call upstream `Close` on a timeout. Rejected: it adds nothing once the listener is closed (no connection exists before the first `Accept`, and `trackListener` resets `doneChan` anyway).
  - *Alternative:* a separate failure-path teardown in `Start`. Rejected by the maintainer (decision 119): one routine, one mutex, one run.
- **D4. One publish point that a begun teardown refuses.** `Start` builds the listener and the upstream server as today but publishes `listener`, `addr`, `srv`, the gate and both `AddGoroutine` calls in one `srvMu` critical section, after checking `tornDown`. If a teardown has begun, `Start` closes the listener it bound, launches nothing and returns through the start-failure helper (D5) with `errStoppedDuringStartup` as the cause. Either the publish precedes the teardown's critical section, so every `Add` happens before its `Wait`, or `Start` launches nothing. In the second case `Start` closes its listener after the teardown's critical section, possibly after `Stop` has returned: the port is closed once both `Stop` and the overlapping `Start` have returned, not when `Stop` alone has. A `NewServer` failure closes its unpublished listener as today, before the helper.
  - Why `tornDown` is the only flag the publish needs: once this `Start`'s `Created -> Starting` CAS has succeeded, the server becomes terminal only through `doStop` or `failStart`, which both run `teardown()` first, or through `serve()`'s own failure, which follows the publish. The one way to reach a terminal state without a teardown, `Stop` on a `Created` server (`Created -> Stopped`), happens before any `Starting`, and D5's terminal check makes such a `Start` return before it binds.
  - *Alternative:* check `base.State()` under `srvMu`. Rejected: `TransitionToStopping` changes the state lock-free (`base.go:160-191`), so a flag written by the teardown under the same lock is the simpler argument.
  - *Alternative:* a serverbase change to make `AddGoroutine` refuse after a stop. Rejected by scope (brief, requirement 6) and not needed.
- **D5. `Start` returns `nil` only when it observed readiness; every failure return goes through one helper.** The only `nil` return is the `StartedChannel()` branch of the select. Every other return after `TransitionToStarting` (the terminal check below, host key, listen, `NewServer`, a refused publish, the startup context, an error value or a closed error channel) calls `s.failStart(cause)`:
  1. lock `stopMu` (D11), so it never runs inside a concurrent `Stop` and never sees the `Stopping` state;
  2. `recorded := s.base.TransitionToFailed(cause)` (a nil `cause`, from the closed error channel, is replaced by `errStoppedDuringStartup` first);
  3. `s.teardown()` (a no-op when a `Stop` already ran it or nothing was published), its error logged;
  4. unlock and return `recorded` when it is non-nil; otherwise (the server was already terminal with no recorded failure: a concurrent `Stop` won) return an error that matches `errStoppedDuringStartup` and wraps `cause` when `cause` is not that sentinel.

  It never returns `nil`. A startup timeout or cancelled `ctx` therefore returns an error wrapping `context.DeadlineExceeded` or `context.Canceled` with the listener closed, after at most `StartupTimeout` plus `ShutdownTimeout`.
  - *Errors from `TransitionToStarting`* are returned unchanged, without the helper. Such an error means this call did not move the server to `Starting`: either another `Start` owns the server (double `Start`) or `TransitionToStarting` already recorded the failure itself. This call bound nothing, so it has nothing to tear down, and the helper's `teardown()` must not act on resources another call owns. (`TransitionToStarting` itself still calls `TransitionToFailed` on whatever non-terminal state it finds when `ctx` is already cancelled, `Running` included. That is pre-existing serverbase behaviour, listed under Open questions.)
  - *Terminal check, before any setup.* Right after `TransitionToStarting` returns `nil`, `Start` checks `s.base.State().IsTerminal()`. When it is true, `Start` returns `s.failStart(errStoppedDuringStartup)` before it resolves the host key and before it binds. A `nil` from `TransitionToStarting` means one of two things. Either its CAS succeeded, so the state was `Starting` and is terminal now only if a `Stop` has already finished `doStop`. Or it took the no-transition path of a cancelled `ctx` on a server that was already terminal with no recorded failure (Context: `Stop` on a `Created` server, before or concurrently with this `Start`). Terminal states are absorbing (`casToTerminalLocked`, `base.go:271-281`; serverbase-lifecycle spec), so the check is exact for the no-transition case and harmless for the other. In both, `failStart` finds the server terminal with no recorded failure, its `teardown()` has nothing published to close, and it returns `errStoppedDuringStartup`. No listener is bound and no goroutine is launched, so the unordered `Add`/`Wait` and the `stopMu` deadlock of Context cannot arise. Without the check, the `Created -> Stopped` path leaves `tornDown` false, D4's refusal lets the publish through, and `startedCh` never closes; reading the closed error channel afterwards is too late.
  - *Lock order:* `failStart` takes `stopMu` and then, inside `teardown`, `srvMu`; `Start` never holds `srvMu` when it calls `failStart`. `Stop` holds `stopMu` while `doStop` waits for the gate and for `WaitForShutdown`; neither waits for `Start`, so a `Start` blocked on `stopMu` cannot deadlock it.
  - *Why `stopMu` before `TransitionToFailed`:* if `Start` marked the server `Failed` first, a `Stop` could take `stopMu`, see `Failed` and wait in `WaitForShutdown` for a serve goroutine whose listener is still open, while `Start` waits for `stopMu` to tear it down.
- **D6. Test seam: one unexported struct field.** `Server` gets `hooks *lifecycleHooks`, nil in production, with:
  - `beforePublish func(net.Addr)`: called in `Start` after `wish.NewServer` has succeeded, immediately before the publish critical section (D4), with the bound address. Every setup step (host key, bind, `NewServer`) precedes it, and a `Stop` during any of them reaches the same `tornDown` check, so holding this hook exercises the refusal with the most to clean up (a bound listener and an unpublished upstream server). It does not fire when `Start` returns earlier (the D5 terminal check or a setup failure).
  - `serveEntered func()`: called at the top of `serve()`, after the deferred calls are registered and before it reads `srv` and `listener`.
  - `beforeServe func()`: called in `serve()` after it has read `srv` and `listener`, before `srv.Serve`.
  - `beforeShutdown func()`: called in `teardown()` immediately before upstream `srv.Shutdown`, only on the path that calls it. A test that must show the graceful shutdown was skipped (D3, task 3.2) asserts that it never fired.
  - `stopEntered func()`: called at the top of `Stop`, before it takes `stopMu`.

  Tests set it on a `Server` from `mustNew` before `Start`; the `go` statement orders the write before the reads. No package-level variable.
  - *Alternative for "Shutdown skipped":* tell the cases apart by the result of `srv.Serve` (a closed `doneChan` gives `ssh.ErrServerClosed`, an open one the raw `net.ErrClosed`). Rejected: when `Shutdown` runs before `Serve`, `trackListener` resets `doneChan` because nothing is tracked (`charm.land/ssh@v0.4.3/server.go:592-596`), so `Serve` returns `net.ErrClosed` whether `Shutdown` was skipped or called with an expired context.
- **D7. Regression test shape and negative control.** The negative control is behavioural and deterministic, not a race-detector count. With a held window the base cannot produce a `DATA RACE` report: on the base `serve()` signals readiness before the hook point, so `Start` has already returned `nil`, and a `WaitGroup` `Wait` on a zero counter records no write for the detector. Two controls of the D7 shape against upstream v0.4.3 alone gave no report in 20 and in 50 runs. The maintainer accepted this control (decision 119, item 3).
  - `TestServerStopWhileServeLoopDelayed`: `beforeServe` signals that it was reached and waits until `State()` is `Stopping`; it does not sleep. `Start` runs in a goroutine. Once the hook is reached the test asserts that `Start` has not returned, then calls `Stop`. After both return: `Stop` returned `nil`, `Start` returned an error matching `errStoppedDuringStartup`, one dial to the bound port is refused, and `Wait()` returns. On the fix the gate orders upstream `Add` before `Wait` whatever the timing.
  - Every test that holds a hook also releases it from `t.Cleanup`, so a failing assertion never leaves a goroutine blocked (on the base a failed check would otherwise hang the package).
  - On 36f85fd6, with only the D6 seam and a declaration of the sentinel added in a throwaway worktree (no behaviour change), this test and `TestServerStartWaitsForServeLoop` fail on every run under `-race`. Either of two base failures counts: `Start` had already returned while the serve goroutine was held, or `Start` returned `nil` where an error matching `errStoppedDuringStartup` was expected. That deterministic failure is the recorded negative control.
  - Probabilistic supplements on the same throwaway base, run with `-race`, their `DATA RACE` and failure counts recorded as found, zero included, not done conditions: the bounded loop of task 5.1, and a loop of the D7 shape whose `beforeServe` releases as soon as `State()` is `Stopping`, with no sleep (decision 119, item 3).
- **D8. Upstream reference.** One comment, at the readiness wrapper, cites https://github.com/charmbracelet/ssh/issues/61, names the defect by behaviour (charm.land/ssh v0.4.3: a `Shutdown` before `Serve` registers its listener returns at once and `Serve` serves on, racing its listener WaitGroup), states the ordering D1 relies on (`trackListener` before the first `Accept` in `Serve`), and says to remove the workaround (D1-D3 back to a plain `Shutdown`) once upstream fixes it. No TODO marker.
- **D9. Skill doc.** `.agents/skills/server/SKILL.md`, Start rule 4, gains: when a library's `Serve` registers its listener itself, readiness means the library has registered it (signal from the first `Accept` of a wrapped listener), and `Stop` must not call the library's `Shutdown` before that point or the serve goroutine's exit. Start rule 6 gains: a startup failure after resources are published tears them down through the same routine as `Stop`, so a failed `Start` leaves no listener open. Start rule 1 gains a caveat: with an already-cancelled `ctx`, `TransitionToStarting` returns `nil` without a transition on a server that a `Stop` already moved `Created -> Stopped`, so `Start` checks `State().IsTerminal()` before it binds anything (D5). The Stop section, which today says to use the base transition loop "instead of hand-rolled locks" and whose example has a losing `Stop` call `WaitForShutdown` directly, gains: when a `Start` can still publish resources or add goroutines while a `Stop` runs (`TransitionToStopping` accepts `Starting`), serialise `Stop` and the start-failure teardown with one mutex, so a losing `Stop` waits only after the winner's teardown, and make the publish refuse once a teardown has begun (D4, D11). The generic examples stay (they fit `net/http`), with a sentence pointing to `internal/sshserver` for the serialised variant.
- **D10. Formal.** One correspondence row names a symbol this change touches: `Server.Stop` in `formal/tla/HostCallbackToken.tla:33`, bound to `TestHostCallbackToken_StopLeavesAuthenticatedConnectionOpen` as characterisation only (F11: `Stop` closes the listener; open connections stay open). Being characterisation-only, it has no mutation plan, so `formal_mutation.py symbols` against a fresh plan reports `Start`, `Stop`, `doStop` and `serve` as unplanned; the mutation-bound rows of this package are in `server_auth.go` and `server_conns.go`, which this change does not touch. The change keeps the F11 characterisation: for a ready server `Stop` still closes the listener first and then calls upstream `Shutdown`, and that test must still pass. No ledger refresh is planned; the implement stage re-runs `symbols` on every touched symbol and runs `python3 scripts/formal.py correspondence`, `make formal-reach` and, since Java is available, `make formal` (formal-bindings rule, checklist step 8).
- **D11. `stopMu` serialises `Stop` calls and the start-failure teardown.** `Stop` holds a new `stopMu sync.Mutex` for its whole call, `TransitionToStopping` included; `failStart` holds it around `TransitionToFailed` and `teardown` (D5). A `Stop` that loses `TransitionToStopping` therefore reaches `WaitForShutdown` only after the winning `Stop` or the failing `Start` has finished its teardown, and by D4 every `AddGoroutine` of `Start` precedes the winner's `Wait` or never happens. The zero value works, so literal construction needs nothing. No goroutine that `Stop` waits for takes `stopMu`, so the lock cannot deadlock.
  - *Alternative:* a done channel closed at the end of `doStop`, which a losing `Stop` waits on. Rejected: a `Stop` that loses because the server went `Created -> Stopped` or `Failed` without `doStop` would need a separate path, and the mutex gives the same ordering with less state.
- **D12. Public `Wait()` concurrent with `Start`: godoc only (decision 119, item 2).** The godoc of `Wait()` says it must be called only after `Start` has returned (or without `Start`), because it waits on the goroutines that `Start` launches. Check, at 03ed6860: `rg -l sshserver --type go -g '!internal/sshserver/**'` lists only `internal/app/commandadapters/host_access.go`, `host_callback_server.go` and a comment in `internal/testutil/goroutineleak.go`; `rg -n '\bWait\(\)' --type go -g '!internal/sshserver/**'` gives 20 hits, none on an `sshserver.Server` (in those files only `cmd.Wait()` and `wg.Wait()` in tests). The callers outside the package (`HostAccess`, `runtimeHostCallbackServer`) use `New`, `Start`, `Stop`, `IsRunning`, `GetConnectionInfo` and `RevokeToken` only. Inside the package, `srv.Wait()` is called at `server_test.go:431` (no `Start`, `serve()` called directly), `:578` and `:599` (after `Start` returned). New tests call `Wait()` only after `Start` has returned.

## Risks / Trade-offs

- [Upstream reorders `trackListener` and `Accept` in a later version] → D1 then signals too early, and the behavioural tests would not notice. Mitigation: the D8 comment names v0.4.3 and the ordering it relies on, so a bump of `charm.land/ssh` must re-check `Serve`; the package's tests under `-race` in CI remain a probabilistic backstop.
- [Upstream connection-registration race, gliderlabs/ssh#117] → a handshake that completes while `Stop` runs can still race `connWg`. Accepted as a known upstream residual (Non-Goals); the D8 comment area does not claim otherwise.
- [`Start` returns slightly later] → it now waits for `ensureHostSigner` and `trackListener`, microseconds with a configured host signer; `StartupTimeout` (default 5 s) bounds it.
- [A failing `Start` takes longer] → on a startup timeout or cancelled `ctx` it tears down first, which can add up to `ShutdownTimeout` (default 10 s) when the serve goroutine never reaches `Accept`. In exchange it leaves no listener open, and `HostAccess.Ensure`, which drops the instance on error, no longer leaks one.
- [Behaviour change: `Start` returns an error instead of `nil` when a concurrent `Stop` wins] → no production caller overlaps the two (`host_access.go:44-95`); the error is truthful.
- [The race detector rarely sees the original race] → the negative control relies on deterministic behavioural assertions instead (D7); the race-detector supplements are recorded with their counts, whatever they are.
- [A `beforeServe` hold longer than `ShutdownTimeout`] → `Stop` returns a timeout error after the serve goroutine exits, and a failing `Start` returns its own error with the timeout logged; both covered by tests.
- [Dial assertions on Windows] → a refused loopback connect there typically takes about 2 s (SYN retries). Single tests dial once with a bounded timeout; the loop of task 5.1 runs its dials concurrently and collects them at the end, so the cost is paid about once. A port freed by `Stop` could in principle be rebound by a parallel test before the dial; that would show as a successful dial naming the port, and is accepted as rare.

## Migration Plan

None: internal package, no config or schema change. Rollback is a revert.

## Maintainer decisions

- 2026-11-25 (brief `program-notes/briefs/sshserver-race-brief.md`, decision 117): readiness = upstream has registered its listener, observed at the first `Accept`; `Stop` never calls upstream `Shutdown` before that point or the serve goroutine's exit, bounded by `ShutdownTimeout`; scope frozen to `internal/sshserver` (plus the server skill doc).
- 2026-11-25 (brief `program-notes/briefs/sshserver-race-revise-1.md`, decision 119, after spec review run wf_ed9737d2-555):
  - the startup-timeout and cancelled-`ctx` teardown is fixed here, through one teardown routine shared with `doStop`, under one mutex, run once (D3, D5, D11); no serverbase change;
  - public `Wait()` concurrent with `Start`: godoc only, after an rg check (D12);
  - the deterministic behavioural negative control satisfies brief requirement 7 (D7), with an optional race-detector supplement on the base;
  - the D8 comment cites https://github.com/charmbracelet/ssh/issues/61;
  - `Start` returns `nil` only when it observed readiness, every failure return goes through one helper (D5);
  - the Stop-racing-Start loop asserts invariants, not an enumeration of `Start` results (task 5.1);
  - the capability is named `host-callback-server-lifecycle`, after the existing `host-callback-*` naming (`openspec/changes/close-sessions-on-token-revoke/specs/host-callback-session-lifetime/`);
  - the purpose is narrowed to the listener-registration race; the connection-registration race is a known upstream residual (gliderlabs/ssh#117).

## Open questions

Both items below are pre-existing serverbase behaviour, outside this change's frozen scope. They are listed for the maintainer as possible serverbase follow-ups and do not change this change's specs or tasks.

- **serverbase: `TransitionToStarting` returns `nil` without a transition.** With an already-cancelled `ctx` on a server already terminal with no recorded failure (a `Stop` on a `Created` server), `TransitionToStarting` returns `TransitionToFailed`'s recorded `nil` (`base.go:96-100`, `:134-140`), so a caller cannot tell that nothing started. This change handles it inside `internal/sshserver` with the D5 terminal check before any setup, so it needs no serverbase change. `tuiserver.Start` has the same shape (`internal/tuiserver/server.go:139-147`: `bindAll` right after `TransitionToStarting`) and is not changed here (scope); a serverbase fix would cover both servers.
- **serverbase: a cancelled-`ctx` `Start` on a `Running` server fails it.** `TransitionToStarting` checks `ctx` before its `Created -> Starting` CAS and calls `TransitionToFailed`, which CASes any non-terminal state to `Failed` (`base.go:96-100`, `:134-151`, `:271-281`). A second `Start` with a cancelled `ctx` on a running sshserver therefore marks it `Failed` while the listener stays open and the serve loop keeps running; a later `Stop` sees `Failed` and blocks in `WaitForShutdown`. `TestServerDoubleStart` (`internal/sshserver/server_test.go:235-254`) uses a live `ctx` and does not cover it. Not fixed here: inside `internal/sshserver` this call cannot tell it from its own startup failure without a serverbase change, and no production caller starts a server twice (`HostAccess.Ensure`, `internal/app/commandadapters/host_access.go:44-73`, calls `Start` only on an instance it has just built with `sshserver.New`).
