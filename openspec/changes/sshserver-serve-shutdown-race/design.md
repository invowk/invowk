# Design

## Context

Motivation: proposal.md, "Why". Current behaviour, at base 36f85fd6:

- `serve()` calls `s.base.TransitionToRunning()` as its first step (`internal/sshserver/server_lifecycle.go:172`), before it reads `srv` and `listener` (`:175-178`) and before `srv.Serve(listener)` (`:184`). `Start` returns `nil` as soon as `StartedChannel()` closes (`:98-102`), so it returns before upstream `Serve` has run.
- Upstream `Serve` (`charm.land/ssh@v0.4.3/server.go:294-339`) runs `ensureHandlers`, `ensureHostSigner` (`:304`), then `trackListener(l, true)` (`:312`), which resets `doneChan` when no listener or connection is tracked (`:592-596`) and calls `listenerWg.Add(1)` (`:598`), and only then its first `l.Accept()` (`:316`), in the same goroutine.
- Upstream `Shutdown` (`server.go:268-287`) closes the tracked listeners and `doneChan` under `srv.mu`, then waits on `listenerWg` in a new goroutine (`:275-279`). A `Shutdown` that runs before `trackListener` finds nothing to wait for; `Serve` then registers the listener, resets `doneChan` and serves on, and its `Add` races the `Wait` (CI: `server.go:275` against `:312`).
- `doStop` closes our listener before `Shutdown` (`server_lifecycle.go:141-145`). That is why `Serve` does not serve on in invowk today: its first `Accept` fails on the closed listener and, with `doneChan` reset, returns the `net.ErrClosed` error, which `serve()` ignores (`:188-190`). The race on the WaitGroup remains.
- `Start` publishes `s.listener` and `s.addr` (`:62-65`) and `s.srv` (`:85-87`) in two separate critical sections and calls `AddGoroutine` outside any lock (`:90`, `:94`). `TransitionToStopping` accepts `StateStarting` (`internal/core/serverbase/base.go:174`), so a `Stop` during `Start` runs `doStop` at once. When it runs before `:90`, `doStop` takes nil resources, `WaitForShutdown` (`:158`, `base.go:218-220`) returns on a zero counter, and `Start` then calls `AddGoroutine`: an `Add` racing a `Wait` in our own WaitGroup. When it runs before `:62`, the listener `Start` stores later is never closed and the serve goroutine serves on it with nobody to stop it.
- In that case `TransitionToRunning` fails its CAS (`base.go:124-128`), `startedCh` never closes, and `Start` reads the closed error channel (`:104-106`): it receives `nil`, `TransitionToFailed(nil)` finds a terminal state and returns the recorded `nil` (`base.go:134-140`), so `Start` returns `nil` for a server that is stopped.
- `TestServerServeFailureTransitionsToFailed` (`internal/sshserver/server_test.go:409-433`) builds a `Server` literal with only `base`, `srv` and `listener` and calls `serve()` directly, without `Start`.
- A `Stop` that loses `TransitionToStopping` (`Stopping`, `Stopped` or `Failed` already set) calls `WaitForShutdown` directly (`server_lifecycle.go:118-121`). While the winning `Stop` runs `doStop` during a `Start` that has not yet called `AddGoroutine`, that `Wait` on a zero counter can race `Start`'s `Add` too. The public `Wait()` (`:275-276`) calls `WaitForShutdown` in the same way.
- The production caller (`internal/app/commandadapters/host_access.go:63-67`, `:85-95`) calls `Start` and later `Stop` from one goroutine.
- `TestHostCallbackToken_TraceHarness` runs with a `ShutdownTimeout` of at most 100 ms and tolerates `context.DeadlineExceeded` from `Stop` (`internal/sshserver/token_trace_test.go:245`).

## Goals / Non-Goals

**Goals:**

- Readiness and stop ordering that keep every upstream `listenerWg.Add` ordered before any `listenerWg.Wait`, and every `AddGoroutine` of ours ordered before any `WaitForShutdown` that a `Stop` call reaches, for any interleaving of one `Start` with one or more `Stop` calls.
- Regression tests that fail deterministically on 36f85fd6, run with `-race`, through behavioural assertions that hold without the race detector (D7).

**Non-Goals:**

- Changes to `internal/core/serverbase`, `internal/tuiserver`, `go.mod` or the upstream module (no fork, no replace).
- The `Start` failure paths that leave a serve goroutine running (see Open questions).
- The public `Wait()` called while a `Start` has not yet returned, whether or not a `Stop` runs too (see Open questions).

## Decisions

- **D1. Readiness at the first `Accept` of a wrapped listener.** `serve()` passes `srv.Serve` a small wrapper around the listener whose `Accept` runs a one-shot callback before it delegates. The callback calls `s.base.TransitionToRunning()` and opens the serve gate (D2). Upstream calls `trackListener` before its first `Accept` in the same goroutine (`server.go:312`, `:316`), so `Add` happens before readiness, readiness before `Start` returns, and `Start` before any `Stop` that follows it. The wrapper's `Close` and `Addr` delegate; double `Close` (ours in `doStop`, upstream's in `Shutdown` and its deferred close) stays best-effort as today.
  - *Alternative:* poll upstream state (`srv.started` is unexported; no public "serving" signal exists in v0.4.3). Rejected: nothing to poll.
  - *Alternative:* keep readiness early and only reorder `Stop`. Rejected: `Start` would still report ready before the server accepts, and the brief requires readiness to mean the listener is registered.
  - *Alternative:* serialise `Serve` and `Shutdown` with a mutex of ours. Rejected: `Serve` blocks for the server's whole life.
- **D2. A serve gate, opened on every exit path, owned by `serve()`'s argument.** A small nil-safe type (a `sync.Once` and a channel) is created by `Start`, stored in a `Server` field in the publish critical section (D4) and passed to the serve goroutine as an argument: `go s.serve(gate)`. `serve()` never reads the gate from the `Server`, so a `doStop` that has already cleared the server's fields cannot leave it without one. The gate opens at the first `Accept` (D1) and, through a `defer gate.open()` at the top of `serve()`, on every return: the early `srv == nil || listener == nil` return (which also covers a `doStop` that cleared the fields before `serve()` read them), an upstream `Serve` that fails before `Accept` (only `ensureHostSigner`, which cannot fail once `Start` has configured a host key), and the normal return. Its methods accept a nil receiver, so the literal construction in `server_test.go:409-433` keeps working with `serve(nil)`.
- **D3. `doStop` waits for the gate before upstream `Shutdown`.** `doStop` reads the gate field together with `srv` and `listener` in its critical section (clearing it there is harmless, since `serve()` holds its own reference), keeps closing the listener first, then waits for the gate with the existing `shutdownCtx` (`ShutdownTimeout`). Gate open: call `Shutdown(shutdownCtx)` as today. Timeout: log it, skip `Shutdown` and return an error wrapping `context.DeadlineExceeded`; the closed listener ends the serve loop at its first `Accept`, and `WaitForShutdown` then waits for it. A nil gate (no server published) skips the wait. The ordinary interleaving where `doStop`'s critical section runs between `Start`'s publish and `serve()`'s read of the fields therefore ends at once: `serve()` returns early, its deferred open releases `doStop`, and upstream `Shutdown` runs on a server whose `Serve` never ran (nothing tracked, nothing to race).
  - *Alternative:* call upstream `Close` on a timeout. Rejected: it adds nothing once the listener is closed (no connection exists before the first `Accept`, and `trackListener` resets `doneChan` anyway).
- **D4. One publish point that a started stop refuses.** `doStop` sets a `stopBegun` flag in the critical section where it takes the resources. `Start` builds the listener and the upstream server as today but publishes `listener`, `addr`, `srv`, the gate and both `AddGoroutine` calls in one `srvMu` critical section, after checking `stopBegun`. If a stop has begun, `Start` closes the listener it bound, launches nothing and returns an unexported sentinel error (`errStoppedDuringStartup`), leaving the state to `Stop`. Either the publish precedes `doStop`'s critical section, so every `Add` happens before its `Wait`, or `Start` launches nothing. In the second case `Start` closes its listener after `doStop`'s critical section, possibly after `Stop` has returned: the port is closed once both `Stop` and the overlapping `Start` have returned, not when `Stop` alone has.
  - *Alternative:* check `base.State()` under `srvMu`. Rejected: `TransitionToStopping` changes the state lock-free (`base.go:160-191`), so a flag written by `doStop` under the same lock is the simpler argument.
  - *Alternative:* a serverbase change to make `AddGoroutine` refuse after a stop. Rejected by scope (brief, requirement 6) and not needed.
- **D5. `Start` reports a stop that wins before readiness.** When `Start` reads the closed error channel (`ok == false`) it returns `LastError()` if one is recorded, `nil` if `StartedChannel()` is already closed (the server was ready, then stopped), and `errStoppedDuringStartup` otherwise, instead of calling `TransitionToFailed(nil)`. The state stays as `Stop` set it.
- **D6. Test seam: one unexported struct field.** `Server` gets `hooks *lifecycleHooks`, nil in production, with `beforePublish func(net.Addr)` (called in `Start` after the listener is bound and before the publish point, with the bound address), `serveEntered func()` (called at the top of `serve()`, after the deferred calls are registered and before it reads `srv` and `listener`) and `beforeServe func()` (called in `serve()` after it has read `srv` and `listener`, before `srv.Serve`). Tests set it on a `Server` from `mustNew` before `Start`; the `go` statement orders the write before the reads. No package-level variable.
- **D7. Regression test shape and negative control.** The negative control is behavioural and deterministic, not a race-detector count: two controls of the D7 shape against upstream v0.4.3 alone gave no `DATA RACE` report in 20 and in 50 runs, because a `WaitGroup` `Wait` on a zero counter records no write for the detector, and on the base `serve()` signals readiness before the hook point, so `Start` has already returned `nil` there.
  - `TestServerStopWhileServeLoopDelayed`: `beforeServe` signals that it was reached and waits until `State()` is `Stopping`; it does not sleep. `Start` runs in a goroutine. Once the hook is reached the test asserts that `Start` has not returned, then calls `Stop`. After both return: `Stop` returned `nil`, `Start` returned an error matching `errStoppedDuringStartup`, one dial to the bound port is refused, and `Wait()` returns. On the fix the gate orders upstream `Add` before `Wait` whatever the timing.
  - On 36f85fd6, with only the D6 seam and a declaration of the sentinel added in a throwaway worktree (no behaviour change), this test and `TestServerStartWaitsForServeLoop` fail on every run under `-race`: `Start` has returned `nil` while the serve goroutine is held. That deterministic failure is the recorded negative control (brief requirement 7, read as "a test run with `-race` that fails on the base"; the question is in the result for the maintainer).
  - As a probabilistic supplement, the bounded loop of task 5.1 runs on the same throwaway base with `-race`, and its `DATA RACE` and failure counts are recorded as found, zero included; it is not a done condition.
- **D8. Upstream reference.** One comment, at the readiness wrapper, names the defect by behaviour (charm.land/ssh v0.4.3: a `Shutdown` before `Serve` registers its listener returns at once and `Serve` serves on, racing its listener WaitGroup) and says that D1-D3 can be simplified back once upstream fixes it. No TODO marker; the maintainer adds the issue URL in a later revise.
- **D9. Skill doc.** `.agents/skills/server/SKILL.md`, Start rule 4, gains: when a library's `Serve` registers its listener itself, readiness means the library has registered it (signal from the first `Accept` of a wrapped listener), and `Stop` must not call the library's `Shutdown` before that point or the serve goroutine's exit. The generic example stays (it fits `net/http`).
- **D10. Formal.** One correspondence row names a symbol this change touches: `Server.Stop` in `formal/tla/HostCallbackToken.tla:33`, bound to `TestHostCallbackToken_StopLeavesAuthenticatedConnectionOpen` as characterisation only (F11: `Stop` closes the listener; open connections stay open). Being characterisation-only, it has no mutation plan, so `formal_mutation.py symbols` against a fresh plan reports `Start`, `Stop`, `doStop` and `serve` as unplanned; the mutation-bound rows of this package are in `server_auth.go` and `server_conns.go`, which this change does not touch. The change keeps the F11 characterisation: for a ready server `Stop` still closes the listener first and then calls upstream `Shutdown`, and that test must still pass. No ledger refresh is planned; the implement stage re-runs `symbols` on every touched symbol and runs `python3 scripts/formal.py correspondence`, `make formal-reach` and, since Java is available, `make formal` (formal-bindings rule, checklist step 8).
- **D11. Concurrent `Stop` calls are serialised.** `Stop` holds a new `stopMu sync.Mutex` for its whole call. A `Stop` that loses `TransitionToStopping` therefore reaches `WaitForShutdown` only after the winning `Stop` has returned, and by D4 every `AddGoroutine` of `Start` precedes the winner's `Wait` or never happens. The zero value works, so literal construction needs nothing. No goroutine that `Stop` waits for calls `Stop`, so the lock cannot deadlock.
  - *Alternative:* a done channel closed at the end of `doStop`, which a losing `Stop` waits on. Rejected: a `Stop` that loses because the server went `Created -> Stopped` or `Failed` without `doStop` would need a separate path, and the mutex gives the same ordering with less state.

## Risks / Trade-offs

- [Upstream reorders `trackListener` and `Accept` in a later version] → D1 then signals too early, and the behavioural tests would not notice. Mitigation: the D8 comment names v0.4.3 and the ordering it relies on, so a bump of `charm.land/ssh` must re-check `Serve`; the package's tests under `-race` in CI remain a probabilistic backstop.
- [`Start` returns slightly later] → it now waits for `ensureHostSigner` and `trackListener`, microseconds with a configured host signer; `StartupTimeout` (default 5 s) bounds it.
- [Behaviour change: `Start` returns an error instead of `nil` when a concurrent `Stop` wins] → no production caller overlaps the two (`host_access.go:63-95`); the error is truthful.
- [The race detector rarely sees the original race] → the negative control relies on deterministic behavioural assertions instead (D7); the race-detector supplement is recorded with its counts, whatever they are.
- [A `beforeServe` hold longer than `ShutdownTimeout`] → `Stop` returns a timeout error after the serve goroutine exits; covered by a test.
- [Dial assertions on Windows] → a refused loopback connect there typically takes about 2 s (SYN retries). Each test dials once with a bounded timeout, and the loop of task 5.1 dials only on a sample. A port freed by `Stop` could in principle be rebound by a parallel test before the dial; that would show as a successful dial naming the port, and is accepted as rare.

## Migration Plan

None: internal package, no config or schema change. Rollback is a revert.

## Open questions

- **Startup timeout and cancelled `ctx` leave the server serving.** When `startupCtx` ends (`server_lifecycle.go:108-110`), `Start` calls `TransitionToFailed`, which cancels the base context but closes neither the listener nor the upstream server; the serve goroutine keeps serving, and a later `Stop` sees `Failed`, skips `doStop` and blocks in `WaitForShutdown` (`:118-121`). Pre-existing and outside the frozen scope; it does not change this change's specs or tasks. Listed for the maintainer: fix it in a follow-up (tear down through the same gate) or here in a revise.
- **Public `Wait()` during `Start`.** `Wait()` called while `Start` has not reached its publish point returns at once on a zero counter and can race `Start`'s `AddGoroutine`. That is a caller running `Wait()` concurrently with `Start`, not a `Start`/`Stop` overlap; no caller does it today. Listed for the maintainer as a possible follow-up.
- **Brief requirement 7.** This plan reads "fails on 36f85fd6 under `-race`" as a test run with `-race` that fails deterministically on the base (D7), with the race-detector count as a recorded supplement. If the maintainer requires an actual `DATA RACE` report, a revise is needed.
