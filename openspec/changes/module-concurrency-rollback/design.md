## Goals / Non-Goals

**Goals:**
- One mechanism, one place per concern: modulesync decides what is locked and for how long; an OS adapter only takes and releases an exclusive file lock; the CLI only renders.
- Each formal fix lands with its model flip, its inverted replay and its `mutantPreFix…` command in one commit, so `make formal` and the replays agree at every commit.
- The inverted replays count as killers for the reach run and `mutation-formal`, so the new lock code is planned for mutation.

**Non-Goals:**
- `module update` with no lock still creates an empty lock (tracker Q4; brief "Not in scope").
- Discovery items (F12, module-subdirectory hardening, discovery performance, `agent --verify`) belong to W1b.
- The `RemoveProg` note and the `WriteMod` and `WriteLock` / `LockFile.Save` rows belong to the W3 formal follow-ups: W1a changes only their binding cells (renamed tests, D12), never their notes or line numbers.
- No lock for read-only consumers, no config option for the timeout, no `go.mod` change.
- A successful `AddRequirement` or `RemoveRequirementIfPresent` still replaces a symbolic `invowkmod.cue` with a regular file (`pkg/fspath/atomic.go:86`; OQ-B, MA5): listed for the tracker.

## Decisions

### D1. A port in modulesync, a file-lock adapter in `internal/modulelock`

modulesync defines the port it needs (names indicative):

```go
// EditLocker takes exclusive OS advisory locks on lock files.
type EditLocker interface {
    // Lock tries path without blocking; while it is busy it calls onBusy once,
    // retries about every 100 ms, and gives up when ctx ends or 5 minutes pass.
    Lock(ctx context.Context, path types.FilesystemPath, onBusy func()) (unlock func() error, err error)
    // PhysicalDir returns dir's physical absolute path (links and junctions resolved).
    PhysicalDir(dir types.FilesystemPath) (types.FilesystemPath, error)
}
```

`internal/modulelock` implements it with `flock(LOCK_EX|LOCK_NB)` on linux, darwin, freebsd, netbsd, openbsd and dragonfly, and `LockFileEx(LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY)` on windows, through `golang.org/x/sys`. Its signatures use only the standard library and `pkg/types`, and it imports neither modulesync nor moduleops, so their internal tests can use the real adapter without an import cycle. The lock file is opened `O_RDWR|O_CREATE` with mode 0600 and never truncated or deleted; unlock releases the lock and closes the descriptor. A second `Lock` of a path the same `FileLocker` value already holds fails at once (`ErrLockHeld`) instead of waiting for itself. The poll interval (100 ms) and the timeout (5 minutes) are fields set by the constructor; the adapter's own tests shorten them through `export_test.go`. On timeout it returns `*modulelock.TimeoutError` whose message is `timed out after 5m0s waiting for lock file <path>: another invowk process holds it; let it finish or stop it, then retry`. On cancellation it returns `waiting for lock file <path>: <ctx error>`. Any other failure (open, permission, unexpected lock error) fails at once and names the path. Other platforms return `ErrLockUnsupported` from `Lock` (fail closed: no release target is affected; accepted, revise-1).

`PhysicalDir` is `filepath.EvalSymlinks(filepath.Abs(dir))` on Unix. On Windows it opens the directory with `FILE_FLAG_BACKUP_SEMANTICS` and reads `GetFinalPathNameByHandle(FILE_NAME_NORMALIZED|VOLUME_NAME_DOS)`, stripping `\\?\` (and turning `\\?\UNC\` into `\\`), because `EvalSymlinks` does not follow junctions on Go 1.23+ (`formal/README.md` F18 row); this also yields the on-disk case and long names. The prefix handling is a pure helper (`trimFinalPathPrefix`) in a file without build tags, so its table test (`\\?\C:\x` → `C:\x`, `\\?\UNC\srv\share\x` → `\\srv\share\x`, a path without the prefix unchanged) runs on every platform.

`PhysicalDir` tests (`internal/modulelock`): on Unix, a directory and a symbolic link to it give the same result; on Windows, a directory and a junction to it (created with `cmd /c mklink /J`), the directory spelled in another case, and its 8.3 short name (from `windows.GetShortPathName`) all give the directory's long, on-disk-case path. Each Windows case skips with the reason logged where the link or the short name cannot be made (8.3 names disabled on the volume). A modulesync test then builds two resolvers on one cache root, one through the project's real path and one through a symbolic link to it, and checks that `LockProject` uses one lock file name (spec "One project through two paths"; skips where `os.Symlink` is refused).

The composition root is `cmd/invowk`: it builds one `modulelock.FileLocker` per command run and passes it, with the wait renderer, to the use cases. Alternatives: the adapter computing lock names and printing (puts naming policy and rendering in an OS package and makes order checks untestable without real files); `modulesync` importing the adapter directly (app depends on infrastructure, no fake for tests).

### D2. What the project lock covers, command by command

modulesync owns a small per-operation helper, `editLocks` (held by the `Resolver`, in the new file `internal/app/modulesync/edit_locks.go`), exposed as the exported `(*Resolver).LockProject(ctx) (unlock func() error, err error)`, which moduleops' vendor path needs (it joins `vendorDependencyResolver`, `vendor_dependencies.go:30-33`; accepted, revise-1), and the unexported `(*Resolver).lockSource(ctx, gitURL)`. Both return an unlock closure that calls `(*editLocks).release`, which drops the held-lock record and then calls the adapter's unlock; that method is the one release point the `Release` correspondence row names (D12). The lock-taking use cases receive the locker, the wait callback and the cache root as one explicit dependency value (`modulesync.EditLocks{Locker EditLocker; OnWait func(LockWait); CacheDir types.FilesystemPath}`, where an empty `CacheDir` means the default root `NewResolver` uses today; production leaves it empty, tests set a temporary directory). `NewResolver` gains a variadic option (`WithEditLocks`) so existing callers compile; the test constructor `newResolverWithFetcher` gets the same option.

Which entry points require a locker:
- **Require one** (fail with `ErrEditLockerRequired`, no file read): the package-level use cases `AddModuleDependency`, `RemoveModuleDependency`, `SyncModule`, `UpdateModule`, `TidyModule` and `moduleops.VendorDependencies`; the `Resolver` methods `AddModuleDependency`, `RemoveModuleDependency`, `SyncModule`, `UpdateModule`, `TidyModule` and `LockProject`; and `vendorDependenciesWithResolver`, through `LockProject`. Production never runs unlocked by accident. `TestModuleEditUseCasesRequireLocker` checks each package-level use case and each `Resolver` method with no locker: `ErrEditLockerRequired`, both files untouched, no cache directory created.
- **Run without one**: the inner methods `Add`, `Remove`, `Sync`, `Update`, `Tidy`, `LoadDeclaredFromLock` and `resolveOne`, which take no project lock; `resolveOne` takes a source lock only when the resolver has a locker (D3). `moduleops.resolveVendorDependencies` takes no lock either.

Existing tests that call a locking entry point therefore get a locker: `use_cases_lock_written_test.go` (4 call sites: one `Resolver.AddModuleDependency`, two `Resolver.RemoveModuleDependency`, one `SyncModule`), `use_cases_dependency_test.go` (4: the package-level `AddModuleDependency` and `RemoveModuleDependency` and the two `Resolver` methods), `internal/app/moduleops/vendor_test.go` (1: `VendorDependencies`; its three `resolveVendorDependencies` calls take no lock), plus the replays (D13: three call sites in `concurrent_edits_formal_test.go`, one in `vendor_concurrent_formal_test.go`). Each gets a real `modulelock.FileLocker` or a recording fake, and a temporary `CacheDir` (parallel tests cannot use `t.Setenv(INVOWK_MODULES_PATH)`); no test that locks may use the default cache root, because the lock directory would then land in the developer's real `~/.invowk/modules` (D5).

| Command | Lock taken | Released after |
|---|---|---|
| `module add` (`(*Resolver).AddModuleDependency`) | before `readLockSnapshot` | the declaration edit or the last restore |
| `module remove` (`(*Resolver).RemoveModuleDependency`) | before `readLockSnapshot` | the last edit or the last restore |
| `module sync` (new `(*Resolver).SyncModule`; `SyncModule` wraps it) | before `LoadRequirements` | the lock save (or the empty-requires return) |
| `module update` (new `(*Resolver).UpdateModule`) | before `m.Update` reads the lock | the lock save |
| `module tidy` (new `(*Resolver).TidyModule`) | before `LoadRequirements` | the last `AddRequirement` |
| `module vendor` (`vendorDependenciesWithResolver`) | before `LoadRequirements` (moved into it from `VendorDependencies`) | `VendorModules` returns (after its last copy into `invowk_modules/`, which comes after the sync's lock save) |

So `SyncModule`, `TidyModule` and `VendorDependencies` create their resolver before reading `invowkmod.cue` (they read it first today, `use_cases.go:407-418`, `:429-440`, `vendor_dependencies.go:75-86`). A consequence: on a project with no `requires`, sync, tidy and vendor now create the cache root, `locks/` and the project lock file before they find nothing to do (D5, MA1 accepted). The inner methods (`Add`, `Remove`, `Sync`, `Update`, `Tidy`) do not lock: they run under the caller's project lock, and vendor calls `Sync` while holding it. This matches the model's `Early`/`Final` placement (`.tla:142-145`, `:164-198`).

### D3. The source lock covers checkout to the verified, read copy

`resolveOne` takes the source lock right before `m.fetcher.Fetch` (`resolver_deps.go:130`) and releases it when `resolveOne` returns (accepted, revise-1), which covers the clone or fetch and checkout, `selectSourceModule`, the hashless-entry `RemoveAll`, `cacheModule` with its verification, and `loadTransitiveDeps`' read of the cache copy (`:130-181`). Holding it to the end of `resolveOne` (rather than exactly to the verified copy) also keeps a concurrent hashless refetch from removing the copy this process is still reading; nothing inside takes another lock. `ListVersions` stays outside: it uses in-memory storage and no checkout (`git.go:110-144`). When the resolver has no locker (unit tests that build a `Resolver` directly), `resolveOne` takes no source lock; every production construction sets one (D2).

The key is the checkout path's cache-relative part: `getRepoCachePath`'s derivation moves into one function (`sourceCheckoutKey(gitURL) string`) that both `getRepoCachePath` and the source lock use, so every URL spelling that shares a checkout shares the lock.

### D4. Lock order is enforced, not only documented

`editLocks` records which locks it holds. `LockProject` fails with `errLockOrder` (no wait) while a source lock is held, and `lockSource` fails while another source lock is held. A resolver used directly with no project lock (the F9 replay, unit tests) may take a source lock: the project-first rule binds the use cases, which always lock the project first. A unit test with a recording fake locker checks the order project, then source, then source release, then project release for a sync that fetches, and a second test calls `LockProject` while a source lock is held and expects `errLockOrder`; that test fails against an implementation that takes the locks in reverse or does not check. The model's `noCircularWait` and `mutantReverseOrder` (`manifest.toml:2077-2091`) cover the protocol.

The project-lock window of every locking command is tested at the use-case level (`TestModuleEditsHoldProjectLock`, a table over add, remove, sync, update, tidy and vendor, with a temporary `CacheDir`):
- **Nothing read before the lock.** The recording fake's `Lock` rewrites `invowkmod.cue` and the lock file to a second valid state before it grants the lock. Each command's result and final files must derive from that second state (for example sync's lock lists the module only the second `invowkmod.cue` requires; remove finds the entry only the second lock holds), which fails for an implementation that read either file first.
- **Nothing written after the release.** The fake's unlock records both files' content and, for vendor, whether `invowk_modules/` is complete. The files must not change after unlock, and vendor's copies must be complete before it.
- **Cancelled wait.** A fake `Lock` that returns `context.Canceled` makes each command fail with an error that wraps it, with both files byte-identical to before.

The source-lock wait has its own tests (`TestSourceLockWaitCancelled` and `TestSourceLockWaitTimedOut`): a fake that grants the project lock and returns `context.Canceled`, respectively a `*modulelock.TimeoutError`, for the source lock. For add, sync and update each command must fail with an error that wraps it (`errors.Is` / `errors.As`), leave both files byte-identical to before, and add must report rollback `none` (spec "Wait for a source lock cancelled or timed out"); the timeout error text must name the source lock file.

A further test (`TestReadOnlyConsumersIgnoreProjectLock`) holds a project's lock with a real `modulelock.FileLocker`, then runs `ListModuleDependencies`, `LoadRequirements` and the discovery load that `invowk cmd` and `validate` use on that project. Each must return under a short test deadline, which shows that none of them waits on the lock.

### D5. Lock file names and the `locks` directory

Per the binding decision: `<cache root>/locks/project-<hex SHA-256 of PhysicalDir(project dir)>.lock` and `<cache root>/locks/source-<hex SHA-256 of sourceCheckoutKey(url)>.lock`, where the cache root is the resolver's `cacheDir` (`resolver.go:79-95`). Before the first lock, modulesync runs `os.MkdirAll(cacheRoot, 0o755)` (the mode `NewResolver` uses, `resolver.go:97-99`) and then `os.Mkdir(locks, 0o700)`, tolerating an existing directory; it does not change the mode of an existing one. Lock files are never deleted by invowk.

Consequence (MA1, accepted in revise-1): `module remove`, and `module sync`, `tidy` and `vendor` on a project with no `requires`, now create the cache root and `locks/` (and the project lock file) when they are missing. Skipping the lock when the cache root is missing is not safe: a concurrent `module update` creates the root and takes the lock, and the remove would run unlocked, which is F8's `update_remove` case; sync, tidy and vendor cannot know that `requires` is empty before they read `invowkmod.cue`, which they do only under the lock.

When the cache root cannot be resolved (no home directory and no `INVOWK_MODULES_PATH`) or the cache root, `locks/` or the lock file cannot be created or opened, the command fails before it reads either file, with an error that names the path and the fix: `cannot create module lock directory <path>: <cause>; set INVOWK_MODULES_PATH to a writable directory`, and for an unresolvable root `cannot determine the module cache directory: <cause>; set INVOWK_MODULES_PATH`. A test (`TestModuleEditLockDirectoryNotWritable`) points `CacheDir` at a path under a regular file (so `MkdirAll` fails on every platform, as root too) and checks that add, remove and sync fail with that error and leave both files untouched.

`TestRemoveModuleDependencyDoesNotCreateModuleCache` is renamed `TestRemoveModuleDependencyCreatesOnlyProjectLock` and asserts that remove creates nothing in the cache except the `locks` directory and its project lock file (no `sources/`, no module copy); `TestSyncModuleWithoutRequirementsReportsNoWrite` (parallel, today on the default cache) gets a temporary `CacheDir` and asserts the same for an empty sync (D2). `module deps` takes no lock and keeps creating nothing (`TestListModuleDependenciesDoesNotCreateModuleCache` unchanged).

Where the lock files are relative to a project: `<cache root>/locks/` is never a module directory (its name has no `.invowkmod` suffix and it holds no `invowkmod.cue`), a cache checkout (`sources/…`), a cache copy or an `invowk_modules/` directory, and no content hash, vendoring, `validate` or `audit` reads it. It is outside the project directory only when the cache root is: a cache root inside the project (a project at `$HOME`, an `INVOWK_MODULES_PATH` under the project, or every CLI testscript, which runs with `HOME=$WORK`, `tests/cli/cmd_test.go:46`) puts it inside. See MA3.

### D6. Waiting is reported once and rendered by the CLI

`editLocks` passes the adapter an `onBusy` that calls `OnWait(LockWait{Kind, LockPath, GitURL})` once. `cmd/invowk` renders it with a `//plint:render` helper to stderr: `Waiting for another invowk module command on this project (lock: <path>)` or `Waiting for another invowk module command on module source <url> (lock: <path>)`. No line is printed when the lock is free. Ctrl+C cancels the command context (`fang.WithNotifySignal(os.Interrupt)`, `cmd/invowk/root.go:101-107`), the wait returns the cancellation error, and the command exits through the normal error path. What the command has done by then depends on the lock it waited for:
- **Project lock:** the wait comes before any read of `invowkmod.cue` or the lock file (D2), so the command has read and written neither.
- **Source lock:** the wait comes inside `resolveOne`, after the command read both files (add and remove took their snapshots, sync, tidy and vendor read `requires`, every command read the lock), but before any write of either file: in every command the fetches precede the lock save and the `invowkmod.cue` edits (`resolver.go:145-161`, `:302-320`, `:262-273`; `resolver_tidy.go` writes nothing; vendor copies only after its sync). So the command fails with both files as it found them, and add needs no rollback.

The timeout error goes through each command's existing error path (add, remove, sync and update: `Failed to … module(s): <error>`; tidy: the bare error, `module_tidy.go:43-46`; vendor: `failed to resolve dependencies: <error>`, `module_package.go:190-192`) and exits 1 (`exitCodeForError`, `cmd/invowk/usage_error.go:175-186`).

### D7. Read-only consumers, and the model's reader

Discovery, command runs, `validate`, `audit` and `module deps` take no lock (binding decision 2). They read `invowkmod.cue` and the lock with plain reads and rely on every write being an atomic replace: `LockFile.SaveIfChanged` (A1, `.tla:12-19`), `AddRequirement` and `RemoveRequirementIfPresent` already are, and the restore becomes one (D8).

The check the brief asks for: the model's `rollback_read` reader is the `tidy` program (`.tla:117-118`, `:190-193`). It is not a read-only consumer: under any lock configuration it takes the project mutex (`UseProj`, `.tla:139`), and in the code `module tidy` writes `invowkmod.cue` and takes the project lock (D2). With the flipped base it would be serialised behind the rolling-back add, so `rollback_read` could no longer witness F10 and `mutantRestoreRemoveThenWrite` would stop being detected. The model therefore gets a read-only consumer: a program kind `read`, whose body is a named operator `ReadProg == <<St("ReadMod"), St("ReadLock")>>` (no `Early`/`Final`, so never `Acquire`, in every configuration), which replaces `TidyProg` as `rollback_read`'s second process (F10 commit, D12). The comment on `UseProj` ("by every operation including the reader") is rewritten to say the reader holds none. `TidyProg` has no other scenario, so in the F10 commit its operator, its program branch and its correspondence row are deleted, together with its `[triage] binding_gaps` entry (`manifest.toml:202`); its `[correspondence] unresolved_elements` entry already left in the refactor commit (D12, C0). Tidy's lock window is covered by the use-case lock-window test instead (D4). `ReadProg`'s row has no Go symbol (`-`, unbound by design), with the reason "read-only consumers (discovery, command runs, validate, audit) take no mutex and rely on atomic replaces".

### D8. Snapshot without following links; restore by atomic replace (item 4, F10)

`readFileSnapshot` uses `os.Lstat`. A snapshot is one of: missing; regular (bytes and permission bits); symbolic link (its `os.Readlink` target); other (directory, device: restored as today, by doing nothing). `restore`:

- missing: `os.Remove`, ignoring "not exist" (as today, `use_cases.go:315-319`);
- regular: `fspath.AtomicWriteFile(path, data, perm)`;
- link: if the path is still a link with the same target, nothing; otherwise create a link with that target under a random name in the same directory and rename it over the path (one atomic replace). A failure is a restore error (for example Windows without symlink privilege);
- other: nothing.

The restore's two primitives are seams on the `Resolver`, carried into each snapshot it takes: the regular-file writer (default `fspath.AtomicWriteFile`) and the link creator (default `os.Symlink`). The F10 test and the lock-restore failure test (D9) use the writer; the failed-link-restore test uses the link creator.

The F10 Go test (`TestConcurrentEdits_F10RestoreReplacesFile`) must see the restore's own effect on the file, not the add's earlier save, which already renames over the lock (`LockFile.SaveIfChanged` → `fspath.AtomicWriteFile`). So it seeds the duplicate-add situation: the lock already holds the exact entry the add resolves and `invowkmod.cue` already requires that module. The add's save is then skipped (the test asserts `lockWritten == false` first, so it cannot pass vacuously), `AddRequirement` fails as a duplicate, and the rollback restores the lock. The test records `os.Stat` of the lock before the command and checks after it that the content is the snapshot's and that `os.SameFile` with the recorded stat is false: only the restore can have replaced the file, a rename produces a new one, and an in-place `os.WriteFile` keeps the same file and fails the test on Linux, macOS and Windows (task 2.2's negative check). No check reads through the writer seam: truncation happens inside the writer, so such a check could not fail. This is the `Restore` row's binding; the row stays model-only for the interleaving itself, because the rename has no observable intermediate state to replay.

The dangling-link test (`TestAddModuleDependencyRollbackKeepsDanglingInvowkmodLink`) fails on the base: `os.Stat` reports not-exist and the restore deletes the link. ### D10. CLI after a rollback (items 2 and 5)

`runModuleRemove` prints `Removed <namespace>` lines only when no declaration has a rollback. ### D11. Requires entries by byte span (item 3 and OQ-A)

The editor stops working on lines for matching. A small scanner walks the `requires` block from the `requires:` field to its matching `]`, skipping quoted strings (with escapes) and `//` comments, and returns each top-level `{…}` entry as a byte span, plus the byte offset of the closing `]`. Fields are read from the span: a `git_url:` or `path:` label at depth 1, outside strings and comments, followed by a string literal (parsed with the existing `strconv.QuotedPrefix` logic). Add's duplicate check and remove's match both use it. `findRequiresBlock` gets the same string- and comment-awareness.

Removal: when the entry's span starts and ends on lines that hold nothing else but whitespace and a trailing comma, the lines are removed exactly as today (so the multi-line layout `module add` writes produces byte-identical output; existing tests pin it). Otherwise the span, one following comma and the spaces up to the next token are cut from the text. The last entry still removes the whole `requires` field as today (`invowkmod_edit.go:130-148`), whether the block spans lines or one line.

Insertion (OQ-A, brought into scope by revise-1, same commit as item 3): when the line holding the closing `]` has only whitespace before it, the entry lines are inserted before that line as today (byte-identical output for the multi-line layout). Otherwise (a one-line block, or `}]` on one line) the text is split at the `]` offset: the text before it, a `,` when the last entry has no trailing comma, a newline, the formatted entry lines (`formatRequiresEntry`, `:269-283`), a newline, then `]` and the rest of its line. Every add or remove that changes a one-line block must leave a file that `invowkmod.ParseInvowkmod` accepts, with the remaining entries unchanged; the tests parse every result. The OQ-A test (`TestAddRequirementOneLineBlock`) fails on the base, where the entry lands before `requires:`.

## Risks / Trade-offs

- [Different cache roots] Two processes with different `INVOWK_MODULES_PATH` use different `locks` directories and do not exclude each other on a shared project. → Documented as a known limit; the module cache is per user, and pointing two runs at different caches already gives them different module copies.
- [Case-insensitive volumes on macOS] `EvalSymlinks` keeps the case it is given, and `os.Getwd` can return `$PWD`'s spelling, so `cd ~/Proj` and `cd ~/proj` give two project lock names on APFS. → Windows is normalised by `GetFinalPathNameByHandle`. On macOS this is a known limit (MA2, accepted in revise-1), stated in the docs; the follow-up keys the project lock on the directory's file identity (device and inode, or volume serial and file index) and is listed in the result.
- [Network file systems] `flock` on NFS may be local-only or emulated. → Documented as an advisory lock between invowk processes on one machine.
- [Remove and empty sync, tidy and vendor create the cache root] See D5 and MA1. → Use-case tests that lock get a temporary cache root (D2), so the suite never writes into `~/.invowk/modules`; an unwritable root fails with an actionable error (D5).
- [Longer runs] A command now waits for another on the same project, up to 5 minutes. → The waiting line says why; Ctrl+C ends it.
- [Link restore on Windows] Recreating a link can fail without symlink privilege. → Reported as an incomplete rollback with the error (exit 1), never silently skipped.
- [Shared formal files with W2] W2 also edits `formal/README.md` rows, the manifest and the formal-bindings ledger. → W1a merges first; W2 rebases and redoes its refresh (brief "Overlap").
- [W3 rows] W1a changes the binding cells of W3's `RemoveProg`, `WriteLock` and `LockFile.Save` rows and removes the `RemoveProg` unresolved pair (D12). → Reported in the result so W3 retargets only notes and lines.
- [Exit-status change] Scripts that ignored a rolled-back add now fail. → Called out as BREAKING with migration notes; the run did not change the project.
