## Context

See proposal.md for the motivation. Current state, at origin/main e14950aa with u-root v0.16.0 (paths below `pkg/` are in the u-root module):

- **Operand checks.** `Registry.Run` calls `validateUrootCommandPathArgs` (`internal/uroot/registry.go:106`), which, under a validating context, calls `urootCommandOperands` (`internal/uroot/registry_operands.go:139`). That function parses the arguments as the built-in does, resolves each operand with its hook (`resolveUrootArgs`, `:284`; tar's `-f`/`-file` values at `:289-299`) and checks `gzip`'s output paths (`:161-165`, `checkGzipOutputPaths` at `:380`). The `gzip` check resolves each derived path with `hc.ResolvePath` and does not hand it on: `gzip` derives it again from the same resolved operand (`:374-379`). That is the model this change follows.
- **The resolver.** `HandlerContext.ResolvePath` calls `ValidatePath` (`internal/uroot/handler.go:74-82`), which the runtimes set to `virtualPathValidator.validate` (`internal/runtime/sh.go:543`, `internal/runtime/lua.go:678`). `validate` resolves the path physically through every link and junction to the deepest existing ancestor and joins the missing components (`normalizeExistingOrParent`, `internal/runtime/virtual_policy.go:415`), then, unless access is `full`, checks it against the allowed roots and refuses with `virtual path denied` (`:308-322`). Under `full` access it still resolves, with fallbacks instead of errors (`normalizeVirtualPathForAccess`, `:444`).
- **The validating context is set under both access modes**, so `urootCommandOperands` runs under `full` access too. `HandlerContext` has no field that says which mode is active (`internal/uroot/handler.go:28-46`).
- **The wrappers hand their calls to u-root unchanged** (`internal/uroot/cp.go:34-36`, `internal/uroot/tar.go:32-34`, `runUpstream` at `internal/uroot/wrapper.go:47`), with the handler's directory as working directory (`:36-41`). The operands they receive are the resolved, absolute paths.

### What `cp` does with its operands (`pkg/core/cp/cp.go`)

- Destination: `os.Stat(to)` decides whether `to` is a directory (`:287-290`); more than one source with a non-directory `to` is an error before anything is copied (`:291-293`). For each source, the destination is `to`, or with a directory `to`, `filepath.Join(to, filepath.Base(file))` (`:303-307`).
- Without `-r`: `Copy` (`:93`) stats the source, following links unless `-P` (`:77-82`), runs the pre-callback, which skips a directory (`:199-202`) and an existing destination that is the same file (`:204-218`), then copies.
- With `-r`: `CopyTree` (`:119`) walks the source with `filepath.Walk` (`:123`), which does not descend into links, and calls `Copy(path, filepath.Join(dst, rel))` for every entry (`:128-132`). `filepath.Walk` reads a directory's names before it calls the walk function for that directory (`$GOROOT/src/path/filepath/path.go:349-350`).
- Destination calls: `os.MkdirAll(dst, perm)` for a directory (`:140`), `os.OpenFile(dst, O_RDWR|O_CREATE|O_TRUNC, perm)` for a regular file (`:170`), `os.Symlink(target, dst)` for a link under `-P` (`:145-152`); the pre-callback's `os.Stat(dst)` (`:204`). All but `Symlink` follow a link at `dst`; `MkdirAll` also follows links on the way. No chmod, chown or chtimes.
- Source calls: `os.Stat` or, with `-P`, `os.Lstat` (`:77-82`), `os.Open` (`:164`), `os.Readlink` (`:148`). Without `-P`, an entry that is a link is followed by `Stat`: a link to a file is read (`:164`), a link to a directory becomes `MkdirAll(dst)` and is not descended. On Windows a junction's `Lstat` mode is `ModeIrregular`, not a directory or link (`$GOROOT/src/os/types_windows.go:193-227`): the walk does not descend it, and `Stat` follows it.
- Errors: a failed source keeps the loop going; only the last error is returned (`:302-318`).

### What `tar -x` does (`pkg/core/tar/tar.go`, `pkg/tarutil/tar.go`)

- `-f` is required (`core/tar/tar.go:107-109`); exactly one operand with `-x` (`:101-103`); `-c`, `-x` and `-t` exclude one another (`:92-100`). The archive path is `ResolvePath(file)` (`:122`; `pkg/core/base.go:55-60` only joins the working directory), opened with `os.Open` (`:145`). Standard input is never read as the archive: `unixflag.ArgsToGoArgs` drops a lone `-`, so `-f -` leaves `tar` without its operand (a usage error), and `--file=-` names a file called `-`.
- `ExtractDir` (`tarutil/tar.go:73`): `os.Stat(dir)`, and `os.Mkdir(dir)` when it is missing (`:83-90`); then, for every entry that passes the filters (`:92-96`; the only filter is `-v`'s, which prints and passes every entry, `core/tar/tar.go:117-119`), `createFileInRoot` (`tarutil/tar.go:202`).
- `createFileInRoot`: `upath.SafeFilepathJoin(rootDir, hdr.Name)`, skipping the entry on error (`:204-210`; `pkg/upath/safejoin.go` refuses absolute names and names that clean to `..`). It switches on `hdr.FileInfo().Mode() & os.ModeType` (`:212`): links, devices and every other type return an error, which stops the extraction (`:213-245`); mode `0` is `os.Create(path)` plus a copy (`:217-228`); `ModeDir` is `os.MkdirAll(path, perm)` (`:230-233`). Both then call `os.Chmod(path, perm)` (`:247`). `hdr.FileInfo().Mode()` comes from the header's type flag and mode bits (`$GOROOT/src/archive/tar/common.go:563-602`), so a hard-link entry is a regular file.
- **Every call on a destination:** `os.Stat` and `os.Mkdir` on the extraction directory, and `os.Create`, `os.MkdirAll` and `os.Chmod` on each entry path. All of them follow links. There is no chown, chtimes, link, symlink, mknod, rename or remove.

## Goals / Non-Goals

**Goals:**

- Under `restricted` access, every path `cp` and `tar -x` create, write, create directories at or change the mode of, and every source link `cp` follows, is resolved in full and checked against the allowed roots before the command runs; one denial refuses the whole command.
- The prediction is complete: what u-root touches at run time is a subset of what was checked, given the tree does not change in between (D9).
- `full` access is unchanged, and so is every other built-in.

**Non-Goals:**

- No invowk-side reimplementation of `cp` or `tar`; u-root still does the copying and extracting.
- No change to the operand checks of #198, to `tar -c` or `tar -t`, or to the resolver.

## Decisions

### D1. Where the checks run

A new file `internal/uroot/registry_derived.go` holds `checkUrootDerivedPaths(ctx, hc, name, resolved)`, called from `urootCommandOperands` right after the `gzip` check (`registry_operands.go:161-165`), on the resolved arguments, before the rebuild. `urootCommandOperands` gains a `ctx` parameter (from `validateUrootCommandPathArgs`, `registry.go:119`), so the walk and the archive read stop on cancellation. Like the `gzip` check, the checked paths are not handed on: u-root derives them again from the same resolved operands. This is how the main spec's "Checked and reported virtual paths are the resolved path" applies to derived paths: the operands u-root receives are the resolved paths the validator checked, each derived path is checked in its resolved form, and D5 and D6 keep what u-root derives at run time equal to what was checked. Each derived path is checked with `hc.ResolvePath`, which is the full resolution plus the allowed-root check: a dangling link whose target lies outside is refused, missing components below real directories are accepted, and missing components below a link to an outside directory are refused.

Alternatives: checking inside the `cp` and `tar` wrappers' `Run` would also cover direct `Run` calls, but would parse the arguments a second time and split the operand policy across two places; the operand checks already live only in the registry path.

### D2. Gating: restricted access only

`HandlerContext` gains `FullAccess bool`, documented as set by the embedding runtime when access is `full`. `tryUrootBuiltin` (`internal/runtime/sh.go:541-545`) and `runVirtualUtility` (`internal/runtime/lua.go:669-680`) set it from a new method `virtualPathValidator.fullAccess()`, in a new file, so `validate` and `validateNoFollow` stay untouched. `checkUrootDerivedPaths` returns at once when the flag is true. The zero value checks: a validating context that does not set the flag (a future embedding, or a test) gets every derived-path check and every prediction refusal, so forgetting the flag fails closed. Existing `internal/uroot` tests with a validating context therefore run the checks too; a test that asserts u-root's own behaviour on a shape D5 or D6 refuses sets `FullAccess`.

Alternatives: an opt-in flag (`CheckDerivedPaths`) was rejected because its zero value runs no check, so an embedding that sets the validators but forgets the flag would skip every derived path. Running the checks under both modes, as `gzip`'s are, was rejected: under `full` access `validate` never refuses (`virtual_policy.go:313-315`), so the checks would only cost a tree walk or an archive read, and the prediction refusals of D5 and D6 must not apply there. Passing the access mode as a string was rejected: `internal/uroot` needs one bit.

### D3. Enumerate, then check

Two enumerators, `cpDerivedPaths(ctx, resolved, visit)` and `tarDerivedPaths(ctx, resolved, visit)`, compute what u-root will touch, in u-root's order, and call `visit` once per path with its use (write a file, create a directory, create a link, change the mode, follow a source link) and, for `cp`, the source entry and its operand. The production visitor resolves each path with `hc.ResolvePath` and applies D5's rules; the differential test (D10) collects the paths instead. Both enumerators stream: `cp` keeps only the resolved source operands with their file identities, a per-directory cache of the identity checks of D5 rule 2, and, for D5 rule 3, the first link creation and whether another destination was yielded; `tar` keeps nothing between entries.

### D4. The paths `cp` derives

From the resolved arguments, as `cp.go:279-313` computes them: `recursive` is the last value of `-r`, `-R`, `--recursive` and `--RECURSIVE`, `noFollow` of `-P` and `--no-dereference` (`urootArgs.boolOption`, `registry_operands.go:350`). With fewer than two operands, or more than two and a `to` that is not a directory, the enumerator yields nothing: u-root fails before copying. Otherwise, for each source, `dst` is computed as at `:303-307`, with `os.Stat(to)` as at `:287`.

Every source operand after the first is first checked against D5 rule 1 (it must exist); a missing first source yields nothing, because u-root fails on it and goes on with the next source. A resolved source operand is a physical path that holds no link (the operand hook follows every link, `registry_operands.go:331-338`), so `Copy` never sees the operand itself as a link.

- Without `-r`: a source that is a directory yields nothing (`:199-202`); otherwise `dst` is a file write. Since the operand holds no link, `cp` without `-r` creates no link, with or without `noFollow`.
- With `-r`: the enumerator walks the source with `filepath.Walk`, as `CopyTree` does, and for each entry computes `filepath.Join(dst, rel)` with `rel` from `filepath.Rel(src, path)` (`:128-132`). The use follows the entry's type as `Copy` sees it: `Lstat` with `noFollow`, `Stat` otherwise (`:77-82`): a directory is a directory creation, a regular file a file write, a link (with `noFollow`) a link creation. Without `noFollow`, every entry whose `Lstat` type is neither a directory nor a regular file (a symbolic link, or on Windows a junction or another reparse point) is also yielded as a followed source link, resolved and checked, whether it leads to a file or to a directory: `Stat` reads its target either way.

**When `Copy` fails.** The enumerator never ends a source earlier than u-root's `CopyTree` does; where the two could differ it yields more, which fails closed (Risks):

- A walk error (the walk function receives a non-nil error: a directory whose names cannot be read) ends that source's enumeration, as u-root's walk function returns that error and ends `CopyTree` (`:123-126`). The next source continues, as at `:303-313`. A missing walk root yields nothing, because u-root's walk fails on it at once: for the first source that is u-root's own error, and a later missing source D5 rule 1 refuses first.
- An entry whose `Stat` fails without `noFollow` (a dangling link, or a link in a cycle) makes u-root's `Copy` return the error and end the walk (`:97-99`). The enumerator first yields the entry's followed-source-link check (the resolver refuses a dangling link whose target lies outside), then yields its destination as a file write, and continues with the next entry.
- An entry of a type `copyFile` does not support (`:154-159`: a named pipe, a socket or a device, through `Stat` without `noFollow` or `Lstat` with it, and on Windows a junction under `noFollow`, whose `Lstat` mode is `ModeIrregular`) makes u-root end the walk after the pre-callback. The enumerator yields its destination as a file write and continues.
- The pre-callback's `ErrSkip` (a source directory without `-r`, the same file, a refused `-i` prompt, or a destination `Stat` error other than "does not exist", `:199-227`) makes `Copy` return nil, so `filepath.Walk` still descends into a skipped directory. The enumerator does not evaluate the pre-callback: it yields every such entry and its descendants as if they were copied.

With `noFollow` (`-P`), a source link is not followed and its target is not checked; whether the command may create the link is D5 rule 3 (maintainer decision 4).

### D5. Keeping the `cp` prediction exact

A prediction made before the run is complete only if the run cannot change what it reads, walks or resolves. `cp` never removes or renames an entry, `os.Symlink` fails where an entry already exists, and a directory or regular file that `cp` creates is seen by a later resolution as it is. The run can therefore change the prediction in three ways only, and under `restricted` access each is refused before anything is written (D7):

1. **A source operand after the first that does not exist (`errCpSourceMissing`).** With several sources, an earlier source can create a later source, or a path on the way to it, before u-root reaches that source, so neither what the later source reads nor the destinations its walk yields could be known in advance. The visitor refuses every source operand after the first whose resolved path does not exist (`os.Lstat` fails) when the check runs, with or without `-r`. Such a source fails in u-root anyway unless an earlier source creates it, so the refusal only moves the error before the first write. The first source operand has no earlier source, so nothing the command writes can create it: when it is missing, the enumerator yields nothing for it and u-root keeps its own "no such file or directory" error, so a typo in a lone source still gets that plain error. Every remaining source operand is a physical path whose components exist and hold no link, and it stays the same path during the run, whatever its spelling, because `cp` neither removes nor renames.
2. **Writing into a source tree (`errCpIntoSource`).** u-root reads a directory's names before it copies the directory itself (Context), so entries written into a directory of a source tree that is not read yet would be walked and copied too, at paths the prediction did not cover; this holds for the source being copied and for a later source of the same command. With `-r`, the visitor refuses a destination when its resolved path, or one of that path's existing ancestors, is the same file (`os.SameFile`) as any resolved source operand of the command: the destination is then at or below that source, whether it is the source itself, a path below it, or another spelling of either. The exception is a destination that, as u-root builds it and read without following its last component (`os.Lstat`), is the same file as the source entry it copies: then u-root's same-file check (`cp.go:204-218`) skips it, or, with `-P` on a link, `os.Symlink` fails on the existing entry, and nothing is written. So `cp -r d d` and `cp -r d d/sub` are refused (a host `cp` refuses them as well), and so is a multi-source command in which an earlier source writes into a later one (`cp -r a/s d/s d` with `d/s` existing); `cp -r d .` in `d`'s parent directory runs. The identity test is exact: a destination's missing components are created by the run as new entries, so they cannot be an existing source, and a link the run creates among them is never crossed by a later destination (rule 3); the existing part of the resolved path holds no link, so its ancestors are its real parents; and a component that is another spelling of an existing entry is found by `os.Lstat`, so it is part of that existing part. The checks are cached per directory, so a walk costs one `Lstat` per new directory.
3. **A link the command creates, next to any other destination (`errCpLinkWithOtherDestinations`).** With `-P -r`, `cp` creates links (`cp.go:145-152`). A later destination of the same command (of a later source, or later in the same walk) that the destination volume treats as that link, or as an entry below it, would resolve through the link at run time, but the link did not exist when the prediction resolved that destination. Which names a volume treats as one entry cannot be told from their spelling: letter case, Unicode normalisation and short names differ by volume and even by directory, and a name on an ancestor the same command creates is not known in advance either. So this rule compares no names. Under `restricted` access the visitor refuses the whole command when it yields a link creation and any other destination: another link creation, a file write or a directory creation, from the same or any other source operand. It records the first link creation and whether another destination was yielded, and when both hold it refuses with the resolved path of that link, before u-root runs. A command whose only destination is the one link it creates is not refused by this rule, because no other destination can cross that link. With `-r`, each source's top destination directory (`MkdirAll(dst)`) is itself a destination, so every `cp -P -r` whose sources hold a link is refused. Without `-P` `cp` creates no link, and neither does `cp -P` without `-r`, because the resolved operand holds no link (D4): `cp -P lnk d` copies the link's target, which the operand check resolved and checked, to `d/<target's base name>`, as before this change. The rule does not apply to those commands; without `-P` the source links are followed and checked (D4).

Outside these cases `cp` reads only source operands that exist and do not change, never writes into a tree it has yet to walk, creates directories and regular files, which a later resolution sees as they are, and creates a link only as its one destination, so the predicted resolution matches the run.

Alternatives: comparing resolved path strings byte for byte was rejected, because the resolver keeps the given spelling of existing components on macOS and joins missing components as written, so two spellings of one entry compare unequal on case-insensitive and normalisation-insensitive volumes. Refusing only a source operand at or below an earlier destination, instead of every missing source operand, would depend on that comparison too. Resolving a later destination through the recorded link's target would allow more commands but duplicate the resolver's link walk in `internal/uroot`. Refusing every multi-source `-P -r` would not cover the single-source case of rule 3. Predicting from spelling which names the destination volume treats as one entry (a key that folds letter case and normalisation) was rejected: each alias class it missed (short names, a name on an ancestor the command creates, unusual case-folding tables) would need another special case, whereas a rule that compares no names closes the whole class. Refusing every overlap between two sources' destinations would refuse ordinary merges of same-named trees (`cp -r a/s b/s d`), which stay allowed.

### D6. The paths `tar -x` derives

From the resolved arguments: the enumerator runs only when `-x`/`--extract` is set, `-c` and `-t` are not, there is exactly one operand and an archive (`core/tar/tar.go:92-109`); otherwise u-root fails before extracting, and it yields nothing. The archive is the last `-f`/`--file` value (`urootArgs.stringOption`, `registry_operands.go:364`), already resolved. Then:

- **Archive type.** The archive is read twice: once here and once by u-root. Under `restricted` access an archive whose resolved path exists and is not a regular file is refused (`errTarArchiveNotRegular`), because a named pipe or a device would not give the second read the same data. A missing archive yields nothing: u-root's `os.Open` reports it. Standard input cannot be the archive (Context), so no buffering is needed.
- **Extraction directory.** It is the resolved operand, already checked. When it exists and is not a directory, the enumerator yields nothing (`tarutil/tar.go:88-90`).
- **Entries.** For each header from `archive/tar`'s reader: the path is `upath.SafeFilepathJoin(dir, hdr.Name)`, the function u-root calls; an error skips the entry, as at `:204-210`. The type is `hdr.FileInfo().Mode() & os.ModeType`, as at `:212`: `0` yields a file write plus a mode change, `os.ModeDir` a directory creation plus a mode change, and any other type ends the enumeration, because u-root stops there. A read error ends the enumeration: u-root's own read stops at the same entry. The `-v` filter passes every entry, so no entry is filtered.

`tar` creates no links (`:213-215`), so every link a later entry could cross exists when the enumerator resolves it; the prediction needs no rule like D5's. The two type switches (u-root's and the enumerator's) are the one piece of logic written twice; the differential test (D10) covers both arms and the stop.

### D7. Errors

A path the resolver refuses returns the resolver's error unchanged (`virtual path denied` and the resolved path), which `Registry.Run` wraps as `[uroot] cp: ...` or `[uroot] tar: ...` (`registry.go:107-109`), as for operands. The four prediction refusals are new sentinel errors in `internal/uroot`, so tests can match them with `errors.Is`. Their messages begin with `virtual path denied`, the text every other refusal of a restricted path carries (maintainer decision 1), followed by the reason, and the returned error names the resolved path: `errCpSourceMissing` ("virtual path denied: cp source does not exist"), `errCpIntoSource` ("virtual path denied: cp destination is inside a source tree"), `errCpLinkWithOtherDestinations` ("virtual path denied: cp -P would create a link next to other destinations") and `errTarArchiveNotRegular` ("virtual path denied: tar archive is not a regular file").

### D8. virtual-lua

`invowk.cmd` and `invowk.capture` run built-ins through `runVirtualUtility` (`internal/runtime/lua.go:533-545`, `:656`), which builds its own `HandlerContext` (`:669-680`). Setting `FullAccess` there from the same validator (D2) gives Lua the same checks. One test each for `cp` and `tar -x` through `invowk.capture` (maintainer decision 5).

### D9. The window between check and use

The checks run before u-root does, and u-root uses the paths afterwards. In between, only the script's own concurrent work can change the tree or the archive: its background jobs, the other stages of a pipeline the command is part of (mvdan/sh runs them concurrently), and allowed host binaries started in either way. A regular-file archive (D6) cannot change by being read. The only change `tar -x` itself can make to its archive is an entry whose destination resolves to the archive (or to a hard link of it): `os.Create` (`tarutil/tar.go:218`) truncates it, and `archive/tar`'s later reads reach the end of the file, so fewer entries are extracted than were predicted and checked, which fails closed. This window is accepted, as it is for every other built-in's operand check, and is not described in the user docs (maintainer decision 2).

### D10. Tests

- **Unit (`internal/uroot`)**, new `registry_derived_test.go`: a test tree with the validator's fixed root `base/root` and a sibling `base/outside` that is outside that root, like `gzipTestTree` (`registry_operands_gzip_test.go:18`). The fixed-root validator of `registry_operands_test.go:22-61` compares paths lexically, so a new test validator in the same package resolves links physically (`filepath.EvalSymlinks` of the deepest existing ancestor, following a dangling final link with `os.Readlink`) before the root check. Each row, under a restricted context (`FullAccess` false: refused, `errors.Is` the denial or the prediction sentinel, the message contains `virtual path denied`, and every entry below `base` unchanged, by `treeSnapshot`) and under a full-access context (`FullAccess` true: u-root's own behaviour, unchanged):
  - `cp f d` and `cp f g d` with `d/f` a live and a dangling link out of the root; `cp -r src dst` and `cp -P -r src dst` with `dst/src/x` a file link, `dst/src/sub` a directory link and `dst/src` itself a link out of the root; `cp -r src dst` with a source link to a file and to a directory out of the root, and with a dangling source link whose target lies out of the root; `cp -P -r` with a source link out of the root (refused by D5 rule 3 under restricted access, copied as a link under full access); `cp f dl` with `dl` a directory link out of the root (refused by the existing operand check); links inside the root on every shape that creates no link, allowed.
  - The D5 refusals, each on every platform: rule 1, a later source missing when the command starts, without and with `-r` (`cp f missing d`; `cp -r a/s d/s/x d` with `d/s` missing; `cp -P -r a/s d/s/l/f d` with `d/s` missing and `a/s/l` a link out of the root), and, not refused, a missing first source (`cp missing d` with u-root's own "no such file or directory" error, and `cp missing f d` copying `f`, each with the same result as under full access); rule 2, `cp -r d d`, `cp -r d d/sub`, and an earlier source writing into a later one (`cp -r a/s d/s d` with `d/s` existing, and `cp -r a/s d/s/x d` with `a/s/x` and `d/s/x` existing, where an earlier destination equals the later source operand); rule 3, the multi-source shape `cp -P -r a/s b/s d` with `a/s/l` a link and `b/s/f` a file, and the single-source shapes `cp -P -r src dst` with `src` holding a link and a file and with `src` holding only a link (the directory `dst/src` is the other destination), each refused with `errors.Is` the rule 3 sentinel and nothing below `base` changed, links inside the root included; `cp -P lnk d` with `lnk` a link to a file inside the root, not refused, with the same result as under full access (the target copied under its own base name, no link created); and the allowed shapes `cp -r d .` and `cp -r a/s b/s d` (same-named trees merged, no link).
  - On a case-insensitive volume only (macOS and Windows; the test probes the temporary directory by creating an entry and reading it back with another case, and skips otherwise), subtests named after the behaviour: a destination directory that names a source by another case (`cp -r b B` and `cp -P -r a/s b B` with `a/s` holding no link, refused by rule 2's identity test).
  - `Copy` failures (D4): a dangling source link without `-P` whose target lies inside the root (u-root's error, nothing refused), a named pipe in the source tree (Unix), and on Windows a junction in the source tree under `-P` (`ModeIrregular`); each with the same result as under full access, and entries after the failing one still checked (a destination link out of the root after the failing entry is refused).
  - `tar -x` with `ex/t` a live and a dangling file link (file entry `t`, mode 0777), `ex/l` a directory link (directory entry `l` with mode 0777; file entry `l/f`; entries `l/a/b` and `l/a/b/f`); entries with absolute and `..` names skipped; a link entry stopping the extraction; a hard-link entry extracted as an empty regular file; a named-pipe archive refused (Unix); `-f -` failing with u-root's usage error and `--file=-` reading the file `-`, neither reading standard input; links inside the root, allowed.
  - Gating: with a validating context and `FullAccess` true, no derived path reaches the validator (a recording validator); with a validating context that leaves `FullAccess` at its zero value, the derived paths do reach it.
- **Differential (`internal/uroot`)**, `TestUrootDerivedPathsMatchUpstream`: on link-free trees in a temporary directory, for every case, either the restricted visitor (with a validator that accepts every path) refuses the command with a prediction sentinel, or the paths the enumerators yield equal what u-root touches when it runs. ## Risks / Trade-offs

- [A tree walk and an archive read before every restricted `cp -r` and `tar -x`] → Both stream (D3); `archive/tar` skips entry data with `Seek` on a file. `full` access pays nothing (D2).
- [A prediction that misses a path would leave that path unchecked] → The enumerators reuse u-root's own join (`SafeFilepathJoin`), `filepath.Walk` and the same `Rel`/`Join`; D5 refuses the three shapes the run itself could change, comparing by file identity (rule 2) or comparing no names at all (rule 3), never by spelling; the differential test compares prediction and run, including the links `cp -P -r` creates, and fails on a seeded miss.
- [The prediction checks more than u-root touches (a source skipped by `-i`, the entries after a failing copy)] → It fails closed: such a command may be refused although it would not have written there. Only `restricted` access is affected.
- [Restricted `cp -r` without `-P` now refuses a source link to a directory outside the roots, which u-root copies as an empty directory] → Following the link stats its target; under `restricted` access every followed path is checked. Accepted by the maintainer.
- [Restricted `cp` refuses the whole command when a source operand after the first does not exist (D5 rule 1), where u-root would copy the other sources and then report the missing one] → The refusal comes before the first write; a missing first or only source keeps u-root's own error; only `restricted` access is affected.
- [Under the default `restricted` access, `cp -P -r` of a tree that holds a link is refused (D5 rule 3), because the tree's top directory is a second destination] → Accepted by the maintainer: a rule that compares no names closes the whole class of names a volume treats as one entry, where name prediction needed a new alias class every round. No sample, testscript or doc in the repository uses `cp -P`; `access: "full"` keeps u-root's behaviour.
- [Existing tests and future embeddings that set a validator now get the derived-path checks by default (D2)] → Intended: the zero value of `FullAccess` checks, so a missing flag fails closed; tests of u-root's own behaviour set `FullAccess`.
- [A u-root bump changes `cp` or `tarutil`] → The differential test and the type-switch cases fail until the enumerators match again; the `uroot` skill names the enumerators next to the `FlagInfo` parity rule.
- [The window between check and use] → Accepted (D9).

## Migration Plan

None. Scripts whose paths stay inside the allowed roots behave as before. Rollback is a revert of the two code and docs commits.

## Maintainer decisions

From the maintainer brief (2026-11-24; decisions 83, 88, 89, 93 and 94 of the program notes):

1. Check before use, reusing the existing resolvers: before any write, `cp` and `tar -x` compute every path they will create, write, create directories at or change the mode of, and each is checked with the full resolution and the allowed-root check; without `-P`, `cp` also checks the followed target of every source link; any denial refuses the whole command with `virtual path denied`; `full` access is unchanged (D1-D6). The `tar` destinations use u-root's own join and skip rules; the list of every call on a destination is in Context; the archive cannot be standard input, and a non-regular archive is refused under `restricted` access (D6).
2. The window between check and use is accepted and documented here only (D9).
3. No invowk-side reimplementation of `cp` or `tar`. The brief's "split if a path cannot be predicted" is replaced by decision 8: the shapes that cannot be predicted are refused under `restricted` access, so every remaining path is predictable and the change stays one change.
4. `cp -P` does not follow a source link and does not check its target. "A copied link stays a link" is narrowed by decision 9: under `restricted` access `cp` creates a link only when that link is the command's only destination, and refuses a copy that would create a link next to other entries; `access: "full"` keeps u-root's behaviour. A link named as a `cp` operand is resolved by the operand check (D4), so `cp -P lnk d` copies the link's target and creates no link, as before this change.
5. virtual-lua gets one `invowk.capture` test each for `cp` and `tar -x` (D8).
6. Tests as in D10: both access modes, outside trees that are really outside the roots, the differential test, Windows junction variants, and a negative control on e14950aa.
7. Pushed text uses hardening wording only (D12).

From the revise brief (2026-11-24, second spec round):

8. Refusing the shapes that cannot be predicted under `restricted` access is confirmed: D5 rules 1 to 3 and the non-regular archive of D6. It fails closed and touches only `restricted` access.
