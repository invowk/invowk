# CI Workflows and Gate Tooling

- Step-level `env:` applies to that step only. Promote a variable used by several steps to job-level `env:` (or repeat it); otherwise a `set -u` report step can fail after the real build or test step succeeded.
- Write generated reports under ignored artifact directories unless they are intentional release or docs assets. Before committing a workflow or tool change that moves reports, check with `git ls-files` that root-level outputs (`report.json`, `go-mutesting-summary.json`, `go-mutesting-agentic.json`, `go-mutesting-gitlab.json`, `go-mutesting-report.html`) are not tracked.
- `lint.yml` is required: it carries the ruleset-required `goplint consumer gates` check, and its `pull_request` trigger deliberately has no path filter. Keep it that way. Its `script tests (worktree-safety gate)` job runs `make test-scripts` on every PR and is meant to become a required check: keep the job name stable, and do not add `make test-scripts` steps to `ci.yml`. Every CI `make test-scripts` step first exports `INVOWK_TRIAGE_BASE` from `scripts/ci-triage-base.sh` in the same step (a depth-1 checkout has no `origin/main`).
- `release.yml`'s `test` job mirrors `ci.yml`'s: change the matrix, the test, engine-setup and matrix-gated steps (their `if`, `INVOWK_TEST_*` env at any level, and `go test` packages and flags) in both. `scripts/check-ci-release-parity.py` (run by `make test-scripts`) fails on drift; record an intentional difference in its exception tables with the reason.
- `formal-verification.yml` carries the ruleset-required `Models, golden vectors, and correspondence` check (required since 2026-11-14, pinned to the GitHub Actions app). It must report on every PR, including docs-only ones (it skips its heavy steps via `scripts/formal.py affected`); never add a path filter that stops it reporting.
- `mutation-testing.yml` is manual dispatch only; never make it a PR or scheduled gate.
- CodeQL stays on the advanced setup (`codeql.yml`, with `go-version-file: go.mod` for Go). Never enable GitHub's default CodeQL setup.
- Pins: `.agents/rules/version-pinning.md`. Workflow inventory and pre-commit hooks: `.agents/runbooks/quality-gates.md`.

## Dependabot merge gate

- `dependabot-gate.yml` runs on `workflow_run` of the workflows whose checks it requires, so it always executes main's copy of itself and of `scripts/dependabot-gate.py`. Never give it a `pull_request_target` trigger, and never check out or run pull request code in it.
- The script decides `merge` or `hold` from read-only API calls and fails closed. The decision is a pure function of one JSON snapshot; the list in the script's docstring is the authority. In short, `merge` needs all of:
  - a pull request by `dependabot[bot]` on `main` from this repository, open, not a draft, without conflict and without a `hold` or `do-not-merge` label;
  - one verified Dependabot commit that is the head the triggering run tested, and a head that is not behind `main` (the ruleset does not require up-to-date branches, so GitHub never reports "behind");
  - gomod or npm files only (GitHub Actions updates never merge), and a gomod update that changes `go.mod`;
  - file contents the script compares itself, base against head, because nothing binds Dependabot's commit metadata to the files. `go.mod` may change requirement versions only; `website/package.json` only the ranges of dependencies the metadata names. Each version step is classified by the script: a major, a downgrade, a pre-release, a pseudo-version, `+incompatible`, a minor bump of a 0.x version, any 0.0.z version and an added or removed Go requirement all hold, except under the two relaxations below. The metadata's update types must be semver-patch or semver-minor as well. A carriage return in any of these files holds;
  - a lockfile that binds what npm installs: an npm update must change `website/package-lock.json`, and every changed entry must be an installed package whose `resolved` is exactly the `registry.npmjs.org` tarball of the name in its key and of its version, with a sha512 integrity. An alias (a `name` field), a new install script, a version lower than the base's and a step to another major all hold, and every dependency the metadata names must be locked at exactly the named version. `main` has two alias entries (`react-loadable`, `react-helmet-async`): an update that changes anything in either one holds, except their graph flags (`peer`, `dev`, `optional`, `devOptional`, each absent or `true`) when every other field is as on `main`. A new alias, an updated aliased package and an entry that gains `name` hold;
  - nothing on the sync-pair deny list, named or changed as a side effect;
  - every check on the head commit green, except `Track Benchmarks`, and every required check of the ecosystem present and successful, including the Socket and SonarCloud checks;
  - for every required GitHub Actions check, Dependabot's own run of its workflow file: the newest `pull_request` run of that file, on this repository's branch, that `dependabot[bot]` started (by user id). A commit authored by the bot and signed by GitHub does not prove Dependabot pushed it. No one else may have started a `pull_request` run of a required workflow file on this repository's branch for the head, even one whose checks were superseded. Runs of a fork's pull request (anyone can open one with Dependabot's head commit, and a maintainer may approve its runs) are told by `head_repository.id` and neither hold nor count: their checks are skipped, even when `filter=latest` lists them in place of Dependabot's;
  - the required check looked up by name among the check runs of that run's own check suite (`filter=all`), each one a job of the run with the same id (`actions/runs/<id>/jobs?filter=all`). Only the run's latest attempt counts (a re-run keeps the suite and gives every job a new id). The job must have a runner and steps: GitHub files a check that a job creates through the API in the suite of one of the head's runs and lists it among that run's jobs, without a runner (the `JUnit Report (...)` checks were listed under `lint.yml` on #190), and such a check never counts. The run's conclusion, the check run's, the job's must be `success` and every step's `success` or `skipped`, and the head's `filter=latest` listing must show that job, and no other check outside a fork's runs, under the name.
- Two relaxations of the `go.mod` classification, approved by the maintainer on 2026-11-24. The verdict's `admitted` list, shown in the job summary, names the rule for each line it lets through:
  - `indirect-side-effect`: a requirement that is `// indirect` on every side where it exists and that the metadata does not name may be removed, may be added at a released or pseudo-version (unless another requirement has the same path apart from its `/vN` or `.vN` suffix), and may change to a released or pseudo-version that is strictly newer by semver precedence; a change to a pre-release holds, and a step to another major is admitted with the crossing named (`indirect-side-effect (crosses v0 to v1)`);
  - `allow-0x-minor`: a module under an `ALLOW_0X_MINOR` prefix (only `golang.org/x/`) that is not on the deny list may take a minor bump of a 0.x version, direct or indirect.
  - Neither lifts the deny list, `+incompatible`, a downgrade, a move between direct and indirect, or a pseudo-version, pre-release or 0.0.z version of a direct or named requirement. Widening either one (a new prefix, another kind of step) is a policy decision for the maintainer, never a fix for a held pull request.
- Expect about six in ten grouped Go updates to merge (10 of the 16 in the repository's history up to 2026-11; the strict rules merged 2). The rest hold on a direct pseudo-version, a module path migration or a major, which is the rule working, not a defect.
- No job that runs pull request code may hold `checks: write`, in any workflow a pull request can start (`pull_request`, `pull_request_target`, `workflow_run`, review and comment events): such a token can create a check with any name and PATCH the conclusion of any `github-actions` check run of the commit, and code the job runs can reach it even with `persist-credentials: false` (writable `_actions/`, post steps that get the token, passwordless sudo on hosted runners). `persist-credentials: false` is hygiene, not the control. `ci.yml` publishes its JUnit reports from the `test-report` job, which only downloads the test legs' XML and runs the pinned report action. The two exemptions, `benchmarks.yml`'s `bencher` and `benchmarks-upload.yml`'s `upload-fork-pr`, read pull request code only as a `docker build` context without `.git`; `scripts/test_dependabot_gate.py` checks that evidence and fails on any other such job.
- `GATE_MODE` is a constant in the workflow file, now `decide-only`: the job writes the verdict and its reasons to the job summary and stops. The move to `merge` is a reviewed PR that changes that line; never read the mode from a repository variable.
- Only in `merge` mode and after a `merge` verdict does the job mint the `invowk-dependabot-merge` App token (`vars.DEPENDABOT_MERGE_APP_ID`, `secrets.DEPENDABOT_MERGE_APP_PRIVATE_KEY`). The merge step first runs `dependabot-gate.py up-to-date`, which stops the step when `main` moved since the verdict, then squash-merges with `--match-head-commit`. The App has no ruleset bypass, so the `main` ruleset still applies to its merges. Keep `GITHUB_TOKEN` read-only in this workflow (`actions: read` lists the workflow runs and their jobs), and add no comments, labels or approvals.
- The job condition admits only runs whose `actor` is `dependabot[bot]`, by user id. Do not add `triggering_actor` to it: a maintainer who re-runs a flaky job must let the gate evaluate again.
- Keep the tables in step. A job renamed in `ci.yml`, `lint.yml`, `formal-verification.yml`, `codeql.yml` or `test-website.yml` needs the same change in `REQUIRED_*`, and a renamed workflow or workflow file the same change in `WORKFLOW_FILES`. A new sync pair goes into `DENY_GOMOD` or `DENY_NPM` and into the `exclude-patterns` of `.github/dependabot.yml`. `scripts/test_dependabot_gate.py` (run by `make test-scripts`) fails on drift.
