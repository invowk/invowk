# Change Flow

One Workflow per OpenSpec change, one agent per stage, run from the main session with the template `.agents/workflows/change-flow.js`. The floor every stage keeps is `.agents/rules/agent-workflows.md`; on conflict the rule wins over this runbook and over the template.

## Running it

Create the change worktree and branch first (`git worktree add <worktree> -b <branch> origin/main`), then call the Workflow tool with `scriptPath: ".agents/workflows/change-flow.js"` (the main checkout's copy) and `args`. The Workflow tool loads a `scriptPath` only from the session's working directory or a file the session has read, so to try an unmerged template from another worktree, copy it to the scratchpad, Read it, and pass that copy. Loading by name also works, through the compatibility symlink to `.agents/workflows`: `Workflow({name: 'invowk-change-flow', args})` (verified 2026-11-18). After a pull that adds or renames a template, the session's registry can take about a minute to see it; until then the name is "not found" and `scriptPath` works. The args:

| Arg | Required | Meaning |
|-----|----------|---------|
| `mode` | yes | `new`, `revise`, `continue`, `finalize`, `fast-lane` or `dry-run` |
| `change` | yes (not dry-run) | OpenSpec change id (`openspec/changes/<change>/`) |
| `worktree` | yes | absolute path of the change worktree |
| `branch` | yes | the change branch (never `main`) |
| `primary` | yes | absolute path of the main checkout, for the guard |
| `pr` | no | the draft PR number, once it exists |
| `base` | no | default `origin/main` |
| `from` | with `continue` | `implement`, `simplify`, `review` or `fix` |
| `lane` | no, `continue` only | `fast` when the run being continued was a `fast-lane` run, so the independent spec review still runs if the change is not fast-lane eligible |
| `review_file` | with `continue` from `fix`; optional with `finalize` | absolute path of a JSON file holding an earlier run's `review` result field (findings, failed lenses, code-review text) |
| `notes` | no | an extra brief, for example the path of a decisions file |

The script validates the args and throws on a bad one before it spawns any agent. Run `mode: "dry-run"` after editing the template: it runs the script's self-checks (arg validation, stage plans, lens-id normalisation, guard comparison and its message, failed-review detection) and spawns no agent. `python3 scripts/test_change_flow_template.py` (part of `make test-scripts`) drives the same template under node with stub agents.

**An existing worktree.** When the change worktree already exists (a stopped run, a `blocked` result, a run that a usage-limit pause ended), keep it: never delete or recreate it, and never launch over it as if it were new. Check that `git -C <worktree> rev-parse --abbrev-ref HEAD` prints the change branch and that `git -C <worktree> merge-base --is-ancestor <base> HEAD` exits 0.

- On the expected branch and at or after the base: launch `continue` from the stage that stopped, or `revise` when it stopped in the spec or spec-review stage (`continue` starts at implement at the earliest). The commits, uncommitted edits and checked tasks there are the earlier attempt's work, and the stage continues from them.
- On another branch, or with a `HEAD` that does not descend from the base: do not launch, and report it. A branch that is only behind a base that moved is first rebased by the main session (stage 1 below); after that it is at or after the base.

The script cannot make this choice. It has no filesystem access and never sees the worktree, so the rule lives here and in the restart sentence of the writing-stage prompts (`RESUME`, below), which the script test asserts in every writing-stage prompt and in no read-only one.

## Modes

- `new`: the change does not exist yet. Spec with `openspec-propose`, then the full flow.
- `revise`: the change exists and its artifacts need edits. Spec with `openspec-update-change`, then the full flow.
- `fast-lane`: docs, agent tooling or CI-only changes. One agent writes the spec and self-reviews it, then implementation onward. If the lens selector says the change is not fast-lane eligible (Go or non-testdata CUE files, or a formal, schema, security, supply-chain or architecture lens), the independent spec review runs before code review. If that review needed a spec-fix round, the code was written against the old spec, so the run returns `blocked` and asks for `continue` from `implement`.
- `continue`: resume after a stopped run, at `from`. Use it when the earlier stages are done and committed. Review findings are not committed: every result, `blocked` included, carries a `review` field once the fan-out ran, so save it to a file and pass it as `review_file` with `from: "fix"` (the script refuses `from: "fix"` without one). Pass `lane: "fast"` when continuing a `fast-lane` run.
- `finalize`: only the fix-and-gates stage, for example after the maintainer answered a `maintainer_asks` item. Without `review_file` the fix agent is told that no review ran in this run and applies no review findings; the result says `review_ran: false`.

## Stages and why this order

1. **Spec** (`openspec-propose` or `openspec-update-change`). The spec stage, and the implement stage when it starts the run (`continue` from implement), first check that the branch contains the base (`git merge-base --is-ancestor <base> HEAD`) and return `blocked` when it does not: the main session rebases a stale branch between runs, so conflicts are not deferred to the fix stage.
2. **Spec review**: an independent read-only agent. Blocking findings go to one spec-fix agent (`openspec-update-change`) and a re-review; if they remain, the run returns `blocked`. The spec reviewer may call the `advisor` tool once, at its final checkpoint, in each round (P10).
3. **Implement** (`openspec-apply-change`): tests with the code, commit, push, draft PR, and the formal lane below.
4. **Simplify** (`simplify`, quality only, on the committed diff against the base). It runs only the tests of what it touched.
5. **Lenses**: `scripts/change-flow-lenses.py --base <base> --head HEAD` picks the domain lenses from the paths the change touches. Triggers are read live from the rules that own them (`paths:` frontmatter of formal-bindings, windows, cue-patterns, ci-workflows and version-pinning; the pgo-staleness hook regex; `formal/manifest.toml` `[ci] paths` without `Makefile`, `go.mod` and `go.sum`) plus the security and module-security areas, which the script test keeps in sync with their agent and skill files. Malformed output selects every lens, and the script logs it.
6. **Review fan-out**, in parallel, findings only: the `base` lens (`.agents/agents/code-reviewer.md` over the diff, plus the delta specs) always; `code-review high <pr or branch>` always; and the selected domain lenses, each loading its skill or agent file by name. The `code-review` agent returns the fork's text between `CODE-REVIEW-BEGIN` and `CODE-REVIEW-END`, then `CODE-REVIEW-STATUS: ok|failed` and its guard line. The lens counts only with status `ok` and a body that holds more than skill boilerplate and bare "(none)" / "No findings" / `[]` lines; otherwise, or when the agent returned nothing, it is a failed lens, logged and listed in `failed_lenses`, and the `base` lens keeps the floor. A failed `base` lens stops the run. Of the fan-out, only the `base` lens may call the `advisor` tool, once, at its final checkpoint; the `code-review` agent and the domain lenses may not (P10).
7. **Fix and gates**: one independent agent rebases on the base, dedupes and verifies every finding, applies the confirmed ones, records the rejected ones with reasons, runs the full `.agents/rules/checklist.md` once on the final tree, archives the change (`openspec-archive-change`), runs `/learn` minimally, pushes, and watches `gh pr checks`. It first runs `fetch --prune` and cherry-picks the commits others put on the branch (for example the CI PGO bot's), as listed by `scripts/change-flow-foreign-commits.sh <worktree> <branch> <base>`: commits on `origin/<branch>` with no patch-equivalent locally and not on the base, so the pre-rebase copies a stopped run leaves there are never replayed and a branch someone rebased brings no base commits along. If the remote branch has a merge commit, for example from GitHub's "Update branch", the helper exits 3 and the agent stops, because a force push would drop the merge. It then pushes with `--force-with-lease=<branch>:<that fetched tip>`; a rejected lease means fetch, cherry-pick and push again, never a bare force. It runs the helper from the primary checkout, so a branch older than the helper can use it; a PR that changes the helper is therefore not exercised by its own fix stage, and a template tried from the scratchpad pairs with `main`'s helper. It skips checklist step 1 (`/simplify` belongs to stage 4; a cleanup here would land after the review), skips the archive when the change is already archived, refreshes the formal-bindings ledger (the Formal lane below) when a bound function body was rewritten, and in a `finalize` run only when a bound body changed since the head an earlier fix stage gated, and never edits the change-flow tooling from `/learn` inside a change's PR. It returns `{status, base_sha, head_sha, gates, rejected, maintainer_asks, changed_files}`, where `changed_files` lists the non-test files it changed, so the main session can review edits made after the review; it never marks the PR ready or merges; questions a rule says to ask the user go into `maintainer_asks`.

`simplify` runs before review because it edits logic: the last pass that edits code must be the bug-hunting one, or refactored code would reach `main` with no correctness review. The gates run once, at the end, because every earlier stage can still change the tree.

A stage can run twice: a workflow agent that pauses on a usage limit restarts, and the same prompt runs again (P11). Every writing stage (spec, spec-fix, implement, simplify, fix) is therefore told, in one shared sentence (`RESUME`), that work of the stage already in the worktree is its own earlier attempt: commits on the branch, uncommitted edits, checked tasks, logs with `rc=` lines, ledgers or reports. It reads that work, continues from it by finishing or redoing the unfinished step, and then runs the stage's checks. It never discards it, never starts over and never stops because it exists. For what it finds in the worktree, the only stops are a worktree on another branch and, in the stages that check the base (spec, and implement when it starts the run), a failed base check. A later stage does not stop because the base moved during the run (P8), and the fix stage rebases. So that a restart can continue, a stage keeps its decisions on disk as it works (`tasks.md` checkboxes, `design.md`, `rc=` logs, the commits it makes anyway); the rule adds no extra commit. Read-only stages (spec review, the lens selector, the reviewers) just run again. In `new` and `fast-lane` the spec stage uses `openspec-update-change` when the change directory already exists, because `openspec-propose` asks what to do with an existing change and a workflow agent cannot answer. One stop on earlier work remains, by design: in the fix stage, a commit on `origin/<branch>` whose patch changed when an earlier attempt's rebase resolved a conflict is listed by the helper like someone else's commit, and the stage returns `blocked` with it in `maintainer_asks`, because cherry-picking it would be wrong and a force push would drop it if it were foreign.

## Formal lane

- Implementation runs `python3 scripts/formal.py affected --event pull_request --base <base> --head HEAD`. When it prints `run=true`, it also runs `python3 scripts/formal.py correspondence`, `python3 scripts/formal_mutation.py triage --check` and `make formal-reach`.
- `make formal` is left to the required `Models, golden vectors, and correspondence` CI check, unless Java is present locally and the lane is affected.
- When a function body bound by `.agents/rules/formal-bindings.md` was rewritten, the fix agent refreshes that function's ledger entries in the same PR, on the final tree after the review fixes: a green `triage --check` proves nothing about a rewritten body, and a survivor whose anchor no longer appears fails it, since `[triage] stale_survivors` only shrinks. Before any mutation run it checks what the plan mutates. `python3 scripts/formal_mutation.py plan --out <scratch dir>` must exit 0 and write `formal-plan.json`: a failed plan writes nothing and is a failure to fix or a `maintainer_asks` entry with status `blocked`, never "nothing planned". Then `python3 scripts/formal_mutation.py symbols --plan <scratch dir>/formal-plan.json <[file:]symbol> ...`, given every rewritten bound symbol and `FILE:OLD` for each renamed or deleted one, resolves each name as the refresh does (`resolve_symbol`) and labels it `planned`, `removal-only` (renamed or deleted: absent from `functions[]`, but its ledger entries still need the refresh), `unplanned` (still declared, but its row is in `unbound[]`, for example `LockFile.Save`, `no-binding` and `characterisation-only`: no planned mutants) or `unknown`; it exits 1 on an unknown name or an empty `functions[]`, and its last line says `-> refresh` or `-> skip`. Only on `-> skip` does the agent skip the mutation run and the refresh; it still runs `triage --check`, and names the symbols it checked with their labels. If that `triage --check` fails, it goes back to the refresh, or lists the failure in `maintainer_asks` and returns `blocked`. Otherwise it refreshes the planned and removal-only symbols. The #186 run spent 35 minutes on `LockFile.Save`, which has no planned mutants. It runs `make mutation-formal` once, report-only, in a throwaway `git worktree add --detach` at HEAD; then `make mutation-formal-refresh MUTATION_FORMAL_SYMBOL=<[file:]symbol>[,...]` (or `MUTATION_FORMAL_STALE=1`) with `MUTATION_REPORT_DIR=<throwaway>/artifacts/mutation` for the rewritten or stale symbols (for a renamed or deleted function, `FILE:OLD`, which is removal-only, together with the new name, as the skill says); triages each entry the refresh added (class and reason, replacing the whole placeholder reason: `triage --check` also rejects a reason that still contains the placeholder's "write the class and the reason"); runs the two `mutation-formal-rerun` runs per new escapee that the refresh names; and commits the baseline, ledger and reruns once `triage --check` passes. Before the reruns it commits every tracked edit outside the wrapper's allow-list (`dirty_path_is_allowed` in `scripts/mutation.sh`: the two mutation baselines, the formal-bindings ledger and reruns file, and `artifacts/mutation/`). The wrapper refuses to start while any other tracked file has staged or unstaged changes, not only `formal/manifest.toml`: in PR #188's fix stage it refused a dirty `tasks/next/formal-binding-gaps.md`. The refreshed baseline and ledger may stay uncommitted until `triage --check` passes. Procedure: the partial-refresh steps of `.agents/skills/formal-verification/SKILL.md`. It runs the mutation and the refresh after the review fixes and the tidy and lint fixes are committed, and redoes both on the new HEAD if a later gate edits a bound body. It writes only the class `equivalent` or a deferred `binding-gap` or `model-gap` with a `follow_up`: a class that needs a binding, model, correspondence-row or golden edit (a closed gap, `abstraction`, `defect`) changes the plan-inputs digest after the review, so that survivor, like one it cannot classify, goes into `maintainer_asks`, and the stage returns `blocked`. The target has no file scope, so even one rewritten function plans every formal-bindings mutant (780 mutants in about 35 minutes locally on 2026-11-19). Run it in the background with an `rc=` line and wait for it with Monitor. In a `finalize` run it skips the refresh only when the maintainer brief names the head an earlier fix stage gated, the refresh ran or was not needed there, and no bound body changed between that head and HEAD.

## Merging

The template ends at "ready for maintainer merge". The main session then checks that the returned `base_sha` equals the current `origin/main` (otherwise it reruns `finalize`), and squash-merges as `git-merge.md` describes once the maintainer approves. The main session also handles every `maintainer_asks` item: SonarCloud issue status, PR ready, labels and the like.

The main session never reverts, stashes or commits someone else's edit in the primary checkout to make a merge possible. It merges through `gh` (squash), or integrates in a clean worktree and pushes by SHA (`git push origin <sha>:refs/heads/<branch>`), and leaves the primary checkout's branch behind.

## Reading a guard trip

When a stage's two guard records differ, the run returns `blocked` and the reason says what changed in the primary checkout: `HEAD <before> -> <after>` (8 characters each), `branch <before> -> <after>`, and the `git status --porcelain` lines that appeared and that disappeared (at most 20 each, then `+N more`). For example: `simplify: primary checkout changed (status): appeared: " M internal/x.go"`, or `implement: primary checkout changed (head): HEAD c2fe96ff -> 482dc086`. A difference between one stage's last record and the next stage's first is logged with the same detail and does not stop the run.

- **A foreign edit**: a file someone else changed there, or the main session's own pull, commit or checkout (`HEAD` or the branch moved, or the paths are not the stage's). The stage did nothing wrong. Resume with `continue` from the stopped stage; its work is in the worktree and it continues from it. Never revert, stash, commit or "fix" that edit.
- **A stage that wrote there**: the paths are files of the change, or `HEAD` moved to one of the change's commits. That is a real stop. Report it, and do not resume until the cause is known.

## Probe facts (2026-11-18)

Measured in this repository's sessions; re-check them after a Claude Code upgrade.

- P1. Workflow agents (the default type and `general-purpose`) have `Skill`, but not `Agent` or `Workflow`. They load `CLAUDE.md`, the always-loaded rules and the memory index, but not the conversation: decisions must live in repo rules.
- P2. `code-review` always runs as a fork in the session's primary directory (the main checkout), not in the agent's worktree. With no target it reviewed the main checkout. With an explicit branch or PR target it reviews the right diff, because refs are shared across worktrees. A positive control with seeded Go bugs returned 9 findings, both seeded bugs included, to an agent with no schema.
- P3. When the calling agent has a `schema`, the fork's output does not reach the caller (CST later found it in the fork transcript): the agent sees only "Skill execution completed". A "(none)" result with no explanation counts as a failed lens, not as zero findings; the template logs it and the `base` lens keeps the floor.
- P4. `simplify` runs inline and single-pass ("Agent tool unavailable -> single-pass inline cleanup"). It follows the cwd only when the agent uses `cd <worktree> && ...` or `git -C`; Bash cwd resets to the primary directory between calls.
- P5. Checklist step 7 used to tell agents to resolve Sonar false positives in the SonarCloud UI, an outward write. Since 2026-11-18 the agent records the entry in both properties files and lists it for the maintainer.
- P7. The first real fix-and-gates agent backgrounded its gates and ended its turn to wait. The workflow then forced its result, killing the gates and leaving the fixes uncommitted (run of 2026-11-18). Every stage prompt now forbids ending a turn with work running, and the fix agent commits confirmed fixes before the long gates. `finalize` is the recovery for a run that stopped this way.
- P6 (observed in the CST and LushText sessions on 2026-11-18, not re-measured here). The fork reads the files around each hunk from the primary checkout, so a finding may describe main's code instead of the branch's: the fix agent checks each one with `git -C <worktree> show HEAD:<file>`. `high <branch>` diffs against `main`, so with another base it also reports the base's own commits. A caller with a `schema` finds the fork's findings only in the fork transcript, as the input of its last `StructuredOutput` call; this template avoids that by giving the code-review lens no schema.
- P8. The first real runs (S4 `finalize`, S5a `revise`, 2026-11-19) worked end to end. They showed the gaps the template now closes: a stage started on a stale base, an older branch without the helper, a re-archive of an archived change, a 35-minute mutation re-run after a rebase-only `finalize`, `/learn` editing this runbook from a feature PR, and the fix agent re-running `/simplify` and changing code after the review. Also: workflow agents do have the Monitor tool, and the `rc=` wait pattern worked.
- P9. A `git commit` takes about 5 minutes: the pre-commit hooks run lint, the routed goplint gate (full analysis on a `go.mod` change), the Windows cross-build and `sonar-local`, longer than the default 120000 ms Bash timeout. A commit under the heavy lock also waits for the lock, and that wait counts against a foreground Bash timeout. Every stage prompt that commits (spec, spec-fix, implement, simplify, fix) therefore says to run a locked `git commit` in the background with an `rc=` line and the Monitor wait, never in the foreground, not even with a 600000 ms timeout.
- P10. Workflow agents have the `advisor` tool, which sends the agent's whole transcript to a stronger reviewer model. Nothing in the template asked for it, yet in one session 73 of 152 workflow-agent transcripts called it, 121 calls in all. The maintainer's rule, the "Advisor" bullet of the floor rule, allows it in two places only, at most one call each, at the agent's final checkpoint: the spec-review agent in every round, and the `base` reviewer of the fan-out. It is forbidden everywhere else, in every mode: spec (the fast-lane self-review included, while the independent spec review a fast-lane run sometimes gets may call it), spec-fix, implement, simplify, the lens selector, the domain lenses, `code-review` and fix-and-gates. A failed call is reported in the agent's result, with no retry and no fallback subagent. Every prompt builder of the template carries one of two shared sentences (`ADVISOR_ALLOWED`, `ADVISOR_FORBIDDEN`), and `scripts/test_change_flow_template.py` checks every agent prompt in every mode it drives, and that each builder carries exactly one.
- P11 (observed in the CST session on 2026-11-22/24, not measured here). A workflow agent that pauses on a usage limit restarts, and the same prompt runs again. CST's stage said to stop and report when the branch or worktree already existed, and it stopped twice on its own half-done work (6 commits and an uncommitted edit, then 13 commits). Here the main session creates the worktree, so the risk is a writing stage that finds its own earlier commits, edits or checked tasks and stops, starts over or discards them. Every writing-stage prompt now carries the restart sentence, and the spec stage of `new` no longer proposes a change that already exists.
- P12 (CST, same dates). A run stopped on the guard because of a foreign one-line edit in the primary checkout. The message named only the fields that differed (`status, head`), so nobody could tell that edit from a stage writing where it must not. `guardChanged` now names `HEAD`, the branch and the porcelain lines that appeared or disappeared; "Reading a guard trip" says what to do with each case.
