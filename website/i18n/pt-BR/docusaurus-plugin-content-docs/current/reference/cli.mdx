# Referência CLI

Referência completa para todos os comandos e flags de linha de comando do Invowk™.

## Flags Globais

Estas flags estão disponíveis para todos os comandos:

| Flag | Curta | Descrição |
|------|-------|-----------|
| `--help` | `-h` | Mostrar ajuda para o comando |
| `--ivk-color` | | Controlar a saída com cores da própria CLI do Invowk: `auto` (padrão), `always`, `never`. Precedência: `--ivk-color` > `NO_COLOR` / `CLICOLOR_FORCE` / `TERM=dumb` > detecção de TTY. Valores inválidos saem com `2` |
| `--ivk-config` | `-c` | Caminho do arquivo de configuração. Sobrepõe `INVOWK_CONFIG` e o [arquivo de configuração do usuário](/docs/configuration/overview#localização-do-arquivo-de-configuração); um arquivo ausente ou inválido é um erro (saída 1; o `invowk audit` usa seu código de erro de varredura, 2). Veja [qual arquivo de configuração é usado](../configuration/overview#qual-arquivo-de-configuração-é-usado) |
| `--ivk-no-cwd` | | Ignorar o `invowkfile.cue` e os módulos `*.invowkmod` do diretório atual na descoberta de comandos (sobrepõe `INVOWK_NO_CWD`) |
| `--ivk-interactive` | `-i` | Executar comandos em buffer de tela alternativo (modo interativo) |
| `--ivk-verbose` | `-v` | Habilitar saída verbose |
| `--version` | | Mostrar informação de versão (apenas no comando raiz, não herdado por subcomandos) |

### Variáveis de Ambiente

| Variável | Descrição |
|----------|-----------|
| `INVOWK_CONFIG` | Caminho absoluto do arquivo de configuração usado quando `--ivk-config` não é informado. Vazio significa não definido; um valor relativo, ausente ou inválido é um erro (saída 1; o `invowk audit` usa seu código de erro de varredura, 2). Nunca é resolvido em relação ao diretório atual |
| `INVOWK_NO_CWD` | Igual a `--ivk-no-cwd` quando a flag não é informada. Aceita os valores do `strconv.ParseBool` do Go (`1`, `true`, `0`, `false`, ...); vazio significa desligado, e qualquer outro valor é um erro (saída 2) nos comandos que descobrem fontes de comandos |
| `NO_COLOR` | Quando não vazio, omite sequências ANSI da saída da própria CLI do Invowk e renderiza cartões de erro do Glamour com `"notty"`, salvo se `--ivk-color=always` for passado |
| `CLICOLOR_FORCE` | Quando não vazio e diferente de `"0"`, habilita estilização ANSI em pipes não-TTY para a própria CLI do Invowk, salvo se `NO_COLOR` estiver definido ou `--ivk-color=never` for passado |
| `TERM` | `TERM=dumb` desabilita estilização ANSI para a própria CLI do Invowk, salvo se `CLICOLOR_FORCE` ou `--ivk-color=always` estiver definido |

Chamadas aninhadas do `invowk` herdam `INVOWK_CONFIG` e `INVOWK_NO_CWD` só quando quem chama as definiu, pelas regras normais de `env_inherit_mode` do comando; as formas de flag nunca são exportadas para processos filhos. Comandos do usuário sempre recebem descritores `stdout`/`stderr` brutos sem encapsulamento, e `invowk tui style` / `invowk tui format` continuam opt-in para estilização ANSI em pipelines salvo quando `--ivk-color=never` é passado. A habilitação de cores é ortogonal a `ui.color_scheme` (`"auto"`, `"dark"`, `"light"`), que seleciona o tema quando as cores estão habilitadas.

### invowk cmd

Executar comandos definidos em invowkfiles.

<Snippet id="reference/cli/cmd-syntax" />

Sem nome de comando, `invowk cmd` lista os comandos disponíveis: primeiro o invowkfile raiz, depois os módulos em ordem alfabética e, dentro de cada fonte, os comandos em ordem alfabética pelo nome completo (agrupados por categoria, os sem categoria primeiro). Comandos configurados com `passthrough: true` são anotados com `[passthrough]`.

**Flags:**

| Flag | Curta | Descrição |
|------|-------|-----------|
| `--ivk-runtime` | `-r` | Sobrescrever o runtime (deve ser permitido pelo comando) |
| `--ivk-from` | `-f` | Origem para executar comando (ex.: 'invowkfile' ou nome do módulo) |
| `--ivk-force-rebuild` | | Forçar reconstrução de imagens de container (somente runtime container) |
| `--ivk-container-name` | | Sobrescrever o nome do container persistente de destino (somente runtime container) |
| `--ivk-dry-run` | | Imprimir plano de execução resolvido sem executar |
| `--ivk-watch` | `-W` | Modo watch: reexecutar ao detectar mudanças em arquivos |
| `--ivk-env-file` | `-e` | Carregar variáveis de ambiente de arquivo (repetível) |
| `--ivk-env-var` | `-E` | Definir variável de ambiente (KEY=VALUE, repetível); um valor sem `KEY=` é um erro (saída `2`), enquanto `KEY=` define um valor vazio |
| `--ivk-env-inherit-mode` | | Herdar variáveis do host: `none`, `allow`, `all` |
| `--ivk-env-inherit-allow` | | Allowlist de variáveis do host; exige `--ivk-env-inherit-mode=allow` (repetível) |
| `--ivk-env-inherit-deny` | | Denylist de variáveis do host (repetível) |
| `--ivk-workdir` | `-w` | Sobrescrever diretório de trabalho do comando |

:::note Fronteira pré-comando `--ivk-*` para comandos passthrough
Todas as flags persistentes `--ivk-*` de `invowk cmd` são aceitas **antes** do caminho do comando (além de após comandos normais). Para comandos com `passthrough: true`, apenas flags `--ivk-*` posicionadas **antes** do caminho do comando configuram o Invowk; todo token após o caminho do comando (incluindo `--help`, `-h`, flags desconhecidas, `--` e flags `--ivk-*` aninhadas) é repassado literalmente ao script em invocações diretas, com `@source`, `--ivk-from` e `<source> <cmd>`. Como `invowk cmd <name> --help` executa o comando passthrough, use `invowk help cmd <name>` para inspecionar a ajuda do Invowk sem executar.
:::

:::note
Os prefixos `ivk-`, `invowk-` e `i-` são reservados para flags do sistema e não podem ser usados para flags definidas pelo usuário.
:::

:::note
Quando `--ivk-watch` executa conectado a um terminal com `OSC7577_TOKEN` definido, o Invowk emite relatórios assinados OSC 7577 de Program Resume (`clear=1` em `Ctrl+C` ou erros após a inicialização, preservado em `SIGHUP`/`SIGTERM` no Unix, omitido quando `--ivk-env-var` é usado ou limites são excedidos) e remove `OSC7577_TOKEN` dos comandos filhos monitorados. Em terminais conectados, `--ivk-watch`, `-i` e `invowk tui *` também emitem Program Status via `OSC 7501` (`app="invowk"`, limpo ao sair), mantendo `invowk cmd` não interativo silencioso.
:::

**Descoberta de Comandos:**

Comandos são descobertos de (em ordem de prioridade):
1. `invowkfile.cue` do diretório atual (prioridade mais alta)
2. Diretórios `*.invowkmod` irmãos
3. Entradas configuradas em `includes` (somente módulos)
4. `~/.invowk/cmds/` (somente módulos, não-recursivo)

**Desambiguação de Comandos:**

Quando um nome de comando existe em múltiplas origens (ex.: tanto em `invowkfile.cue` quanto em um módulo), você deve desambiguar:

Usando o prefixo `@source`:
```bash
invowk cmd @invowkfile deploy      # Executar deploy do invowkfile
invowk cmd @tools deploy         # Executar deploy de tools.invowkmod
invowk cmd @tools.invowkmod deploy # Nome completo do módulo também funciona
```

Usando a flag `--ivk-from`:
```bash
invowk cmd --ivk-from invowkfile deploy
invowk cmd --ivk-from tools deploy
```

Se você executar um comando ambíguo sem desambiguação, o invowk mostra um erro listando as origens disponíveis.

:::tip
Você pode usar `@source` ou `--ivk-from` mesmo para nomes de comando únicos para ser explícito sobre de onde um comando vem.
:::

### invowk validate

Validar invowkfiles, módulos ou o workspace inteiro.

<Snippet id="reference/cli/validate-syntax" />

Sem argumentos, valida o workspace atual executando a descoberta completa
e reportando todos os diagnósticos de cada caminho de busca.

Com um argumento de caminho, detecta automaticamente o tipo do alvo:

| Caminho | Validação |
|---------|-----------|
| Diretório `*.invowkmod` | Validação de módulo (estrutura, mais parsing de invowkfile e árvore de comandos quando `invowkfile.cue` está presente) |
| Arquivo `invowkfile.cue` | Validação de invowkfile (schema CUE + estrutural + árvore de comandos) |
| Diretório com `invowkfile.cue` | Validação de invowkfile |
| Arquivo `invowkmod.cue` | Validação de módulo (diretório pai) |

:::tip
`invowk validate` sempre executa validação profunda da estrutura e dos metadados do módulo.
Quando o módulo contém `invowkfile.cue`, também faz o parsing do arquivo e valida sua árvore
de comandos; módulos apenas de biblioteca não executam essas verificações específicas.
:::

### invowk audit

Escanear riscos de segurança em invowkfiles, módulos e scripts. Veja o guia de [Auditoria de Segurança](../security/audit) para documentação completa.

<Snippet id="reference/cli/audit-syntax" />

**Flags:**

| Flag | Padrão | Descrição |
|------|--------|-----------|
| `--format` | `text` | Formato de saída: `text`, `json` |
| `--severity` | `low` | Severidade mínima: `info`, `low`, `medium`, `high`, `critical` |
| `--include-global` | `false` | Incluir `~/.invowk/cmds/` no scan |
| `--llm-provider` | | Auto-detectar ou forçar provedor: `auto`, `claude`, `codex`, `gemini`, `ollama` |
| `--llm` | `false` | Habilitar LLM usando configuração ou API |
| `--llm-url` | `http://localhost:11434/v1` | URL base da API compatível com OpenAI |
| `--llm-model` | Fallback de API/Ollama: `qwen2.5-coder:7b`; padrão da ferramenta para provedor CLI quando omitido | Nome do modelo; obrigatório para provedores de API cloud e opcional para provedores CLI |
| `--llm-api-key` | *(vazio)* | Chave de API (vazio para servidores locais) |
| `--llm-timeout` | `2m` | Timeout por requisição |
| `--llm-concurrency` | `2` | Máximo de requisições LLM paralelas |

`--llm` e `--llm-provider` são mutuamente exclusivos. Use `--llm` para o backend configurado/API e `--llm-provider` para forçar a detecção de provedor.

**Códigos de saída:** `0` = limpo, `1` = achados detectados, `2` = erro de scan.

## Exit Codes

O Invowk usa estas classes de código de saída:

| Código | Significado |
|--------|-------------|
| `0` | A invocação teve sucesso. Um grupo de comandos sem argumentos (por exemplo `invowk module` ou `invowk cmd test`) mostra sua ajuda e sai com `0`. |
| `N` | Um comando definido pelo usuário executou e saiu com seu próprio status `N` diferente de zero, repassado sem alteração em todos os runtimes. |
| `128 + sinal` | No Unix, o Invowk encerrou ao receber um sinal de término interceptado (`129` `SIGHUP`, `130` `SIGINT`, `143` `SIGTERM`) após limpeza limitada de recursos, exceto quando um subcomando define outro código (como `invowk tui spin`). |
| `2` | O Invowk rejeitou a linha de comando antes de executar qualquer código do comando do usuário. |
| `1` | O próprio Invowk falhou por qualquer outro motivo. |

O status `2` cobre:

- uma flag desconhecida, um valor de flag que não pode ser interpretado, uma flag sem o valor exigido ou uma flag obrigatória ausente, em qualquer nível;
- um comando desconhecido, incluindo um erro de digitação sob um grupo de comandos e um comando raiz desconhecido seguido de `--help`, `-h` ou `--version` (`invowk cmd test nonexistent`, `invowk config bogus`); os subcomandos do grupo são listados no stderr e nada é escrito no stdout;
- um erro de quantidade de argumentos em um comando embutido (`invowk init a b c`);
- um nome de comando sob `invowk cmd` não encontrado ou ambíguo entre fontes, uma fonte `@source` ou `--ivk-from` desconhecida, um nome de fonte malformado, como um caminho (`@./m.invowkmod`; use o nome do módulo, `m`), e um filtro de fonte sem nome de comando;
- argumentos ou flags declarados que falham na validação;
- um valor inválido de uma flag reservada `--ivk-*`, como um valor inválido de `--ivk-color` (`auto`, `always`, `never`), um `--ivk-runtime` desconhecido ou um runtime não permitido pelo comando, um `--ivk-env-inherit-mode` desconhecido, um nome inválido em `--ivk-env-inherit-allow`/`--ivk-env-inherit-deny`, um `--ivk-workdir` só com espaços, um `--ivk-env-file` vazio, um `--ivk-container-name` inválido ou um valor de `--ivk-env-var` sem `KEY=`;
- um erro de `invowk agent` detectado apenas pela linha de comando, como um nome inválido, flags mutuamente exclusivas, uma descrição ausente, um valor `--llm-*` inválido ou um formato ou operação de prompt desconhecido;
- um valor inválido de `--alias` ou `--prefix` em `invowk completion` (incluindo `--prefix` sem `--alias`, caracteres NUL/quebras de linha ou aspas não fechadas);
- um conflito decidido apenas por flags e variáveis de ambiente: um valor inválido de `INVOWK_NO_CWD`, `--ivk-watch` junto com `--ivk-dry-run`, `invowk config set` enquanto `--ivk-config` ou `INVOWK_CONFIG` está ativo, e `invowk agent cmd create`/`change --verify` sob `--ivk-no-cwd` ou `INVOWK_NO_CWD`.

O status `1` cobre todo o resto: erros de configuração que abortam o comando, incluindo um arquivo de configuração indicado por `--ivk-config` ou `INVOWK_CONFIG` ausente ou inválido, ou um `INVOWK_CONFIG` relativo; erros de descoberta; falhas de fontes no diretório atual (a menos que `--ivk-no-cwd` ou `INVOWK_NO_CWD` esteja ativo), onde um `./invowkfile.cue` ou `./*.invowkmod` que falha na análise, schema ou validação de `invowk_version` aborta o `invowk cmd` imediatamente com seu erro real em vez de recorrer a fontes de menor precedência; invowkfiles ou árvores de comandos inválidas, incluindo um comando não encontrado quando um invowkfile ou módulo fora do diretório atual foi ignorado por falhar ao ser interpretado ou carregado (o comando pode estar definido nele; o erro cita cada fonte ignorada e o seu código de diagnóstico, e um comando ausente dentro de uma fonte `@source` ou `--ivk-from` que carregou continua saindo com `2`); verificações de `depends_on` não satisfeitas; uma plataforma de host não suportada; um engine de contêiner ou runtime indisponível; timeouts (`timeout`) e cancelamentos sem sinal; e falhas de `invowk agent` que dependem de arquivos, da configuração ou de um LLM.

No Unix, sinais de término interceptados (`SIGHUP` = 1, `SIGINT` = 2, `SIGTERM` = 15) cancelam o contexto de execução ativo, removem scripts temporários, encerram grupos de processos filhos nativos fora de TTY e param/removem contêineres efêmeros em uma janela de limpeza limitada antes de sair com `128 + sinal` (`129`, `130`, `143`). Execuções nativas ligadas diretamente a um TTY controlador permanecem no grupo de processos em primeiro plano para que prompts interativos não bloqueiem em `SIGTTIN`/`SIGTTOU`. No Windows, `Ctrl+C` (`os.Interrupt`) cancela o contexto de execução, limpa recursos e sai com status `1`.

Exceções por comando:

| Comando | Códigos |
|---------|---------|
| `invowk audit` | `0` limpo, `1` achados detectados, `2` erro de scan ou de configuração; rejeições da linha de comando também saem com `2` |
| `invowk tui confirm` | `1` quando o usuário recusa |
| `invowk tui spin` | o código de saída do comando executado; `1` quando cancelado com Ctrl+C, quando um sinal encerrou o comando, ou quando ele ainda rodava 15 segundos depois de ser parado |
| `invowk validate` | `1` quando a validação encontra erros |

:::note
Ao repassar um código de saída de um comando ou subcomando embutido (`invowk cmd`, `invowk audit`, `invowk validate`, `invowk tui confirm`, `invowk tui spin`) sem mensagem de erro do próprio Invowk, o Invowk repassa o código silenciosamente tanto em TTY quanto fora de TTY, sem imprimir o quadro `Exit status N`. Passe `--ivk-verbose` para emitir uma única linha de diagnóstico no stderr.

Um comando do usuário pode sair com `1` ou `2` por conta própria, e uma chamada `invowk` aninhada em um script pode propagar seu próprio erro de uso. Um wrapper que precisa distinguir esses casos lê o stderr. O contrato só é exato para comandos cujos scripts evitam os códigos `1` e `2`.

Falhas do engine de contêiner ou do runtime OCI (códigos `125` e `126`) são repetidas como transitórias. Quando as tentativas se esgotam, o código é repassado como se fosse do próprio comando.
:::

## Mensagens de Erro

O Invowk fornece mensagens específicas para ajudar no diagnóstico:

### Nenhum Invowkfile Encontrado

Quando nenhum invowkfile é descoberto em nenhum local de busca:

<Snippet id="reference/cli/error-no-invowkfile" />

**Esta mensagem aparece quando:**
- Nenhum `invowkfile.cue` existe no diretório atual
- Nenhum módulo existe nos `includes` configurados
- Nenhum módulo existe em `~/.invowk/cmds/`

**Soluções:**
- Execute `invowk init` para criar um invowkfile no diretório atual
- Navegue para um diretório que contenha um invowkfile
- Adicione caminhos de módulo em `includes` na sua configuração

### Falha ao Fazer Parse do Invowkfile

Quando um invowkfile é encontrado mas contém erros de sintaxe ou configuração inválida:

<Snippet id="reference/cli/error-parse-failed" />

**Esta mensagem aparece quando:**
- Erros de sintaxe CUE (chaves/aspas faltando, etc.)
- Nomes de campo ou valores inválidos
- Falhas de validação do schema (ex.: tipo de runtime inválido)
- Campos obrigatórios ausentes

**Soluções:**
- Verifique a mensagem de erro específica exibida acima do texto de ajuda
- Valide sua sintaxe CUE: `cue vet invowkfile.cue`
- Rode com modo verbose: `invowk --ivk-verbose cmd`
- Compare com a [referência de schema do invowkfile](./invowkfile-schema)

:::tip
A mensagem de erro sempre mostra primeiro o erro de parse específico (por exemplo, qual campo falhou na validação), seguido por orientações gerais de troubleshooting.
:::
