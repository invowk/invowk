# Modo Interativo

O modo interativo (`-i` / `--ivk-interactive`) executa comandos em um buffer de tela alternativo com suporte completo a PTY (pseudo-terminal), permitindo interações ricas no terminal.

## Visão Geral

Quando você executa um comando com `-i`, o Invowk:

1. Cria um pseudo-terminal (PTY) para o comando
2. Exibe a saída em um buffer de tela alternativo (terminal fica limpo)
3. Encaminha toda entrada de teclado para o comando em execução
4. Permite rolar e revisar a saída após a conclusão
5. Suporta componentes TUI embutidos como overlays modais

### Por Que Esses Comandos Precisam Dele

Sem o modo interativo, stdin não está conectado a um TTY, o que quebra:
- Prompts de senha (não conseguem ler sua entrada de forma segura)
- `sudo` (requer um TTY para entrada de senha)
- Sessões SSH (precisam de controle total do terminal)
- Qualquer programa usando `readline` ou bibliotecas similares

## Componentes TUI Embutidos

Ao executar no modo interativo, componentes TUI chamados de seus scripts são renderizados como **overlays modais** sobre a saída do comando, ao invés de uma tela separada:

<Snippet id="interactive/embedded-tui" />

Isso cria uma experiência fluida onde:
1. Seu script executa na tela alternativa
2. Quando um componente TUI é necessário, ele aparece como overlay
3. Após o usuário completar a interação, o overlay fecha
4. A execução do script continua com o valor capturado

### Como Funciona

Quando um comando executa com `-i`:
1. Invowk inicia um servidor TUI local
2. Processos filhos detectam a variável de ambiente `INVOWK_TUI_ADDR`
3. Ao invés de renderizar diretamente, componentes TUI enviam requisições ao pai
4. O pai os renderiza como overlays modais
5. Resultados são enviados de volta ao processo filho

Isso acontece automaticamente - nenhuma mudança necessária nos seus scripts.

## Buffer de Tela Alternativo

O buffer de tela alternativo é um recurso do terminal que:
- Fornece uma "tela" separada para o comando
- Preserva seu histórico do terminal
- Restaura automaticamente quando o comando termina

Isso significa que após sair do modo interativo:
- Seu terminal parece exatamente como antes
- Sem poluição de saída no seu scrollback
- Separação limpa entre saída do invowk e uso normal do terminal

## Limitações

- **Comando único**: Não é possível executar múltiplos comandos em paralelo no modo interativo
- **PTY necessário**: O terminal deve suportar operações PTY
- **Apenas containers Debian**: Imagens Alpine e Windows não são suportadas

## Suporte ao Runtime Container

O modo interativo funciona perfeitamente com o runtime container. As execuções em container já usam a camada de imagem auto-provisionada (habilitada por padrão), que instala o `invowk` dentro do container quando ele é um executável Linux para a arquitetura da imagem; o modo interativo adiciona a infraestrutura de TUI. Num host macOS ou Windows, defina [`container.auto_provision.binary_path`](/docs/configuration/options#containerauto_provisionbinary_path) como um build Linux, ou as chamadas `invowk tui` dentro do container não funcionam. Veja [Runtime Container](/docs/runtime-modes/container#auto-provisionamento) para detalhes. Quando você executa um comando de container com `-i`:

1. **Camada de imagem provisionada**: Invowk instala seu binário quando ele pode rodar no container (mesmo comportamento do modo não interativo)
2. **Servidor TUI**: Um servidor local trata requisições TUI do container (veja [Exposição de rede](#exposição-de-rede-do-servidor-tui))
3. **Overlays modais**: Componentes TUI renderizam no seu terminal, não dentro do container

```bash
# Executar um comando de container interativamente
invowk cmd myproject build -i -r container
```

Dentro dos scripts do seu container, você pode usar todos os componentes TUI:

<Snippet id="interactive/container-tui-example" />

:::warning Apenas Containers Linux
Imagens baseadas em Alpine não são suportadas — ambientes baseados em musl possuem diferenças comportamentais sutis que reduzem a confiabilidade do runtime. Use `debian:stable-slim` para exemplos genéricos de container; imagens específicas de linguagem pertencem apenas a demonstrações de runtime específicas da linguagem.
:::

### Exposição de rede do servidor TUI

Por padrão, o servidor TUI nunca escuta em todas as interfaces. Onde ele escuta depende do modo da engine de container, e o container recebe um endereço em que o servidor realmente escuta:

| Modo da engine | O servidor escuta em | Host em `INVOWK_TUI_ADDR` |
|---|---|---|
| Docker rootful local no Linux | `127.0.0.1` e o gateway da bridge padrão (por exemplo `172.17.0.1`) | o IP do gateway |
| Docker Desktop (local) | `127.0.0.1` | `host.docker.internal` |
| Podman rootless efêmero com pasta (`passt`) | `127.0.0.1`, com uma porta encaminhada (`--network=pasta:-T,<porta>`) | `127.0.0.1` |
| Qualquer outro (veja abaixo) | nada: a execução interativa é recusada | não definido |

Trate `INVOWK_TUI_ADDR` como uma URL opaca; ela pode ser um IP literal.

**Modos sem rota estreita** recusam execuções interativas: uma engine remota (qualquer endpoint Docker que não seja um socket local `unix://`, `npipe://` ou `fd://`, ou seja `tcp://`, `ssh://` e um `host:porta` sem esquema; `podman-remote`, Podman machine), Podman rootful (também quando o CLI `docker` fala com o socket compatível com Docker do Podman), um container persistente no Podman rootless, Podman rootless sem pasta, Docker rootless, Snap, uma consulta à engine que falhou, e qualquer modo não listado acima. `invowk cmd … -i` sai com status 1 antes de abrir um listener ou iniciar o container do comando, e o erro cita o motivo e o opt-in. O mesmo comando sem `-i` executa como antes. Se o modo interativo vier apenas de `ui.interactive: true` na sua configuração, o invowk executa o comando de forma não interativa e imprime um aviso (`--ivk-interactive=false` o silencia). A verificação acontece antes das verificações de dependências, então nenhum container de verificação é iniciado. O invowk não executa esses comandos sem servidor TUI, porque um prompt cuja resposta o script captura (`name=$(invowk tui input)`) não desenharia nada e entregaria ao script códigos de controle do terminal em vez da resposta. No Podman rootless, um container efêmero com o pasta instalado recebe o plano estreito.

**Opt-in.** Para restaurar conscientemente o bind amplo anterior, defina [`container.tui_server_bind: "all-interfaces"`](../reference/config-schema.mdx#tui_server_bind) na sua configuração do invowk. Nos modos acima (e no Docker Desktop) o servidor passa a escutar em `0.0.0.0` e usa o alias de host da engine, e o invowk avisa a cada execução desse tipo que a porta é alcançável pela rede. Para uma engine remota isso só ajuda se o alias de host levar de volta a esta máquina. A chave é lida apenas do arquivo de configuração que o invowk seleciona: o arquivo de `--ivk-config` ou `INVOWK_CONFIG`, quando informado (o seu arquivo de configuração de usuário não é lido nesse caso), senão o seu arquivo de configuração de usuário. Um invowkfile ou módulo não consegue defini-la.

**Flatpak sem `--share=network`.** A rede do sandbox é privada, então nenhum bind é alcançável pelos containers da engine. As execuções interativas em container são recusadas, e o opt-in não se aplica; conceda `--share=network` ou execute sem `-i`.

**Servidor inalcançável.** Se `invowk tui *` dentro de um container informar que o servidor TUI está inalcançável, a engine não roteia para o endereço em que o servidor escuta (por exemplo no Docker Desktop, ou quando um firewall do host descarta o tráfego da bridge para a porta). O comando falha em poucos segundos com um erro que cita o opt-in. Isso inclui um proxy da engine que aceita a conexão mas não alcança o host: antes de cada requisição de componente, o cliente envia uma verificação de saúde curta e autenticada, então uma conexão resetada, fechada ou silenciosa também falha rápido. O cliente nunca envia requisições TUI por um `HTTP_PROXY` do ambiente do container, então o token da sessão não chega a um proxy.

**Exposição residual.** No Docker rootful, a porta do gateway também é alcançável por outros containers na mesma bridge e por hosts no mesmo segmento de rede que roteiem a sub-rede da bridge por esta máquina. Toda requisição continua exigindo o token bearer da sessão, e a porta existe apenas durante a execução interativa.

**Opções do pasta no host.** No plano pasta, o invowk encaminha uma porta e nada mais. O Podman também aplica as `pasta_options` do seu `containers.conf`; opções como `--map-gw` ou `--map-host-loopback` ali dão ao container mais do loopback do host do que o invowk pede.

**Containers persistentes externos** (`--ivk-container-name` apontando para um container que o invowk não criou) recebem o plano do modo da sua engine. Se esse container estiver numa rede que não alcança o endereço do bind, as chamadas `invowk tui *` falham como inalcançáveis; o bind nunca é ampliado por causa disso.

## Boas Práticas

1. **Use para comandos que precisam de entrada**: Scripts de deploy com confirmações, migrações de banco de dados, etc.

2. **Não use para comandos simples**: Comandos rápidos sem interação não se beneficiam do modo interativo

3. **Combine com componentes TUI**: Crie fluxos de trabalho interativos ricos com prompts embutidos

4. **Considere o padrão de configuração**: Se a maioria dos seus comandos precisa de interação, habilite na configuração
