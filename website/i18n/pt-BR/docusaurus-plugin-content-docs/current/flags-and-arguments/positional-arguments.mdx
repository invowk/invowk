# Argumentos Posicionais

Argumentos posicionais são valores passados por posição após o nome do comando. São ideais para entradas obrigatórias onde a ordem é natural (como `source` e `destination`).

## Propriedades dos Argumentos

| Propriedade | Obrigatória | Descrição |
|-------------|-------------|-----------|
| `name` | Sim | Nome do argumento (alfanumérico, hífens, underscores) |
| `description` | Sim | Texto de ajuda |
| `type` | Não | `string`, `int`, `float` (padrão: `string`) |
| `default_value` | Não | Valor padrão se não fornecido |
| `required` | Não | Deve ser fornecido (não pode ter default) |
| `validation` | Não | Padrão regex para o valor |
| `variadic` | Não | Aceita múltiplos valores (apenas último arg) |

## Argumentos vs Subcomandos

Um comando não pode ter ambos argumentos e subcomandos. Se um comando define `args` mas também tem subcomandos, invowk falha com um erro:

```
✖ Invalid command structure

Command 'deploy' has both args and subcommands in invowkfile.cue
  defined args: env
  subcommands: deploy status, deploy logs

Remove either the 'args' field or the subcommands to resolve this conflict.
```

Esta restrição existe porque parsers de CLI interpretam argumentos posicionais após o nome de um comando como potenciais nomes de subcomandos, tornando a combinação ambígua.

Escolha uma abordagem:
- **Argumentos**: Para comandos folha com entradas diretas
- **Subcomandos**: Para hierarquias de comando complexas onde usuários selecionam uma ação

Um token que não corresponde a um subcomando de um grupo de comandos (por exemplo `invowk cmd test nonexistent` quando só existem `test unit` e `test other`) é rejeitado com status de saída `2`, e os subcomandos do grupo são listados no stderr. Um comando folha que não declara `args` continua recebendo tokens extras como parâmetros posicionais, mesmo quando também tem subcomandos: `invowk cmd w typo` executa `w` com `typo` como `$1`.

## Passthrough Bruto de Argumentos (`passthrough: true`)

Ao encapsular uma ferramenta CLI existente, declarar cada flag da ferramenta no `invowkfile.cue` costuma ser desnecessário. Defina `passthrough: true` em um comando folha para desativar o parsing de flags do Cobra após o caminho do comando:

### Regras de Fronteira da CLI

- **Flags `--ivk-*` pré-comando pertencem ao Invowk**: posicione `--ivk-runtime`, `--ivk-from`, `--ivk-workdir`, `--ivk-env-var`, `--ivk-env-file`, `--ivk-env-inherit-*`, `--ivk-dry-run`, `--ivk-watch` e flags raiz `--ivk-*` **antes** do caminho do comando.
- **Tokens pós-comando vão literalmente**: cada token **após** o caminho do comando—incluindo `--help`, `-h`, flags desconhecidas, `--` e flags `--ivk-*` aninhadas—é repassado literalmente via `$@` / `$1..$n` (POSIX/container/`virtual-sh`), `$args` (PowerShell), `...` / `invowk.args` (`virtual-lua`) e `ARG1..ARGn` / `ARGC`. Isso vale igualmente para invocação direta, `@source`, `--ivk-from` e `<source> <cmd>` qualificado por módulo.
- **Exclusividade mútua**: `passthrough: true` não pode ser combinado com `flags`, `args` ou subcomandos filhos.

:::warning Semântica de Execução de `--help` e Ressalva de `cmd.exe` no Windows
- **`--help` executa o comando**: `invowk cmd <name> --help` repassa `--help` para o script e **executa o comando** (incluindo verificações `depends_on` e provisionamento de container). Use `passthrough: true` apenas em scripts/alvos que tratem `--help` / `-h` com segurança, ou passe `--ivk-dry-run` antes do nome do comando para inspecionar sem executar.
- **Inspecionando sem executar**: execute `invowk help cmd <name>` para ver a ajuda e flags do Invowk sem rodar o script. Comandos com `passthrough: true` aparecem marcados com `[passthrough]` nas listagens de `invowk cmd`.
- **Ressalva do `cmd.exe` no Windows**: o `cmd.exe` não aceita parâmetros posicionais inline (`$@`), portanto `passthrough: true` expõe os argumentos apenas via `ARGn`/`ARGC` no `cmd.exe`. Use `pwsh`/PowerShell (`native`) ou `virtual-sh` no Windows ao encapsular CLIs com `$args` / `$@`.
:::

## Melhores Práticas

1. **Args obrigatórios primeiro**: Siga as regras de ordenação
2. **Use nomes significativos**: `source` e `dest` não `arg1` e `arg2`
3. **Valide quando possível**: Capture erros cedo
4. **Documente com descrições**: Ajude usuários a entender
5. **Prefira flags para valores opcionais**: Mais fácil de entender
