# Runtime Container

:::danger Apenas Containers Linux

O runtime container **suporta apenas imagens de container Linux baseadas em Debian** (ex: `debian:stable-slim`).

**NÃO suportado:**
- **Imagens baseadas em Alpine** — Ambientes baseados em musl possuem diferenças comportamentais sutis que reduzem a confiabilidade do runtime
- **Imagens de container Windows** — Não há shell POSIX disponível

**Requisitos de plataforma:**
- **Linux**: Funciona nativamente com Docker ou Podman
- **macOS**: Funciona com Docker Desktop (usa VMs Linux internamente)
- **Windows**: Requer Docker Desktop com backend WSL2 em modo de containers Linux

Scripts são executados usando `/bin/sh` dentro do container, o que requer um ambiente com shell POSIX compatível.

:::

:::info Escopo da Detecção de Alpine

O Invowk rejeita imagens com nome exato `alpine` ou terminando com `/alpine` (após remover tags e digests). Imagens com "alpine" em outra parte do nome (ex: `go-alpine-builder` ou `myorg/alpine-tools`) **não** são automaticamente rejeitadas. Evite todas as imagens baseadas em musl independentemente do nome — a política é sobre confiabilidade do runtime, não apenas correspondência de nome de imagem.

:::

O runtime **container** executa comandos dentro de um container Docker ou Podman. Ele fornece isolamento completo e reprodutibilidade - seu comando executa no exato mesmo ambiente toda vez.

## Como Funciona

Quando você executa um comando com o runtime container, o Invowk™:

1. Baixa ou constrói a imagem do container (se necessário)
2. Monta o diretório do invowkfile dentro do container
3. Executa o script dentro do container
4. Transmite a saída de volta para seu terminal

## Montagem de Volumes

Monte diretórios adicionais no container:

<Snippet id="runtime-modes/container-volumes-full" />

Por padrão, o diretório do invowkfile é montado em `/workspace`, e entradas relativas em `volumes` são resolvidas a partir do diretório do invowkfile ou do módulo. Arquivos `<cwd>/invowkfile.cue` avulsos podem usar caminhos relativos, volumes nomeados ou bind mounts absolutos do host; módulos `*.invowkmod` podem usar volumes nomeados ou caminhos relativos dentro de seu teto de contenção, e não podem declarar bind mounts absolutos do host.

## Montagem de Workspace e Rotulagem SELinux

Personalize como `/workspace` é montado por comando com `workspace_mount`:

```cue
runtimes: [{
    name: "container"
    image: "debian:stable-slim"
    workspace_mount: {
        enabled: true              // Padrão: true; defina false para omitir /workspace
        root: "invowkfile"         // "invowkfile" (padrão) | "workdir"
        readonly: false            // Padrão: false; defina true para montar /workspace:ro
        selinux_label: "auto"      // "auto" (padrão) | "shared" (:z) | "private" (:Z) | "none"
    }
}]
```

- **Contenção em três camadas:** Módulos vendored, remotos e em `~/.invowk/cmds` ficam estritamente confinados à raiz do módulo; módulos no diretório atual podem resolver `root: "workdir"` e `volumes` relativos até `<cwd>`; módulos configurados em `includes` permanecem confinados à raiz do módulo, a menos que `workspace_root` defina um teto explícito do operador. `--ivk-workdir` na CLI atua como consentimento explícito do usuário.
- **Desacoplamento de scripts:** Scripts inline com interpretador e `script.file` fora de `/workspace` não dependem de `/workspace` gravável—em containers efêmeros, o Invowk os monta em modo somente leitura sob `/.invowk/` (mantendo rótulos SELinux `:z` quando o SELinux está ativo) e limpa diretórios temporários após parar/remover o container.
- **Política SELinux do host:** Operadores podem definir `container: { selinux_labeling: "disabled" }` em `config.cue` para passar `--security-opt label=disable` e omitir a rotulagem automática `:z`.

### Variáveis de Ambiente SSH

Quando `enable_host_ssh: true`, estas variáveis estão disponíveis:

| Variável | Descrição |
|----------|-----------|
| `INVOWK_SSH_ENABLED` | Definido como `true` quando o SSH está ativo |
| `INVOWK_SSH_HOST` | Endereço do host (ex: `host.docker.internal`) |
| `INVOWK_SSH_PORT` | Porta do servidor SSH |
| `INVOWK_SSH_USER` | Nome de usuário (`invowk`) |
| `INVOWK_SSH_TOKEN` | Token de autenticação com escopo da execução |

### Segurança

- Cada execução de comando recebe um token único
- Tokens são revogados quando o comando termina, o que também fecha qualquer conexão SSH aberta com eles
- O servidor SSH apenas aceita autenticação baseada em token
- O servidor é encerrado após a execução do comando

### Requisitos do Container

Seu container precisa de `sshpass` ou similar para SSH baseado em senha:

```dockerfile
FROM debian:stable-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
    openssh-client sshpass \
    && rm -rf /var/lib/apt/lists/*
```

## Auto-provisionamento

Quando `container.auto_provision.enabled` é `true` (padrão), o Invowk cria uma imagem derivada em cache ao anexar uma pequena camada de provisionamento sobre a sua imagem base (seja a `image` especificada ou a imagem construída pelo Containerfile/Dockerfile). Essa camada inclui quaisquer módulos e, quando ele pode rodar no container, o binário do `invowk`, para que comandos `invowk` estejam disponíveis dentro do container.

O binário precisa ser um executável Linux para a arquitetura da imagem. Por padrão o Invowk usa o binário em execução, que serve num host Linux com a mesma arquitetura da imagem. Num host macOS ou Windows, ou num host Linux de outra arquitetura, o Invowk deixa o binário de fora, continua provisionando os módulos, executa o comando e exibe um aviso: chamadas `invowk` aninhadas dentro do container não funcionam até você definir [`container.auto_provision.binary_path`](../configuration/options.mdx#containerauto_provisionbinary_path) como uma build Linux para a arquitetura da imagem. Um `binary_path` que não seja uma build assim faz o comando falhar.

O auto-provisionamento se aplica a execuções de container baseadas em imagem, incluindo execuções não interativas e interativas. Quando um comando aponta para um container persistente existente, o Invowk pula a preparação da imagem e usa esse container diretamente. Para execuções baseadas em imagem, a imagem derivada é cacheada como `invowk-provisioned:<hash>` e reutilizada; se o provisionamento falhar, o Invowk avisa e usa a imagem base apenas no modo padrão não estrito. Com `container.auto_provision.strict: true`, a falha de provisionamento interrompe o comando. Um `binary_path` inutilizável interrompe o comando nos dois modos.

Se o binário é instalado ou não faz parte da identidade da imagem provisionada. Um container persistente gerenciado criado com o binário de fora (ou com ele) deixa de corresponder quando isso muda, por exemplo depois de você definir ou remover `binary_path`, ou na primeira execução depois de atualizar o Invowk num host macOS ou Windows: a execução falha com o erro existente "was created by invowk with a different runtime configuration" até você remover o container.

## Modo Interativo

O runtime container suporta totalmente o modo interativo (`-i`). Execuções interativas usam a mesma camada provisionada descrita acima (quando habilitada) e adicionam a infraestrutura de TUI no host, habilitando:

- Componentes TUI como overlays modais
- Suporte completo a PTY para prompts de senha e confirmações
- Integração transparente com o terminal do host

```bash
# Executar um comando de container interativamente
invowk cmd myproject build -i -r container
```

Quando você executa com `-i`, o Invowk:

1. **Usa a camada de imagem provisionada** (se habilitada)
2. **Inicia um servidor TUI** no host
3. **Encaminha requisições TUI** do container para o host
4. **Renderiza overlays** no seu terminal

Isso significa que seus scripts podem usar comandos `invowk tui` dentro de containers:

<Snippet id="runtime-modes/container-interactive-tui" />

:::tip
A imagem provisionada é cacheada como `invowk-provisioned:<hash>`, então execuções subsequentes são rápidas.
:::

## Vantagens

- **Reprodutibilidade**: Mesmo ambiente em todos os lugares
- **Isolamento**: Sem poluição do sistema host
- **Controle de versão**: Fixe versões exatas de ferramentas
- **Paridade CI/CD**: Builds locais correspondem aos builds do CI
- **Builds limpos**: Ambiente novo cada vez

## Limitações

- **Performance**: Overhead de inicialização do container
- **Espaço em disco**: Imagens consomem armazenamento
- **Complexidade**: Necessário gerenciar imagens
- **Acesso ao host**: Limitado sem ponte SSH

## Quando Usar Container

- **Builds reproduzíveis**: Quando consistência importa
- **Pipelines CI/CD**: Corresponder ambientes local e CI
- **Projetos legados**: Isolar versões antigas de ferramentas
- **Onboarding de equipe**: Sem necessidade de instalação local de ferramentas
- **Builds em ambiente limpo**: Testar sem poluição do host

## Solução de Problemas

### Container Não Inicia

```bash
# Verificar se engine de container está disponível
docker --version  # ou: podman --version

# Verificar se imagem existe
docker image inspect debian:stable-slim
```

### Primeira Execução Lenta

A primeira execução baixa a imagem. Execuções subsequentes são mais rápidas:

```bash
# Pré-baixar a imagem genérica recomendada
docker pull debian:stable-slim
```

### Problemas de Permissão

No Linux, você pode precisar configurar permissões do container:

```bash
# Para Docker
sudo usermod -aG docker $USER

# Para Podman (rootless)
# Geralmente funciona sem configuração
```
