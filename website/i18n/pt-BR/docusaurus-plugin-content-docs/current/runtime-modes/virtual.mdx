# Runtime Virtual-Sh

O runtime **virtual-sh** usa o interpretador de shell POSIX-compatível integrado do Invowk™ (powered by [mvdan/sh](https://github.com/mvdan/sh)). Ele fornece comportamento de shell consistente em todas as plataformas sem exigir um shell externo.

## Como Funciona

Quando você executa um comando com o runtime virtual-sh, o Invowk:

1. Faz o parse do script usando o parser de shell integrado
2. Executa-o em um ambiente embarcado tipo POSIX
3. Fornece utilitários core (echo, test, etc.) integrados

#### Identificação de Erros

Erros dos utilitários u-root são prefixados com `[uroot]` para fácil identificação:

```
[uroot] cp: /source/file: no such file or directory
[uroot] rm: /protected: permission denied
```

#### Sem Fallback Silencioso

Se um comando u-root falha, ele retorna um erro imediatamente. O sistema **não** faz fallback para binários do host, garantindo que bugs sejam detectados em vez de mascarados.

## Chamando Comandos Externos

O runtime virtual-sh pode chamar comandos do host apenas quando uma implementação opta explicitamente com `allowed_binaries`:

<Snippet id="runtime-modes/virtual-external-commands" />

Por padrão, a execução de binários do host é negada. Entradas nomeadas como `go` e `git` são resolvidas de acordo com `binary_lookup_mode`; `allowed_binaries: ["*"]` é a opção explícita que permite todos os binários do host.

:::caution Não é um Sandbox
O runtime virtual-sh **não é um sandbox de segurança**. Ele é um interpretador de shell portável com utilitários integrados e controles para binários do host. Qualquer binário do host permitido (ex.: `git`, `curl`, `python`, `node`) ainda executa como um processo nativo com acesso ao host. Por padrão, as variáveis de ambiente do host também são herdadas (`env_inherit_mode: "all"`).

Se você precisa de isolamento de execução, use o runtime **container**.
:::

## Acesso a Arquivos

Redirecionamentos e os utilitários integrados passam pelo validador de caminhos do Invowk. Por padrão (`virtual.filesystem.access: "restricted"`), um caminho precisa resolver para dentro de uma raiz permitida: o diretório de trabalho do comando, a raiz do script ou módulo, as âncoras `@tmp`, `@config`, `@data`, `@cache` e `@state`, `/tmp` (exceto no Windows) e as entradas de `virtual.filesystem.paths` da plataforma selecionada (veja [Caminhos E Arquivos](./virtual-lua#caminhos-e-arquivos)).

- **Os links são seguidos antes da verificação.** Todo link simbólico e toda junction do Windows no caminho é resolvido, mesmo quando as últimas partes do caminho ainda não existem.
- **Um link que sai das raízes permitidas é negado em qualquer profundidade**, com `virtual path denied`: `mkdir -p link/a/b` e `echo x > link-quebrado` falham quando o link aponta para fora. Um link ou junction cujo destino fica dentro de uma raiz permitida funciona.
- **Um caminho que não pode ser resolvido é recusado** (um ciclo de links, uma unidade ou compartilhamento inexistente), e uma entrada de `virtual.filesystem.paths` que não pode ser resolvida faz o comando falhar antes de o script rodar.
- **`/dev/stdout`, `/dev/stderr` e `/dev/stdin` não são arquivos quando o stream é um pipe** (Linux), então não podem ser abertos como caminhos. Escreva `echo msg >&2` ou `>&1`: uma duplicação de descritor não abre caminho nenhum.

Com `access: "full"` não há verificação de raízes permitidas, e um caminho que o validador não consegue resolver é passado ao sistema operacional como está.

Nos dois modos de acesso, um caminho que pode ser resolvido é usado na forma resolvida, exceto pelas operações que atuam sobre o próprio último componente:

- **Os caminhos são informados na forma resolvida.** Os valores de `INVOWK_PATH_*` e as mensagens `virtual path denied` mostram o destino do link ou da junction, não o link. Para as operações que atuam sobre o próprio link (abaixo), mostram o caminho do link: o seu diretório resolvido unido ao seu nome.
- **A maioria das operações segue um link ou junction até o destino:** ler e gravar arquivos, `cd`, `cp`, o destino de `mv` e todos os testes de arquivo, exceto `-L` e `-h`. O destino de `mv` é uma diferença conhecida em relação a um shell do host: `mv a link`, com `link` apontando para um arquivo, substitui esse arquivo e mantém o link, enquanto um shell do host substitui o link.
- **`rm`, as origens de `mv` e o nome do link de `ln` atuam sobre o próprio link** e não seguem o último componente. `rm link` e `rm -r link` removem o link e mantêm o destino, `mv link dir` move o link, e `ln -sf destino link` substitui um link existente, nunca o seu destino. Com acesso restrito, um link dentro de uma raiz permitida pode ser removido ou movido mesmo quando o destino fica fora delas; o destino permanece. No Windows, `rm -rf` de uma junction remove a junction e mantém a árvore de destino. No macOS, um `rm -r /tmp` restrito é recusado, porque o link `/tmp` fica fora da raiz permitida `/private/tmp`; `rm /tmp/arquivo` funciona.
- **Os testes `-L` e `-h` são verdadeiros para um link simbólico** e falsos para o seu destino (uma junction do Windows dá falso).
- **Um separador no final pede um diretório.** Um operando de `rm`, `mv` ou `ln` que termina em separador, `.` ou `..` é resolvido por completo: `rm -r dirlink/` remove o diretório de destino e mantém o link. Quando ele nomeia um link para um arquivo (`rm live/`, `rm -r live/`, `mv live/ x`, `ln -sf t live/`), o comando falha com `not a directory`, nomeando o caminho resolvido, e nada muda. O `ln` nunca substitui um diretório: um nome de link que nomeia um, em qualquer forma (`dir`, `dir/`, `dir/.`, `.` ou `link/` para um link para um diretório), falha com `cannot overwrite directory` e não remove nada.
- **`cd` e os testes `-r`, `-w` e `-x` verificam o acesso no caminho validado**, com os links seguidos, então `cd` para um link ou junction que aponta para um diretório funciona. Com acesso restrito, um caminho fora de todas as raízes permitidas torna esses testes falsos, e `cd` para ele falha com `cd: virtual path denied`.
- **Os utilitários integrados encontram os operandos do jeito que cada um interpreta os seus argumentos.** `--` encerra as opções, e todo operando é verificado, comece com o que começar. Os valores de opções passam como foram escritos, exceto os que nomeiam caminhos, como `tar -f`, que também são verificados, assim como o arquivo que o `gzip` grava para cada operando. `gzip -S` recusa um sufixo que contenha um separador de caminho.
- **`cp` e `tar -x` verificam os caminhos que derivam dos seus operandos.** Com acesso restrito, todo caminho que eles criam, gravam ou cujo modo alteram (o diretório de destino unido ao nome de cada origem, todo caminho abaixo dele no `cp -r`, toda entrada de um arquivo do `tar -x`) e todo link de origem que o `cp` segue sem `-P` é resolvido e precisa estar dentro de uma raiz permitida. Uma recusa recusa o comando inteiro com `virtual path denied`, antes que algo seja gravado. Para que esses caminhos sejam conhecidos de antemão, um `cp` restrito recusa uma origem posterior que não existe quando ele começa (uma primeira origem ausente mantém o erro simples "no such file"), o `cp -r` não grava em uma árvore de origem do mesmo comando (um diretório copiado para dentro de si mesmo), o `cp -P` só cria um link quando esse link é o seu único destino e recusa uma cópia que criaria um link ao lado de outras entradas (então `cp -P -r` de uma árvore que contém um link é recusado), e o `tar -x` só lê o arquivo de um arquivo regular, nunca da entrada padrão. Um link nomeado como operando do `cp` é resolvido, então `cp -P lnk d` copia o seu alvo. `access: "full"` mantém o comportamento do u-root dos dois comandos.

A verificação cobre apenas as operações de arquivo do próprio interpretador: um binário do host permitido roda como um processo normal do host e não tem seus caminhos verificados. Use o runtime **container** para isolamento.

## Vantagens

- **Consistência**: Mesmo comportamento no Linux, macOS e Windows
- **Sem dependência de shell**: Funciona mesmo se o shell do sistema não estiver disponível (o interpretador é integrado, mas comandos externos ainda exigem permissão explícita para binários do host)
- **Portabilidade**: Scripts funcionam em todas as plataformas
- **Utilitários integrados**: Utilitários core sempre disponíveis
- **Startup mais rápido**: Sem processo de shell para iniciar

## Quando Usar Virtual-Sh

- **Scripts multiplataforma**: Quando o mesmo script deve funcionar em todos os lugares
- **Pipelines CI/CD**: Comportamento consistente entre agentes de build
- **Scripts shell simples**: Quando você não precisa de recursos específicos do bash
- **Ambientes embarcados**: Quando shells externos não estão disponíveis
