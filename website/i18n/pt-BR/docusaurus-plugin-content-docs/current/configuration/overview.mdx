# Visão Geral de Configuração

Invowk™ usa um arquivo de configuração baseado em CUE para customizar seu comportamento. É aqui que você define suas preferências para container engines, caminhos de busca, padrões de runtime e mais.

## Localização do Arquivo de Configuração

O arquivo de configuração fica no diretório de configuração específico do seu SO:

| Plataforma | Localização |
|------------|-------------|
| Linux/outros Unix-like | `$XDG_CONFIG_HOME/invowk/config.cue` quando definido; caso contrário `~/.config/invowk/config.cue` |
| macOS      | `~/Library/Application Support/invowk/config.cue` |
| Windows    | `%APPDATA%\invowk\config.cue` |

Esses diretórios base precisam ser absolutos. Um `XDG_CONFIG_HOME` ou `APPDATA` relativo é ignorado e a próxima base é usada (`~/.config` ou `%USERPROFILE%\AppData\Roaming`); um diretório home ou `USERPROFILE` relativo é um erro. Assim, o arquivo de configuração do usuário e o `~/.invowk/cmds` nunca são resolvidos dentro do diretório atual.

Todos os outros locais por usuário seguem o mesmo princípio e nunca são resolvidos dentro do diretório atual. O `INVOWK_MODULES_PATH` precisa ser absoluto (um valor relativo é um erro). Os caches de módulos e de provisionamento derivam apenas de um home ou base absolutos. Uma entrada relativa em `SSH_KNOWN_HOSTS`, ou um home relativo quando chaves SSH são necessárias, faz falhar uma busca de módulo que não seja HTTPS. As demais bases `XDG_*`/`LOCALAPPDATA` relativas são ignoradas.

### Executando com `HOME` ausente (serviços e timers)

Units de sistema do systemd sem `User=` rodam com `HOME` ausente (veja `systemd.exec(5)`); units de usuário o herdam do gerenciador do usuário. Com `HOME` (ou `USERPROFILE`) ausente:

- a âncora do runtime virtual `@home` fica indisponível, assim como `@config`, `@data`, `@cache` e `@state`, a menos que a variável `XDG_*` ou AppData correspondente esteja definida; as variáveis `INVOWK_ANCHOR_*` delas ficam vazias, e um mapeamento de `virtual.filesystem.paths` sobre elas falha;
- buscas de módulos por qualquer transporte que não seja `https://` são recusadas;
- comandos de módulos precisam de `INVOWK_MODULES_PATH` definido com um caminho absoluto, porque o cache de módulos padrão fica no diretório home;
- o provisionamento de contêineres faz o build em um diretório temporário.

Comandos que não usam âncora derivada do home, cache de provisionamento nem busca por SSH rodam como antes. Para rodar os demais, adicione `Environment=HOME=/root` (ou outro diretório absoluto) ou `SetLoginEnvironment=yes` à unit, defina `INVOWK_MODULES_PATH` e as variáveis `XDG_*` necessárias com caminhos absolutos, ou busque módulos por HTTPS com `GITHUB_TOKEN`, `GITLAB_TOKEN` ou `GIT_TOKEN`.

## Qual Arquivo de Configuração É Usado

O Invowk lê exatamente uma fonte de configuração, escolhida nesta ordem:

1. `--ivk-config <caminho>` (`-c`). O caminho pode ser relativo ao diretório atual, já que você o digitou naquela linha de comando.
2. A variável de ambiente `INVOWK_CONFIG`. Ela precisa ser um caminho **absoluto**; um valor vazio conta como não definido.
3. O arquivo de configuração do usuário da tabela acima.
4. Os padrões embutidos.

A fonte escolhida é usada sozinha: valores de fontes de menor precedência nunca são mesclados, e uma fonte inferior nem chega a ser lida. **O diretório atual nunca é uma fonte de configuração**, então um repositório em que você entra com `cd` não consegue mudar seus includes, o endpoint de LLM ou o provisionamento de containers.

<Snippet id="config/env-config-path" />

Um arquivo nomeado explicitamente precisa funcionar. Se `--ivk-config` ou `INVOWK_CONFIG` apontar para um arquivo ausente ou inválido, ou se `INVOWK_CONFIG` for relativo, o invowk para com código de saída 1 antes de descobrir ou executar qualquer comando, e o erro nomeia a fonte e o caminho. (O `invowk audit` reporta isso com seu código de erro de varredura, 2; o `invowk agent` segue o contrato geral e sai com 1.) Um arquivo de configuração do *usuário* inválido é tratado como antes: o `invowk cmd` e os outros comandos de descoberta reportam um erro de carregamento de configuração e seguem com os padrões, enquanto `config show` e `config dump` reportam o erro.

`config show`, `config dump` e `config path` respeitam `--ivk-config` e `INVOWK_CONFIG`. `config set` e `config init` só mexem no arquivo de configuração do usuário, e `config set` se recusa a rodar (saída 2) enquanto `--ivk-config` ou `INVOWK_CONFIG` estiver ativo, para nunca copiar os valores de um arquivo explícito para a sua configuração de usuário.

:::warning Migrando de um `config.cue` no diretório atual
Versões anteriores também liam um `config.cue` do diretório atual quando não havia configuração de usuário. Esse fallback não existe mais, e nada avisa: o invowk usa os padrões silenciosamente. Mova o arquivo para o caminho da configuração de usuário (veja `invowk config path`) ou aponte `--ivk-config` / `INVOWK_CONFIG` para ele. Scripts que passavam `-c ausente.cue` e dependiam do antigo retorno aos padrões agora falham.
:::

## Ignorando os Comandos do Diretório Atual

`--ivk-no-cwd` (ou `INVOWK_NO_CWD=1`) impede a descoberta de comandos de carregar o `invowkfile.cue` do diretório atual e os módulos `*.invowkmod` irmãos. Os `includes` configurados, `~/.invowk/cmds` e os módulos provisionados continuam valendo. Afeta `invowk cmd` (listagem, execução, `@source`, `--ivk-dry-run`, `--ivk-watch`), o completion, o `invowk validate` do workspace e o `invowk module list`; alvos explícitos como `invowk validate <caminho>` e `invowk audit <caminho>` não são afetados, e `invowk agent cmd create|change --verify` é rejeitado enquanto a opção estiver ligada.

`INVOWK_NO_CWD` aceita `1`, `t`, `true`, `0`, `f`, `false` (qualquer forma que o `strconv.ParseBool` do Go aceite); qualquer outro valor não vazio é um erro. Um `--ivk-no-cwd` ou `--ivk-no-cwd=false` explícito vence a variável.

<Snippet id="config/no-cwd" />

O Invowk não traduz as flags em variáveis de ambiente para processos filhos. Se os seus comandos chamam o `invowk` de novo, defina as formas de ambiente no ambiente de quem chama: as invocações aninhadas as herdam pelas regras normais de `env_inherit_mode` do comando.
