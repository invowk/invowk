# Configuration Schema Reference

:::warning Alpha — Configuration Options May Change
The configuration schema is still being refined. Options **may be added, renamed, or removed** between releases as we finalize the feature set.
:::

Complete reference for the Invowk™ configuration file schema.

## Overview

The configuration file uses [CUE](https://cuelang.org/) format and is located at:

| Platform | Location |
|----------|----------|
| Linux/other Unix-like | `$XDG_CONFIG_HOME/invowk/config.cue` when set, otherwise `~/.config/invowk/config.cue` |
| macOS    | `~/Library/Application Support/invowk/config.cue` |
| Windows  | `%APPDATA%\invowk\config.cue` |

Configuration files are validated as closed structs, so unknown fields cause a validation error. The schema is the full effective configuration shape: user files may omit defaulted fields, and CUE materializes those defaults before Go validation runs.

## Config

The root configuration object.

<Snippet id="reference/config/config-structure" />

Fields marked as not required below may be omitted from a user-authored `config.cue`; they are still present in the effective `Config` after schema defaults are applied.

### container_engine

**Type:** `"podman" | "docker"`
**Required:** No
**Default:** `"podman"`

Specifies which container runtime to use for container-based command execution.

<Snippet id="reference/config/container-engine" />

If the preferred engine is not available, Invowk falls back to the other engine when container runtime is needed.

### includes

**Type:** `[...#IncludeEntry]`
**Required:** No
**Default:** `[]`

Additional modules to include in command discovery. Each entry specifies a path to an `*.invowkmod` directory with an optional `alias` for collision disambiguation.

<Snippet id="reference/config/includes" />

**Path requirements:**
- Paths must be absolute and end with `.invowkmod`
- Non-existent paths are silently ignored
- Duplicate paths are rejected

**Alias rules:**
- Aliases are optional, for collision disambiguation
- Each alias must be unique across all includes entries
- Aliases override the module's declared identifier for collision resolution

**Discovery priority (highest to lowest):**
1. Current directory invowkfile
2. Local modules (`*.invowkmod` in current directory)
3. Configured `includes` (in order) — explicit includes outrank the user directory
4. `~/.invowk/cmds` (modules only, non-recursive)

With `--ivk-no-cwd` (or `INVOWK_NO_CWD=1`), sources 1 and 2 are skipped; see [Ignoring the Current Directory's Commands](../configuration/overview#ignoring-the-current-directorys-commands).

### default_runtime

**Type:** `"native" | "virtual-sh" | "virtual-lua" | "container"`
**Required:** No
**Default:** `"native"`

Sets the global default runtime mode for commands that don't specify a preferred runtime.

<Snippet id="reference/config/default-runtime" />

| Value | Description |
|-------|-------------|
| `"native"` | Execute using the system's native shell |
| `"virtual-sh"` | Execute using Invowk's built-in shell interpreter |
| `"virtual-lua"` | Execute using Invowk's built-in Lua interpreter |
| `"container"` | Execute inside a container |

### virtual

**Type:** `#VirtualConfig`
**Required:** No
**Default:** `{utilities: {enabled: true}}`

Configuration for the virtual runtime family.

<Snippet id="reference/config/virtual-shell" />

### ui

**Type:** `#UIConfig`
**Required:** No
**Default:** `{color_scheme: "auto", verbose: false, interactive: false}`

User interface configuration.

<Snippet id="reference/config/ui" />

### llm

**Type:** `#LLMConfig`
**Required:** No
**Default:** `{}`

Default LLM backend configuration for LLM-aware commands. `invowk agent cmd create|change` and `invowk agent mod create|change` use this config when no LLM flags are passed. `invowk audit` still requires explicit opt-in with `--llm` or `--llm-provider` before it sends script content to an LLM.

<Snippet id="reference/config/llm-provider" />

Use `llm.api` for OpenAI-compatible endpoints when you want to configure an API backend without storing raw secrets in `config.cue`.

<Snippet id="reference/config/llm-api" />

### container

**Type:** `#ContainerConfig`
**Required:** No
**Default:** `{auto_provision: {enabled: true, strict: false, binary_path: "", includes: [], inherit_includes: true, cache_dir: ""}, tui_server_bind: "restricted"}`

Container runtime configuration.

<Snippet id="reference/config/container" />

## VirtualConfig

Configuration for the virtual runtime family.

<Snippet id="reference/config/virtual-shell-config-structure" />

### utilities.enabled

**Type:** `bool`
**Required:** No
**Default:** `true`

Enables u-root utilities in `virtual-sh` and command helpers in `virtual-lua`.

<Snippet id="reference/config/enable-uroot-utils" />

**Available utilities when enabled (28 total):**
- Upstream wrappers (12): `base64`, `cat`, `cp`, `find`, `gzip`, `ls`, `mkdir`, `mv`, `rm`, `shasum`, `tar`, `touch`
- Custom implementations (16): `basename`, `cut`, `dirname`, `grep`, `head`, `ln`, `mktemp`, `realpath`, `seq`, `sleep`, `sort`, `tail`, `tee`, `tr`, `uniq`, `wc`

Sets the color scheme for terminal output.

**Required:** No
**Default:** `false`

### interactive

**Type:** `bool`
**Required:** No
**Default:** `false`

Enables interactive mode by default (alternate screen buffer with PTY).

<Snippet id="reference/config/ui-interactive" />

## LLMConfig

Common LLM defaults and backend configuration. `DefaultConfig()` derives this from CUE and produces an empty defaults-only `llm: {}` object until the user configures a provider or API endpoint.

<Snippet id="reference/config/llm-config-structure" />

### provider

**Type:** `"auto" | "claude" | "codex" | "gemini" | "ollama"`
**Required:** No
**Default:** *(unset)*

Selects a supported provider or CLI harness. `auto` probes local Ollama, cloud API credentials, and CLI tools in provider order.

### model

**Type:** `string`
**Required:** No
**Default:** *(unset)*

Overrides the provider model. CLI harnesses use their own default when omitted.

### timeout

**Type:** Go duration string
**Required:** No
**Default:** *(unset in config; resolver fallback: `2m`)*

Sets the per-request timeout for LLM-backed commands.

### concurrency

**Type:** `int`
**Required:** No
**Default:** *(unset in config; resolver fallback: `2`)*

Limits concurrent LLM requests. Set `0` or omit the field to use the resolver fallback.

### api

**Type:** `#LLMAPIConfig`
**Required:** No
**Default:** *(unset)*

OpenAI-compatible API endpoint configuration. `provider` and `api` are mutually exclusive.
If `api` is present, set at least one of `base_url`, `model`, or `api_key_env`.

**Required:** No

Name of the environment variable containing the API key. Use this instead of storing raw API keys in `config.cue`.

## ContainerConfig

Configuration for container runtime behavior.

<Snippet id="reference/config/container-config-structure" />

### auto_provision

**Type:** `#AutoProvisionConfig`
**Required:** No
**Default:** `{enabled: true, strict: false, binary_path: "", includes: [], inherit_includes: true, cache_dir: ""}`

Controls automatic provisioning of invowk resources into containers.

<Snippet id="reference/config/container-auto-provision" />

With auto-provisioning enabled, Invowk builds a cached, derived image by attaching a small provisioned layer on top of your base image. This runs for every container execution (interactive or not); if provisioning fails, Invowk warns and uses the base image (unless `strict` is set), except for an unusable `binary_path`, which always fails the command.

### tui_server_bind

**Type:** `"restricted" | "all-interfaces"`
**Required:** No
**Default:** `"restricted"`

Controls how widely the TUI server of an interactive container run (`-i`) may listen. Host runtimes (native, virtual-sh, virtual-lua) always bind `127.0.0.1` and ignore this key.

- `"restricted"`: the server binds loopback plus, at most, the one address a verified engine mode routes to the host (the bridge gateway under local rootful Docker on Linux; nothing extra under Docker Desktop or ephemeral rootless Podman with pasta). In engine modes without such a route, an interactive run is **refused** before start (exit status 1), with an error that names this key; the same command without `-i` still runs.
- `"all-interfaces"`: in those modes, and under Docker Desktop, the server binds `0.0.0.0` as before v0.17.0, so anyone who can reach the host can reach the port (the per-session token still guards it). Invowk prints an exposure warning at every such run. The verified narrow modes keep their narrow bind.

<Snippet id="reference/config/container-tui-server-bind" />

This key is user configuration only: invowk reads it from the config file it selects, the `--ivk-config` or `INVOWK_CONFIG` file when one is given (your user config file is then not read), otherwise your user config file. It never reads it from an invowkfile or module, so a repository cannot widen the bind. It has no effect in Flatpak without `--share=network`, where no bind is reachable from the engine's containers. For a remote engine (a Docker endpoint other than a local `unix://`, `npipe://` or `fd://` socket, `podman-remote`, Podman machine) it helps only if the engine's host alias leads back to this machine. See [Interactive mode](../advanced/interactive-mode.mdx#container-runtime-support) for the per-engine rules.

## AutoProvisionConfig

Auto-provisioning configuration for container images.

<Snippet id="reference/config/auto-provision-config-structure" />

### enabled

**Type:** `bool`
**Required:** No
**Default:** `true`

Enables auto-provisioning of the invowk binary and modules into containers.

### strict

**Type:** `bool`
**Required:** No
**Default:** `false`

Makes provisioning failure a hard error instead of falling back to the unprovisioned base image. When `false` (the default), provisioning failure logs a warning and continues with the base image, except for an unusable `binary_path`, which always fails the command. A running invowk binary that is skipped because it cannot run in the container (see `binary_path`) is not a failure: the command runs with the warning either way.

### binary_path

**Type:** `string`
**Required:** No
**Default:** *(empty; uses the running invowk binary when it is a Linux executable for the image's architecture)*

The invowk binary to install in provisioned images, so that commands inside the container can run `invowk` themselves (in-container `invowk cmd` dependencies, `invowk tui` under `-i`). It runs inside a Linux container, so it must be a Linux executable (ELF) built for the image's architecture. Invowk reads the file's header before it installs it; it never runs the file to check.

- **Not set:** Invowk uses the running invowk binary. On a Linux host with the same architecture as the image, nothing changes. On a macOS or Windows host the running binary is a Mach-O or PE file, and on a Linux host it can be built for another architecture than the image (an amd64 host and an arm64 image, for example). Invowk then does not install it: it still provisions your modules and runs the command, prints a warning that names `container.auto_provision.binary_path`, and nested `invowk` calls inside the container do not work. One exception: on a Linux host, a run before the engine has the image assumes the host's architecture (see below), so on that first run the running binary is still installed in an image for another architecture, where it cannot run; from the next run, once the engine reports the image's architecture, it is skipped.
- **Set:** the file must be a Linux executable for the image's architecture. If it is missing, unreadable, not a Linux executable, or built for another architecture, the command fails with an error that names the path and the reason, whatever `strict` says.

Invowk learns the image's architecture from the container engine (a read-only `image inspect` of the base image; nothing is pulled or run for it). When the engine does not have the image yet, Invowk assumes the host's architecture on a Linux host and checks no architecture on other hosts. So on a Linux host, a `binary_path` built for an image of another platform fails on the first run with an error that says the architecture was assumed: pull the image first (`docker pull <image>` or `podman pull <image>`), or build its Containerfile, and run again.

To use nested invowk commands from a macOS or Windows host, download the Linux release archive for the image's architecture (`invowk_<version>_linux_amd64.tar.gz` for amd64 images, `invowk_<version>_linux_arm64.tar.gz` for arm64 images, such as the ones Docker Desktop runs on Apple silicon), unpack it, and set `binary_path` to the `invowk` file inside it. Leave it unset on a Linux host whose architecture matches the image.

### includes

**Type:** `[...#IncludeEntry]`
**Required:** No
**Default:** `[]`

Additional modules to provision into containers. Uses the same `#IncludeEntry` format as root `includes` (each entry has a `path` ending with `.invowkmod` and an optional `alias`).

### inherit_includes

**Type:** `bool`
**Required:** No
**Default:** `true`

When `true`, the root-level `includes` entries are automatically inherited by auto-provisioning. Set to `false` to provision only the modules explicitly listed in `container.auto_provision.includes`.

### cache_dir

**Type:** `string`
**Required:** No
**Default:** *(empty — uses platform-specific default, typically `~/.cache/invowk/provision`)*

Overrides the parent directory used for provision build contexts and cached image metadata.
