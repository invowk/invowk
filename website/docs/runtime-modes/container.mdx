# Container Runtime

:::danger Linux Containers Only

The container runtime **only supports Debian-based Linux container images** (e.g., `debian:stable-slim`).

**NOT supported:**
- **Alpine-based images** — musl-based environments have subtle behavioral differences that reduce runtime reliability
- **Windows container images** — No POSIX shell available

**Platform requirements:**
- **Linux**: Works natively with Docker or Podman
- **macOS**: Works with Docker Desktop (uses Linux VMs internally)
- **Windows**: Requires Docker Desktop with WSL2 backend in Linux containers mode

Scripts are executed using `/bin/sh` inside the container, which requires a standard POSIX-compatible shell environment.

:::

:::info Alpine Detection Scope

Invowk rejects images with exact name `alpine` or ending with `/alpine` (after stripping tags and digests). Images with "alpine" elsewhere in the name (e.g., `go-alpine-builder` or `myorg/alpine-tools`) are **not** automatically rejected. Avoid all musl-based images regardless of naming — the policy is about runtime reliability, not just image name matching.

:::

The **container** runtime executes commands inside a Docker or Podman container. It provides complete isolation and reproducibility - your command runs in the exact same environment every time.

## How It Works

When you run a command with the container runtime, Invowk™:

1. Pulls or builds the container image (if needed)
2. Mounts the invowkfile's directory into the container
3. Executes the script inside the container
4. Streams output back to your terminal

## Volume Mounts

Mount additional directories into the container:

<Snippet id="runtime-modes/container-volumes-full" />

By default, the invowkfile's directory is mounted to `/workspace`, and relative `volumes` entries resolve against the invowkfile or module directory. Standalone `<cwd>/invowkfile.cue` files may use relative paths, named container volumes, or absolute host bind mounts; `*.invowkmod` modules may use named volumes or relative paths within their containment ceiling, and cannot declare absolute host bind mounts.

## Workspace Mount and SELinux Labeling

Customize how `/workspace` is mounted per command with `workspace_mount`:

```cue
runtimes: [{
    name: "container"
    image: "debian:stable-slim"
    workspace_mount: {
        enabled: true              // Default: true; set false to omit /workspace mount
        root: "invowkfile"         // "invowkfile" (default) | "workdir"
        readonly: false            // Default: false; set true to mount /workspace:ro
        selinux_label: "auto"      // "auto" (default) | "shared" (:z) | "private" (:Z) | "none"
    }
}]
```

- **Three-tier containment:** Vendored, remote, and `~/.invowk/cmds` modules are strictly confined to their module root; modules in the current working directory may resolve `root: "workdir"` and relative `volumes` up to `<cwd>`; configured `includes` modules remain confined to the module root unless `workspace_root` sets a wider operator ceiling. Explicit CLI `--ivk-workdir` overrides act as explicit user consent.
- **Script decoupling:** Inline interpreter scripts and out-of-workspace `script.file` paths do not depend on a writable `/workspace` mount—for ephemeral containers, Invowk mounts them read-only under `/.invowk/` (retaining SELinux `:z` labels when SELinux is active) and cleans up temporary directories after container stop/removal.
- **Host SELinux policy:** Operators can set `container: { selinux_labeling: "disabled" }` in `config.cue` to pass `--security-opt label=disable` and omit automatic `:z` volume relabeling.

## Persistent Containers

### SSH Environment Variables

When `enable_host_ssh: true`, these variables are available:

| Variable | Description |
|----------|-------------|
| `INVOWK_SSH_ENABLED` | Set to `true` when SSH is active |
| `INVOWK_SSH_HOST` | Host address (e.g., `host.docker.internal`) |
| `INVOWK_SSH_PORT` | SSH server port |
| `INVOWK_SSH_USER` | Username (`invowk`) |
| `INVOWK_SSH_TOKEN` | Execution-scoped authentication token |

### Security

- Each command execution gets a unique token
- Tokens are revoked when the command completes, which also closes any SSH connection opened with them
- The SSH server only accepts token-based authentication
- The server shuts down after command execution

### Container Requirements

Your container needs `sshpass` or similar for password-based SSH:

```dockerfile
FROM debian:stable-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
    openssh-client sshpass \
    && rm -rf /var/lib/apt/lists/*
```

## Auto-provisioning

When `container.auto_provision.enabled` is `true` (default), Invowk builds a cached, derived image by attaching a small provisioned layer on top of your base image (either the `image` you specify or the image built from your Containerfile/Dockerfile). That layer includes any modules and, when it can run in the container, the `invowk` binary, so `invowk` commands are available inside the container.

The binary must be a Linux executable for the image's architecture. By default Invowk uses the running binary, which fits on a Linux host with the same architecture as the image. On a macOS or Windows host, or a Linux host of another architecture, Invowk leaves the binary out, still provisions the modules, runs the command and prints a warning: nested `invowk` calls inside the container then do not work until you set [`container.auto_provision.binary_path`](../configuration/options.mdx#containerauto_provisionbinary_path) to a Linux build for the image's architecture. A `binary_path` that is not such a build fails the command.

Auto-provisioning applies to image-based container executions, including both non-interactive and interactive runs. When a command targets an existing persistent container, Invowk skips image preparation and uses that container directly. For image-based runs, the derived image is cached as `invowk-provisioned:<hash>` and reused; if provisioning fails, Invowk warns and runs the base image only in the default non-strict mode. With `container.auto_provision.strict: true`, provisioning failure stops the command. An unusable `binary_path` stops the command in either mode.

Whether the binary is installed is part of the provisioned image's identity. A managed persistent container created with the binary left out (or with it) therefore no longer matches once that changes, for example after you set or remove `binary_path`, or on the first run after upgrading Invowk on a macOS or Windows host: the run fails with the existing "was created by invowk with a different runtime configuration" error until you remove the container.

## Interactive Mode

Container runtime fully supports interactive mode (`-i`). Interactive runs use the same provisioned image layer described above (when enabled) and add host-side TUI plumbing, enabling:

- TUI components as modal overlays
- Full PTY support for password prompts and confirmations
- Seamless integration with host terminal

```bash
# Run a container command interactively
invowk cmd myproject build -i -r container
```

When you run with `-i`, Invowk:

1. **Uses the provisioned image layer** (if enabled)
2. **Starts a TUI server** on the host
3. **Forwards TUI requests** from container to host
4. **Renders overlays** on your terminal

This means your scripts can use `invowk tui` commands inside containers:

:::tip

:::

## Advantages

- **Reproducibility**: Same environment everywhere
- **Isolation**: No host system pollution
- **Version control**: Pin exact tool versions
- **CI/CD parity**: Local builds match CI builds
- **Clean builds**: Fresh environment each time

## Limitations

- **Performance**: Container startup overhead
- **Disk space**: Images consume storage
- **Complexity**: Need to manage images
- **Host access**: Limited without SSH bridge

## When to Use Container

- **Reproducible builds**: When consistency matters
- **CI/CD pipelines**: Match local and CI environments
- **Legacy projects**: Isolate old tool versions
- **Team onboarding**: No local tool installation needed
- **Clean-room builds**: Test without host pollution

## Troubleshooting

### Container Not Starting

```bash
# Check if container engine is available
docker --version  # or: podman --version

# Check if image exists
docker image inspect debian:stable-slim
```

### Slow First Run

The first run pulls the image. Subsequent runs are faster:

```bash
# Pre-pull the recommended generic image
docker pull debian:stable-slim
```

### Permission Issues

On Linux, you may need to configure container permissions:

```bash
# For Docker
sudo usermod -aG docker $USER

# For Podman (rootless)
# Usually works out of the box
```
