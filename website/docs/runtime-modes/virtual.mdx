# Virtual-Sh Runtime

The **virtual-sh** runtime uses Invowk™'s built-in POSIX-compatible shell interpreter (powered by [mvdan/sh](https://github.com/mvdan/sh)). It provides consistent shell behavior across all platforms without requiring an external shell.

## How It Works

When you run a command with the virtual-sh runtime, Invowk:

1. Parses the script using the built-in shell parser
2. Executes it in an embedded POSIX-like environment
3. Provides core utilities (echo, test, etc.) built-in

#### Error Identification

Errors from u-root utilities are prefixed with `[uroot]` for easy identification:

```
[uroot] cp: /source/file: no such file or directory
[uroot] rm: /protected: permission denied
```

#### No Silent Fallback

If a u-root command fails, it returns an error immediately. The system does **not** fall back to host binaries, ensuring bugs are caught rather than masked.

## Calling External Commands

The virtual-sh runtime can call host commands only when an implementation explicitly opts in with `allowed_binaries`:

<Snippet id="runtime-modes/virtual-external-commands" />

By default, host binary execution is denied. Named entries such as `go` and `git` are resolved according to `binary_lookup_mode`; `allowed_binaries: ["*"]` is the explicit opt-out that allows every host binary.

:::caution Not a Sandbox
The virtual-sh runtime is **not a security sandbox**. It is a portable shell interpreter augmented with built-in utilities and host-binary gates. Any allowed host binary (for example `git`, `curl`, `python`, or `node`) still executes as a native process with host access. By default, the host's environment variables are also inherited (`env_inherit_mode: "all"`).

If you need execution isolation, use the **container** runtime instead.
:::

## File Access

Redirections and the built-in utilities go through Invowk's path validator. By default (`virtual.filesystem.access: "restricted"`) a path must resolve inside an allowed root: the command workdir, the script or module source root, the `@tmp`, `@config`, `@data`, `@cache` and `@state` anchors, `/tmp` (except on Windows), and the selected platform's `virtual.filesystem.paths` entries (see [Paths And Files](./virtual-lua#paths-and-files)).

- **Links are followed before the check.** Every symbolic link and every Windows junction on the path is resolved, also when the last parts of the path do not exist yet.
- **A link that leaves the allowed roots is denied at any depth**, with `virtual path denied`: `mkdir -p link/a/b` and `echo x > dangling-link` fail when the link points outside. A link or junction whose target stays inside an allowed root works.
- **A path that cannot be resolved is refused** (a link cycle, a missing drive or share), and a `virtual.filesystem.paths` entry that cannot be resolved fails the command before the script runs.
- **`/dev/stdout`, `/dev/stderr` and `/dev/stdin` are not files when the stream is a pipe** (Linux), so they cannot be opened as paths. Write `echo msg >&2` or `>&1` instead: a descriptor duplication opens no path.

With `access: "full"` there is no allowed-root check, and a path the validator cannot resolve is passed to the operating system as it is.

Under both access modes a path that resolves is used in its resolved form, except by the operations that act on the last component itself:

- **Paths are reported in resolved form.** `INVOWK_PATH_*` values and `virtual path denied` messages show the target of a link or junction, not the link. For the operations that act on the link itself (below), they show the link's own path: its resolved directory joined with its name.
- **Most operations follow a link or junction to its target:** reading and writing files, `cd`, `cp`, the destination of `mv`, and every file test except `-L` and `-h`. The `mv` destination is a known difference from a host shell: `mv a link` with `link` pointing to a file replaces that file and keeps the link, where a host shell replaces the link.
- **`rm`, the `mv` sources and `ln`'s link name act on the link itself** and do not follow the last component. `rm link` and `rm -r link` remove the link and keep its target, `mv link dir` moves the link, and `ln -sf target link` replaces an existing link, never its target. Under restricted access a link inside an allowed root can be removed or moved even when its target lies outside them; the target stays. On Windows `rm -rf` of a junction removes the junction and keeps its target tree. On macOS a restricted `rm -r /tmp` is refused, because the link `/tmp` lies outside the allowed root `/private/tmp`; `rm /tmp/file` works.
- **The `-L` and `-h` tests are true for a symbolic link**, and false for its target (a Windows junction tests false).
- **A trailing separator asks for a directory.** An operand of `rm`, `mv` or `ln` that ends in a separator, `.` or `..` is resolved in full: `rm -r dirlink/` removes the target directory and keeps the link. When it names a link to a file (`rm live/`, `rm -r live/`, `mv live/ x`, `ln -sf t live/`), the command fails with `not a directory`, naming the resolved path, and nothing changes. `ln` never replaces a directory: a link name that names one, in any form (`dir`, `dir/`, `dir/.`, `.`, or `link/` for a link to a directory), fails with `cannot overwrite directory` and removes nothing.
- **`cd` and the `-r`, `-w` and `-x` tests check access on the validated path**, with links followed, so `cd` into a link or junction to a directory works. Under restricted access a path outside every allowed root makes those tests false, and `cd` to it fails with `cd: virtual path denied`.
- **The built-in utilities find their operands the way each one parses its arguments.** `--` ends the options, and every operand is checked, whatever it starts with. Option values pass as written, except the ones that name paths, such as `tar -f`, which are checked too, and so is the file `gzip` writes for each operand. `gzip -S` refuses a suffix that contains a path separator.
- **`cp` and `tar -x` check the paths they derive from their operands.** Under restricted access every path they create, write or change the mode of (the destination directory joined with each source's name, every path below it for `cp -r`, every entry of a `tar -x` archive) and every source link `cp` follows without `-P` is resolved and must be inside an allowed root. One refusal refuses the whole command with `virtual path denied`, before anything is written. So that those paths are known in advance, a restricted `cp` refuses a later source that does not exist when it starts (a missing first source keeps its plain "no such file" error), `cp -r` does not write into a source tree of the same command (a directory copied into itself), `cp -P` refuses a copy that would create a link next to other entries (a copied tree's own directory is one of them, so `cp -P -r` of a tree that holds a link is refused), and `tar -x` reads its archive only from a regular file, never from standard input. A link named as a `cp` operand is resolved, so `cp -P lnk d` copies its target, and a restricted `cp -P` creates no link. `access: "full"` keeps the u-root behaviour of both commands.

The check covers the interpreter's own file operations only: an allowed host binary runs as a normal host process and is not path-checked. Use the **container** runtime for isolation.

## Advantages

- **Consistency**: Same behavior on Linux, macOS, and Windows
- **No shell dependency**: Works even if system shell is unavailable (the interpreter is built in, but external commands still require explicit host-binary permission)
- **Portability**: Scripts work across all platforms
- **Built-in utilities**: Core utilities always available
- **Faster startup**: No shell process to spawn

## When to Use Virtual-Sh

- **Cross-platform scripts**: When the same script must work everywhere
- **CI/CD pipelines**: Consistent behavior across build agents
- **Simple shell scripts**: When you don't need bash-specific features
- **Embedded environments**: When external shells aren't available
